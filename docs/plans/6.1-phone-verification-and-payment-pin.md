## Summary

Four flows in the mini program need the same thing — proof that the caller controls a phone number: binding or changing the number, resetting the password, cancelling the account, and the **payment PIN** that guards the balance tender. The client sends the code from three different endpoints, verifies it from one, and never says what it is for (`grep purpose` over the restored source returns nothing), so the purpose has to be inferred from which endpoint issued it.

The client also fixes two shapes worth stating before anything else: the verification endpoint is **not consuming** — `set-pay-pwd` posts the same code twice, once to `common/checkPhoneCode` and again to `info/updatePaySetting` — and the payment PIN is **per-user, not per-store**, with two independent booleans (whether one exists, whether it is required) that the client reads from `info/getPaySettingByUserId`.

Nothing in Spree does any of this. There is no OTP model, no PIN, and the only rate limiting is `ActionController::RateLimiting` keyed by IP — which does not stop SMS pumping aimed at one number range from many addresses.

## Key Decisions (do not deviate without discussion)

- **One code table, two purposes.** The client's own endpoints separate the purposes it cares about: `common/sendPhoneCode` issues for every account flow, `info/sendPayPasswordCode` issues for the PIN. A code issued for one purpose family is refused by the other. Finer purposes are deliberately not modelled, because the client's verify endpoint cannot tell them apart — `common/checkPhoneCode` serves bind, phone change, password reset and cancel with no discriminator, so pretending to know which one it is would be a check that cannot be enforced.
- **The check does not consume; the write does.** `checkPhoneCode` is a pre-check that the client re-sends the code past. Consumption happens inside the transaction of the write that needed the proof, so a code cannot be replayed onto a second write.
- **A code is keyed by phone, not by customer.** The change-phone flow sends a code to a number that belongs to nobody yet.
- **The PIN is its own table, not a column on the customer.** `docs/plans/decisions.md` (2026-09-18, the birthday entry) prefers a nullable column on `spree_customers` for **profile data**. A PIN is not profile data: it is a credential with a lockout, a rotation story and an erasure rule the gem must own, and its failures are a security event rather than a profile edit. The distinction is stated here so the precedent is not read as ignored.
- **The PIN is enforced on the server, in the tender, through one core seam.** The client asks for the PIN only when the server's own `balanceNotPassword` flag says to, and sends it in plaintext on the pay call — so a client-only check is no check at all. The seam is the plan's one core change and is recorded in `fork-decisions.md`, following the `async_refunds?` precedent.
- **`balanceNotPassword` means "this customer has no PIN that is required", never "this order skips the check".** The client treats the flag as licence to send an empty string, so a per-order meaning would make the flag a way to pay without a PIN by choosing the right order.
- **Login is not one of the four flows.** WeChat attests the phone through `encryptedData` + `session_key` (`pagesB/login/login.js:197-245`); no SMS code is involved, and the decryption exists nowhere in the fork today. That work belongs to `spree/providers/social_auth`, which the architecture plan's "Not a gem: extend official work" table assigns it — this plan only names the owner, because `6.1-store-api-miniprogram-gaps.md:87` and `6.0-social-login.md:150` currently point at different owners.
- **Send through our own notification gem; do not build an SMS sender.** `6.1-notifications.md` is the platform's one system-notification sender — the marketplace relay beside it is a buyer-seller conversation, not a sender — and this code arrives as that gem's **`sms` channel**: the door, the enqueue and the retry policy are the gem's, while the provider transport, the signed template and the verification-code semantics are this plan's.
- **A code lives in a table, verified through a digest (ruled 2026-09-18).** The two alternatives — a `generates_token_for`-style signed token with no table (`spree/core/app/models/concerns/spree/customer_methods.rb:29-36`) and `Rails.cache` as the rate limiter already uses — cannot count attempts across processes nor answer "what did we send, to which number, how often", which the per-phone limit and any abuse review both need. **Accepted trade-off:** a write per send, and a BCrypt verification (~100 ms) per check.
- **The check does not consume; the write consumes (ruled 2026-09-18).** The client posts the same code twice by design — `checkPhoneCode` and then `info/updatePaySetting` — so a consuming check would break `set-pay-pwd`, and returning a token instead would break it differently, since the client has nowhere to carry one. **Accepted trade-off:** within its five-minute window a code may pass the check repeatedly; it can still be spent exactly once, because consumption happens inside the writing transaction.
- **The PIN lives in its own table, not on the customer (ruled 2026-09-18).** The birthday precedent at `fork-decisions.md` (2026-09-17, “The birthday is a core customer column”) settles where **profile data** goes; a credential with a lockout, a rotation story and an erasure obligation is not profile data, and a gem-owned row lets the gem own all three. **Accepted trade-off:** one extra read on the pay path.
- **The PIN is enforced by a core seam, not in the API layer alone (ruled 2026-09-18).** The seam is named, because "a registry consulted by the balance settlement path" names nothing: **`Spree.payment_verifications`**, a new key on `Rails.application.config.spree`, **consulted once by `Spree::StoreCredits::Apply`** (`spree/core/app/services/spree/store_credits/apply.rb`, the service behind `carts/store_credits` and `admin/orders/store_credits` today, and the one the order-level balance payment joins when `6.1-store-api-miniprogram-gaps.md` builds it). The gem registers a `payment_pin` verification with it. A registry rather than an API-layer check, because the latter guards exactly one caller; a generic capability rather than a business rule, so it lands in core and is recorded in `fork-decisions.md`, the `async_refunds?` precedent. **Accepted trade-off:** one new core file and one edited one (`apply.rb` gains the consult), both named here.

## Design Details

### The code

```ruby
create_table :spree_verification_codes do |t|
  t.references :store, index: true
  t.string   :phone, null: false            # normalized: digits only, no +86
  t.string   :purpose, null: false          # account / payment
  t.string   :channel, null: false          # sms / voice
  t.string   :code_digest, null: false
  t.integer  :attempts, null: false, default: 0
  t.datetime :expires_at, null: false
  t.datetime :verified_at
  t.datetime :consumed_at
  t.datetime :deleted_at
  t.timestamps
end
```

- No `status` column. Three of the four states a reader wants (pending, verified, consumed) are stamped timestamps and the fourth (expired) is `expires_at < now`, which needs no job to write. A status column here would be a second source of truth for facts the timestamps already carry.
- `code_digest` is BCrypt through `has_secure_password :code`, with the plaintext never stored and the code never logged. A 6-digit space is 10⁶ and BCrypt costs about 100 ms per check, which is the right trade for a value with a five-minute life and a five-attempt cap; a bare digest of a six-digit number is reversible in seconds.
- Index on `(phone, purpose, expires_at)`. `Spree::SingleStoreResource` and `Spree::Metadata` as for any store-scoped model; no `has_status`.
- Expiry **5 minutes**, attempts **5**, both `Spree::Store` preferences rather than constants, because the client sets neither (it shows a 60 s resend window and nothing else).

### Sending

`POST /api/v3/store/verification_codes` with `{phone, purpose, channel, ticket}`.

- **Purpose is inferred by the caller, and enforced by the route.** The client's `sendPayPasswordCode` is a different URL from `sendPhoneCode`, so the purpose is unambiguous at issuance even though it never appears in a payload.
- **Captcha.** Every send in the client is gated on a Tencent captcha ticket (`phoneCodeBehavior.js:19-24`, the plugin at `wxplugins/wxb3e17776051baf153`), which means a send endpoint that ignores it is strictly weaker than the client. The ticket is validated when the store has Tencent captcha credentials configured; when it does not, the rate limits below are the whole defence. Voice codes require it whenever it is configured, because voice is the expensive channel.
- **The send never says whether the code was correct — or whether the phone exists.** One response for a registered number, an unregistered one and a rate-limited one; the client shows a countdown either way.

### Verifying and consuming

`POST /api/v3/store/verification_checks` with `{phone, purpose, code}` — a create, not an action, so the check is a resource whose creation either succeeds or fails.

- It marks `verified_at`, counts a failed attempt otherwise, and **consumes nothing**. The client's set-PIN flow re-sends the same code to the write; consuming at the check would break it, and returning a token instead would break it differently, since the client has nowhere to carry one.
- The write consumes: `Spree::VerificationCode.consume!(phone:, purpose:, code:)` re-verifies inside the caller's transaction and stamps `consumed_at`. A consumed code is refused by both paths, so the check-then-write pair spends the code exactly once.
- A code is valid for its own purpose family only. `payment` codes are not accepted by the account flows and vice versa.

### Rate limits

Two buckets, because they stop different attacks:

- **Per IP**, the existing mechanism: `ActionController::RateLimiting` with a new `rate_limit_verification_send` preference beside the others (`spree/api/lib/spree/api/configuration.rb:12-18`), declared the way `password_resets_controller.rb:10-13` already does. This stops a single host enumerating numbers.
- **Per phone**, in `Rails.cache`, 3 per 10 minutes and 10 per day. This is the one that stops SMS pumping — many addresses, one number range, one bill. The existing per-IP bucket cannot see it, and the client's only client-side guard is a `sendCode` flag it sets itself (`phoneCodeBehavior.js:20`).

### The payment PIN

```ruby
create_table :spree_payment_pins do |t|
  t.references :store, index: true
  t.references :customer, null: false, index: true
  t.string   :pin_digest, null: false
  t.boolean  :required, null: false, default: true
  t.integer  :failed_attempts, null: false, default: 0
  t.datetime :locked_until
  t.datetime :deleted_at
  t.timestamps
end
```

- Unique on `(store_id, customer_id)` with `scope: spree_base_uniqueness_scope`, enforced by the index.
- `required` is the client's `display` switch — the PIN exists but the customer turned the prompt off. `has a PIN` is the row existing. The two are independent in the client and stay independent here (`pagesB/me/personal/info/info.wxml:49` renders three states from them).
- Six digits, BCrypt again, with the same reasoning. The server repeats the client's two rules — no all-same-digit, no simple sequence (`set-pay.js:37`, `verifi-phone.js:119-125`) — because a client-side rule is a suggestion.
- **Lockout:** 5 failures then 30 minutes, shaped after `Spree::AccountLockout` (`spree/core/app/models/concerns/spree/account_lockout.rb`) without reusing the module, which is bound to login. A lockout with no unlock path is a support hole, so the admin endpoint below exists from the first release.
- **Per user, not per seller.** Every PIN call in the client carries `id: user.id` and reads `getPaySettingByUserId`; `siteId` rides every request (`static/config/api.js:42`) and appears in no PIN call. Stated because the rest of this plan set is seller-scoped.
- **Erasure.** `decisions.md` (upstream, 2026-09-02: EU compliance ships whole in open source, “subject requests are asynchronous”) anonymizes phones across the customer, the address book, address snapshots and OAuth identities on GDPR erasure; the PIN row is destroyed in the same pass, and a phone change never resurrects it.

### Where the PIN is enforced

The client asks only for `PayType.BALANCE` (`miniprogram/static/types/commonTypes.js:5`); cash and WeChat Pay never prompt (`settlement.js:775,1024-1026`, `details.js:136`). So the rule is: **a settlement that spends the balance tender must present a valid PIN when the customer has one that is required.**

- One core seam, named: **`Spree.payment_verifications`**, consulted once by `Spree::StoreCredits::Apply` (`spree/core/app/services/spree/store_credits/apply.rb`), so the gem registers a `payment_pin` check rather than decorating anything. This is the plan's only core change, it is generic (any tender may want a second factor), and it is recorded in `fork-decisions.md` per the `async_refunds?` precedent — a gem needing missing behaviour puts the capability in core. **It is two files: one new (the registry key) and one edited (`apply.rb`), and both are named rather than implied.**
- The flag the client reads must be the server's own verdict, computed the same way on the price preview and on the order payload: `balanceNotPassword: true` iff the customer has no required PIN. Both paths answer with the same computation, because a difference between them is exactly how a customer pays without a PIN.
- `payPassword` is plaintext on the wire and must be added to the parameter filter list; it is never logged, never serialized back, and never echoed in an error.

### Client contract to preserve

- `info/getPaySettingByUserId` → `{display, havePayPasswd}`; the plan folds it into `pay_config` (`6.1-scenario-purchases.md:92`) rather than keeping a second read.
- `setOpenPaySetting` refuses to enable when no PIN exists — the client offers 去设置 instead (`pay.js:46-56`). The server refuses it too.
- `setPayCloseSetting` demands the existing PIN, labelled 输入密码 (`verifi-phone.wxml:28,30`), so DELETE takes the PIN and a code.

## Store API Surface

| Method and path | Replaces |
| --- | --- |
| `POST /api/v3/store/verification_codes` | `common/sendPhoneCode`, `common/sendPhoneVoiceCode`, `info/sendPayPasswordCode` — `purpose` and `channel` select which |
| `POST /api/v3/store/verification_checks` | `common/checkPhoneCode` — non-consuming |
| `GET /api/v3/store/payment_pin` | `info/getPaySettingByUserId` (also reported through `pay_config`) |
| `PUT /api/v3/store/payment_pin` | `info/updatePaySetting` — set or change, consumes a `payment` code |
| `PATCH /api/v3/store/payment_pin` | `info/setOpenPaySetting` — the `required` switch, no code |
| `DELETE /api/v3/store/payment_pin` | `info/setPayCloseSetting` — the existing PIN plus a code |
| `DELETE /api/v3/admin/customers/:id/payment_pin` | new — support recovery from a lockout |

Six store routes for eight client endpoints. Every one declares `resource_permitted_attributes`, takes flat params, returns prefixed IDs, and scopes to `current_store`; the check is a create on a resource rather than a custom action, which is what the repo asks for instead of `POST .../verify`.

## Constraints on Current Work

- **Do not consume a code at the check.** The client sends it twice by design; a consuming check breaks `set-pay-pwd` and an unverified `authCode` is worse than the alternative.
- **Do not accept a code issued for the other purpose family**, and do not add a purpose the client cannot send.
- **Do not store a code or a PIN in plaintext, log either, or return either.** They join the parameter filter list in the same change that adds them.
- **Do not let `balanceNotPassword` vary by order.** It is a fact about the customer's PIN, computed once and reported identically from the preview and the order payload.
- **Do not decorate `Spree::Customer`** for the PIN; the core change this plan needs is the tender seam, not a customer column.
- **Do not build mini-program login here.** It belongs to `spree/providers/social_auth` (the architecture plan's "extend official work" table), and the `session_key` decryption it needs is currently owned by nobody — say so in that plan rather than growing a second path here.
- **Do not add a second outbound channel mechanism.** SMS arrives through `spree_notifications`' channel registry.
- **Wire the gem in three places or its specs never run:** `server/Gemfile`, `.github/workflows/tests.yml`, `scripts/test/rspec` — the two shipped provider gems currently miss the middle one.

## Open Questions

The four questions this plan opened — where a code lives, whether the check consumes it, where the PIN lives and where it is enforced — were settled on 2026-09-18 and now sit in **Key Decisions** with their trade-offs.

One item is genuinely deferred: **whether a send must present a captcha ticket, or merely be validated when one is presented.** The client always sends one (`phoneCodeBehavior.js:19-24`), but validating it server-side means a Tencent captcha credential and a call to their API, which this plan does not budget for. What unblocks it: deciding whether the store configures Tencent captcha at all. The rate limits in this plan are the defence either way, and voice codes require a ticket whenever one is configured.
