# WeChat Pay Gateway (`spree_wechat_pay`)

**Status:** In Progress — Phases 0–4 implemented 2026-09-10 (contract freeze,
core async-refund capability + gem skeleton, Native, JSAPI, mini program). The
remaining two scenes, refunds, partner mode and 付款码 are not built.
**Target:** Spree 6.0
**Depends on:** `6.0-payment-gateways-monorepo.md` (the gateway shape this follows), payment sessions in core (shipped), `6.0-payment-method-rules.md` (rules layer on top, not required)
**Author:** Damian Legawiec + Claude
**Last updated:** 2026-09-10

**Corrections after an open-source review (2026-09-10).** Three defects were
found by comparing this work against the official SDKs and the community
ecosystem, and are fixed:

- **`async_refunds?` is now false on the gateway until refunds are built.** It
  was true from Phase 1, and claiming the capability without a refund API is
  worse than not having it: `Refunds::Create` starts the refund in `processing`,
  the credit call fails because no `credit` verb exists, and the row is kept —
  because that is what opting in means — leaving a refund that reserves the
  payment's balance forever with nothing able to resolve it.
- **The CNY restriction is enforced, not just documented.** `available_for_order?`
  refuses any other currency. The payload hardcodes `CNY` while the amount comes
  from the order, so a non-yuan order would have sent that currency's minor units
  labelled as yuan.
- **WeChat's error `field` is read from where it actually lives.** It is nested
  under `detail`, alongside the `issue` that says what to change. The previous
  code read it from the top level, where it is always nil, and the spec encoded
  the same wrong assumption — which is why the bug stayed green.

**Response signature verification and the replay window (2026-09-10).** The two
remaining obligations from that review are now met:

- **Every answer is verified before it is believed.** WeChat signs each
  response, and that signature is the whole of what distinguishes an answer from
  WeChat from one written by whatever the request happened to reach — a
  `code_url`, a transaction state or a certificate set. `Client` now checks it
  before parsing, and reports a failure as an unknown outcome rather than as a
  refusal, because an unattributable answer says nothing about whether the
  request took effect. The single exception is the platform certificate
  download, which cannot be verified against the keys it exists to fetch; every
  official SDK carves out the same call for the same reason.
- **The five-minute replay window is enforced.** A WeChat signature never
  expires on its own, so a notification captured today would verify exactly as
  well tomorrow — and a replayed `TRANSACTION.SUCCESS` reads like a genuine one.
  `Verifier` now refuses anything more than five minutes from now in either
  direction, which is WeChat's own rule and the only thing bounding a replay.

## Implementation status — Phase 4, mini program (2026-09-10)

The mini program works. It shares every line of the pipeline with JSAPI — the
same order endpoint, the same payload shape, the same notification and
settlement path — and differs in exactly two places, both of which are why the
plan phased it separately.

**What shipped.** The `jscode2session` exchange in `Oauth`, the
`mini_program_app_secret` credential, and the mini program branch of
`LaunchParameters`.

**The two differences, both verified.**

- **A different code at a different path under a different name.**
  `GET /sns/jscode2session` with `js_code` rather than `/sns/oauth2/access_token`
  with `code`. The response additionally carries a `session_key`, which this gem
  has no use for — nothing here decrypts mini program payloads.
- **The launch call carries no `appId`.** The signed string is unchanged — the
  first line is still the identifier — but the field is not sent, because the
  mini program's own identity is implicit. This matters more than it looks:
  sending it anyway is not an error WeChat reports, the payment simply does not
  start. The rule lives in `LaunchParameters` rather than in the caller, and a
  spec asserts both the omission and that the signature still covers the
  identifier.

**Verification:** `spree/providers/wechat_pay` — 163 examples, 0 failures.

## Implementation status — Phase 3, JSAPI (2026-09-10)

JSAPI works: the storefront redirects the customer to WeChat, receives an
authorization code, and passes it in `external_data`; the gateway exchanges it
for the payer's openid server-side and returns a finished, signed launch
parameter set.

**What shipped.** `SpreeWechatPay::Oauth` (the code exchange),
`SpreeWechatPay::LaunchParameters` (the parameter set the storefront passes
through), the `payer.openid` field on the JSAPI order, and the
`jsapi_app_secret` credential.

**The OAuth contract, verified.** The exchange is
`GET https://api.weixin.qq.com/sns/oauth2/access_token` with
`appid`, `secret`, `code`, `grant_type=authorization_code` — confirmed against
the official documentation. What matters more than the URL is that this is a
different world from the payment API: a different host, no merchant certificate,
no v3 signature, and nothing shared with `Client`. The documentation does not
state what HTTP status an error carries, so **the body's `errcode` is the only
thing consulted** — reading the status would report "no openid returned" for
every refusal and name nothing an operator could act on. Codes are mapped to
what each actually means: a spent or expired code is the customer starting over
(codes are single use and live five minutes), a rejected appid or secret is a
configuration mistake.

**Two decisions the plan did not make.**

- **The authorization code is required; a supplied openid is not accepted.**
  An openid handed over by the browser would be an identity the browser chose.
  The code is exchanged here, and the AppSecret never leaves the server.
- **`IMPLEMENTED_SCENES` guards the scene vocabulary.** `enabled_scenes` accepts
  all five scenes so a merchant's configuration survives an upgrade, but
  enabling one that is not built refuses plainly. Without it, enabling the mini
  program today would have failed deep inside payload building with nothing
  pointing at the cause.

**Verification:** `spree/providers/wechat_pay` — 156 examples, 0 failures.

## Implementation status — Phase 2, Native (2026-09-10)

The Native scene works end to end: a merchant order number is generated, a
transaction is created, a signed and encrypted notification is verified and
decrypted, the session settles, and the payment carries WeChat's own
identifiers. One scene is implemented, so a store can take a WeChat payment by
QR code and nothing else.

**What shipped.** `SpreeWechatPay::MerchantOrderNumber` (the charset and length
rules, with the random suffix never truncated), `SpreeWechatPay::Transaction`
(create, query, close, and WeChat's state vocabulary in one place),
`Spree::PaymentSessions::WechatPay`, and the gateway's two concerns —
`PaymentSessions` for create/update/complete and `Webhooks` for
verification and event mapping.

**Three things the implementation settled.**

- **The query string is inside the signature.** WeChat documents a fifth case
  for requests carrying query parameters, and the URL line of the signed string
  includes them, percent-encoded. So `Transaction#query` builds the full path and
  the client signs that string rather than a bare path — a distinction that would
  otherwise have produced `SIGN_ERROR` on every lookup.
- **The session's own expiry is not the token's.** `expires_at` follows the
  transaction (seven days, WeChat's default when `time_expire` is omitted) and
  the launch token carries its own two-hour deadline in `external_data`. Setting
  the session's expiry from the token would have killed a Native session two
  hours in while the transaction stayed payable.
- **Renewal is the update verb, not a fourth one.** The storefront re-submits
  the session and the gateway re-issues when the token has lapsed and does
  nothing when it has not, so there is no new route to get wrong.

**One core gap closed.** `parse_webhook_event` is documented as returning
`metadata` — the provider's own identifiers for what happened — but the webhook
controller and the job dropped it, so `PaymentSession#apply_settlement_metadata`
could never receive anything. Three lines now carry it through, which is what
puts WeChat's transaction number on the payment and is what the refund phases
will need for their own records.

**One bug the specs caught.** `PaymentSessions::WechatPay#payload_expires_at`
memoized its parsed value, so after a renewal rewrote `external_data` the session
still reported the old token as lapsed — sending the storefront into a renewal
loop. It is no longer memoized, and the reason is recorded next to it.

## Implementation status — Phase 1 (2026-09-10)

Shipped, and verified by running the suites. The gateway has no scene yet, so it
cannot take a payment: what exists is the async-refund capability in core and the
plumbing every scene will sit on.

**Core.** `Spree::PaymentMethod#async_refunds?` (false by default),
`spree_refunds.status` with `processing`/`completed`/`canceled` via `has_status`,
`Spree::Refund.holding_balance` and a `credit_allowed` that reads it,
`Refunds::Create` starting an async gateway's refund in `processing` and keeping
the row when the credit call fails, and `status` on the admin refund serializer
only.

Two things the implementation settled that the design left open:

- **`holding_balance` is written as `status != 'canceled' OR status IS NULL`
  rather than as a list containing nil**, because `IN (NULL, …)` matches no row
  in SQL. A NULL status counts as still holding balance: the failure that matters
  is releasing money that is still committed, which would let the same amount be
  refunded twice.
- **A NULL-tolerant scope means the backfill is not load-bearing.** The migration
  still backfills existing rows to `completed`, but a row that escapes it — raw
  SQL, a restore from an older dump — is treated the safe way rather than the
  convenient one.

**Gem.** `spree/providers/wechat_pay`, gem `spree_wechat_pay`, registered by its
engine and wired into both branches of `server/Gemfile`. Signing (request and the
three launch variants), verification, notification decryption, the certificate
store and the Faraday client. `async_refunds?` is true; capture methods other
than `checkout` are refused at save time.

One design change the tests forced: **`CertificateStore` takes an injected cache
and fetches once when the cache is cold.** The first implementation read the
cache and nothing else on the strength of "no network I/O on the webhook path",
which is wrong in any environment whose cache store does not persist —
`:null_store` is the Rails test default, and a host can choose it deliberately. A
cold cache there did not mean a slower verification, it meant *no* verification,
and WeChat answers an unverifiable notification by retrying it fifteen times.
Fetching once is bounded, and concurrent fetches converge because every writer
merges into the same set.

## Summary

Add WeChat Pay (微信支付) as an optional payment gateway gem at
`spree/providers/wechat_pay` (gem `spree_wechat_pay`), implementing core's
payment-session contract the same way `spree_stripe` does. WeChat Pay is the
dominant consumer payment method in mainland China, and its API differs from
every gateway Spree ships today in ways that reach back into core: there is no
official Ruby SDK, no general authorize-then-capture split, no stored
instruments, no webhook endpoint registration, and refunds settle
asynchronously.

Five payment scenes ship: JSAPI (inside the WeChat browser), mini program,
Native (scan a QR code), H5 (mobile browser outside WeChat), and APP. One
gateway class serves all of them; the scene is chosen per payment session.

The gem holds its credentials in payment-method preferences, following the
cardinality decision in `decisions.md` (2026-07-30) — payment credentials live
on `PaymentMethod` rows, never on `Spree::Integration`. It ships no migrations
and owns no tables.

One core change ships with this plan: a narrow async-refund capability, so a
gateway whose refund settles after the API call can record that honestly
instead of reporting success it cannot guarantee.

## Key Decisions (do not deviate without discussion)

1. **Own gem under `spree/providers/`, following the established shape.**
   Directory `spree/providers/wechat_pay`, gem `spree_wechat_pay`, class
   `SpreeWechatPay::Gateway`, wire type `wechat_pay`. Lockstep version
   (`s.version = Spree.version`), a `spree_core` dependency floored at that
   version (`>= #{s.version}`, matching what `spree_stripe` ships rather than
   the stricter pin this decision first described), and `faraday` as the gem's
   own dependency — never core's. The `spree` meta gem must not depend on it.

2. **The class name is `SpreeWechatPay`, not `SpreeWeChatPay`.** The class name
   is written into `spree_payment_methods.type`, so changing it later costs a
   data migration. `wechat_pay` is what Rails' inflector turns into `WechatPay`;
   the alternative spelling would need a `we_chat_pay.rb` file to satisfy the
   autoloader. `Spree::Gateway.api_type` already derives `wechat_pay` from the
   outer module, so no override is needed.

3. **Credentials live in payment-method preferences, not `Spree::Integration`.**
   `decisions.md` (2026-07-30, "Credential homes follow cardinality") settles
   this: payments have one credential set *per merchant entity*, several per
   store, which is exactly what `PaymentMethod` rows model. Integrations are for
   store-level singleton connections (delivery, tax) and their `(store, type)`
   uniqueness actively fights the merchant-entity model. Note
   `6.0-integrations-admin.md`'s blanket "new provider gems must ship an
   Integration subclass" constraint is written for the delivery/tax/fulfillment
   seams and does not govern payment gateways.

4. **One gateway class, scene chosen per session.** WeChat Pay is one merchant
   account with several products switched on, so one `PaymentMethod` record
   configures one merchant account and the merchant ticks which scenes are
   enabled. The storefront asks for the scene it can actually drive
   (`external_data.scene`); the gateway validates it against the enabled set and
   rejects an unenabled scene with a structured error rather than silently
   substituting one.

5. **The session's `external_id` is our own merchant order number, not WeChat's
   transaction id.** WeChat assigns its transaction id only after payment, but
   the notification and the refund both key off the merchant order number. This
   matters beyond convenience: core hands `payment.response_code` straight to
   `credit` when a refund is created, and WeChat's refund API accepts a merchant
   order number, so the identifier needs no translation on the refund path.
   WeChat's transaction id and the payer's openid go in `external_data`.

6. **The payer's openid is obtained by the gateway, not the storefront.** Web
   authorization requires the official account's AppSecret, so the storefront
   cannot hold it and a browser cannot be trusted with it. The storefront passes
   the authorization code it received from WeChat as `external_data.code`, and
   `create_payment_session` exchanges it for the openid server-side. Accepted
   trade-off: the storefront must do the redirect step and needs the plugin's
   documentation to do it correctly; in exchange there is no new endpoint, no
   second round trip, and the AppSecret never leaves the server.

7. **Capture at checkout only.** WeChat Pay's domestic API offers no general
   authorize-then-capture split, so `on_dispatch` and `manual` capture cannot be
   honoured. The gateway rejects those capture methods explicitly rather than
   accepting a configuration it cannot keep — a store set to dispatch-capture
   that enables WeChat Pay must find out at configuration time, not when the
   first dispatch tries to take money that was already taken.

8. **CNY only, enforced on the gateway.** WeChat Pay's domestic API settles in
   renminbi alone. `available_for_order?` returns false for any other currency,
   which is the hook `6.0-payment-method-rules.md` explicitly preserves for
   per-gateway overrides. No `CurrencyRule` is added to the rule set — that
   vocabulary belongs to that plan, not this one.

9. **Both verification modes are supported: WeChat Pay public key and platform
   certificates.** New merchants are steered to the public key mode, which is a
   single non-rotating key; established merchants are on platform certificates,
   which rotate. Supporting only one would exclude half the merchant base. The
   mode is an explicit preference rather than inferred from which key is filled
   in, so an ambiguous configuration is nameable in an error. Cached certificates
   live in `Rails.cache`, never in a table — the gateway gem ships no schema.

10. **Async refunds land in core as a narrow capability, off by default.** A new
    `Spree::PaymentMethod#async_refunds?` returning false keeps every existing
    gateway on today's synchronous path, so Stripe and the pending Adyen port
    are unaffected. Only a gateway that opts in gets refund rows that can sit in
    a non-final state. See "Async refunds" below for what this actually requires.

11. **No stored instruments, no setup sessions.** WeChat Pay's domestic API
    exposes no reusable token for one-off payments — entrusted deduction (委托代扣)
    is a separate contracting product with its own onboarding. So
    `source_required?` is false, `setup_session_supported?` stays false, and no
    `Spree::PaymentSessions::WechatPay` needs to build a payment source. The
    payer's openid is recorded in `external_data`, which is enough for an
    operator to identify who paid.

12. **No React dashboard work in the first phase.** The dashboard renders a
    gateway's `preference_schema` through the generic preferences form, so the
    plugin's configuration appears in the admin with no frontend work. The one
    scene that does need UI — 付款码 (merchant scans the customer's barcode), which
    has no storefront to live in — is deferred and tracked separately below.

13. **服务商模式 (partner mode) is out of scope, but the seam is kept.** Partner
    mode is a different integration: ordering moves to `/v3/pay/partner/…` and
    the field vocabulary becomes `sp_mchid`/`sub_mchid`/`sp_appid`/`sub_appid`.
    It is the natural shape for a marketplace, so it will be wanted, but a
    Spree store today is one merchant and building both without a consumer would
    double every payload without proving either. What this plan does keep ready
    is the seam: transaction paths and credential resolution are built in one
    place so partner mode becomes a path prefix and a field map, not a rewrite.
    Note the one asymmetry that makes "it's just a path change" wrong — the
    **refund path is identical in both modes** (`/v3/refund/domestic/refunds`),
    and partner mode differs only by requiring `sub_mchid`. Refunds therefore
    cannot follow ordering blindly.

## Design Details

### Gem layout

```text
spree/providers/wechat_pay/
  spree_wechat_pay.gemspec              # spree_core + faraday
  lib/spree_wechat_pay.rb
  lib/spree_wechat_pay/engine.rb        # registers SpreeWechatPay::Gateway
  app/models/spree_wechat_pay/gateway.rb
  app/models/spree_wechat_pay/gateway/payment_sessions.rb
  app/models/spree_wechat_pay/gateway/webhooks.rb
  app/models/spree/payment_sessions/wechat_pay.rb
  app/services/spree_wechat_pay/client.rb
  app/services/spree_wechat_pay/notification.rb
  app/services/spree_wechat_pay/credentials.rb
  app/jobs/spree_wechat_pay/base_job.rb
  config/locales/en.yml, zh-CN.yml
  spec/
```

`lib/spree_wechat_pay/engine.rb` appends the gateway to
`Rails.application.config.spree.payment_methods` in an `after_initialize` block,
matching `spree_stripe`.

### Credentials and preferences

One merchant account, but **not one application identifier**. An official
account, a mini program and a mobile app are three different identities issued
by two different platforms, and WeChat requires the identifier used to launch
payment to equal the one used to place the order. A single `app_id` preference
would therefore be wrong the moment a merchant runs more than one scene — and
the failure it produces is a payment that silently never starts, not an error.

| Preference | Type | Notes |
| --- | --- | --- |
| `merchant_mode` | string | `direct`, and only `direct` is accepted today. See below |
| `merchant_id` | string | 商户号 |
| `merchant_private_key` | password | The merchant certificate's private key, PEM |
| `merchant_certificate_serial` | string | Serial number of the merchant certificate |
| `api_v3_key` | password | Decrypts notifications and certificate downloads |
| `verification_mode` | string | `public_key` or `platform_certificate` |
| `wechat_pay_public_key` | password | Public key mode verification |
| `wechat_pay_public_key_id` | string | Identifies the key in the signature header |
| `jsapi_app_id` | string | Official account. Required when the JSAPI scene is enabled |
| `mini_program_app_id` | string | Required when the mini program scene is enabled |
| `app_app_id` | string | Open platform. Required when the APP scene is enabled |
| `enabled_scenes` | array | Ticked scenes, validated against the known set |
| `statement_descriptor` | string | Optional override for the product description |

Scene-specific identifiers are flat preferences rather than a nested structure,
because the dashboard's preferences form is generated from a flat schema and
nested hashes would have to be edited as one opaque field. What matters is that
the requirement is **conditional and enforced**: enabling a scene without its
identifier is a validation error naming the scene, not a runtime surprise.

`verification_mode` is explicit rather than inferred from which key is filled in.
Both modes are legitimate configurations and inferring would make an ambiguous
state — both filled, or neither — unrepresentable in the error message an
operator needs.

**`merchant_mode` exists now so it does not have to be retrofitted.** Its only
accepted value today is `direct`. Adding it as a preference with a single legal
value costs one line and removes the alternative, which is a `partner_mode?`
predicate appearing in every payload builder later. The validation that rejects
`partner` is the honest statement of the current state, and lifting it is the
whole of the future work.

### Merchant context

Everything that varies between direct mode and partner mode — which merchant the
credentials belong to, which application identifier applies, which identifier the
payer is known by, and which transaction path to call — is resolved once into a
value object rather than re-derived in every payload:

```text
Gateway  →  MerchantContext  →  payload builders  →  path resolution  →  signer
```

`MerchantContext` carries `merchant_id`, the scene's `app_id`, and — for partner
mode, once it exists — the service provider's and sub-merchant's identifiers and
the corresponding payer identifier flavour. It is a plain Ruby class with
`ActiveModel::Model` and typed attributes, not a `Struct`, per the repository's
rule for domain value objects, and it holds no behaviour beyond resolution: the
payload builders and the path resolver receive it, which is what keeps
`if partner?` out of the five scene implementations.

This is the seam Key Decision 13 refers to. "A path prefix and a field map" was
too thin a description of it: partner mode changes the path, the merchant fields,
the application identifier fields, and which openid flavour is valid, so the
abstraction has to be a resolved context rather than two lookup tables.

Holding credentials in `:password`-typed preferences gets masking on read and
the masked-round-trip guard on write. It does **not** get encryption at rest:
`spree_payment_methods.preferences` is serialized YAML. That is the existing,
documented state of payment credentials (`decisions.md`, 2026-08-09) and this
plan does not change it — but it means the merchant private key and the APIv3
key sit in the same column as Stripe's secret key, and database dumps must be
treated accordingly.

A validation mirrors Stripe's `validate_secret_key`: saving credentials runs one
cheap authenticated call and reports the failure against the field, so a typo in
the merchant id or a mismatched key pair is caught at configuration time rather
than at the first checkout. That call proves request signing works — it does not
prove the other half. WeChat offers a verification self-test that sends a signed,
encrypted notification to the merchant's own callback address and expects it to
be verified and decrypted correctly, which exercises the exact path a real
payment notification takes. It is the only end-to-end proof of configuration
available, and it needs a publicly reachable callback, so it is an explicit
action an operator runs rather than something credential-saving triggers.

### Session lifecycle

**Create.** `create_payment_session(order:, amount:, external_data:)` resolves
the scene, obtains the openid when the scene needs one, calls the scene's
transaction endpoint, and writes a `Spree::PaymentSessions::WechatPay` row whose
`external_id` is the generated merchant order number and whose `external_data`
carries the scene, the payload's own expiry, and everything the storefront needs
to launch payment: `prepay_id` and the client-side signature parameters for
JSAPI and mini program, `code_url` for Native, `h5_url` for H5, and the signed
app parameters for APP.

### Time and lifetime: three clocks, not one

An earlier draft of this plan stated the scene payload lifetimes and WeChat's
`time_expire` ceilings without distinguishing them, which reads as a
contradiction. They are not in conflict — they are different clocks, and the
design depends on keeping them apart.

| Clock | What it governs | Value |
| --- | --- | --- |
| **Transaction payability** (`time_expire`) | How long the customer can still pay this transaction | 15 days for JSAPI, mini program, H5 and APP; 7 days for Native. Omitted means 7 days |
| **Launch token** (`prepay_id`, `code_url`, `h5_url`) | How long what the storefront was handed still works | 2 h for `prepay_id` and `code_url`; **5 min** for `h5_url` |
| **Spree's session expiry** (`expires_at`) | The gateway's own view of when a session is dead | Set by the gateway, cannot outlive the first clock |

WeChat defines the first clock explicitly as the deadline for completing payment,
not the point at which the transaction closes: `支付结束时间是指用户能够完成该笔订单
支付的最后时限，并非订单关闭的时间`. It is the only one of the three that bounds
payability, and it is why the 15-day and 7-day ceilings are in this plan rather
than being deleted.

**`expires_at` follows the transaction, not the token.** Setting it to the
payload's lifetime would be the easy reading of "a session must not outlive what
it hands out", and it would be wrong: an H5 session would die five minutes after
it was created, while the transaction behind it stayed payable for fifteen days.
What must not outlive the payload is the payload — so the payload carries its own
expiry in `external_data`, and the session's `expires_at` is the transaction's
deadline.

**A lapsed token is renewed, not fatal.** This needs a named operation, because
without one the storefront will do the obvious and wrong thing, which is to
reload a dead link:

- **Renew** is not a new endpoint. Core exposes exactly three session verbs —
  create, update, complete — and adding a fourth would be a core API change this
  plan does not need. Renewal is therefore the **update** verb asked for the same
  amount: the storefront re-submits the session, and the gateway re-issues the
  transaction when its launch token has lapsed and does nothing when it has not.
  The storefront needs one code path for "the customer came back and the link no
  longer works", and no new route exists to get it wrong.
- Re-issuing under the same merchant order number is preferred when the amount is
  unchanged. When the amount has moved, or the transaction can no longer be
  reused, the gateway closes it and creates a fresh transaction under a new
  number — the same operation the amount-change path already performs. Either
  way, the response has the shape of creation, so the storefront just renders
  what it is given.
- The renewal is idempotent from the storefront's point of view: asking twice for
  a renewal of an unchanged session produces one live transaction, not two.

WeChat documents that re-issuing under an unchanged merchant order number is
permitted when every parameter is identical, which is what makes re-issue the
preferred path. It does **not** state explicitly that the returned `prepay_id` is
refreshed, so the plan does not assume it: the fallback is the close-and-replace
path, which is documented and already needed for the amount-change case. This is
tracked as an open question below, and the first phase that exercises a lapsed
token must settle it.

The H5 URL is passed through untouched and extended only with the URL-encoded
return address, because WeChat forbids altering it in any other way and rejects a
modified one.

**Update.** WeChat Pay cannot change the amount of an open transaction. When the
cart total moves, the open transaction is closed and a new one is created under
a fresh merchant order number, and the session's `external_id` moves with it.
The session row is the same row — it is the same intent. The storefront never
sees the change, because `update_payment_session` returns the new session data.
The close call is also the guard against a race: if the customer paid the old
transaction in the moment before the update, WeChat refuses to close it and the
update settles the session on the payment that actually happened instead of
abandoning it.

**Complete.** `complete_payment_session` queries the transaction by merchant
order number and settles on what WeChat reports, never on what the storefront
claims. Failure is not "anything that is not success" — see the payment state
matrix below for what each reported state actually means.

#### The payment state matrix

WeChat reports a `trade_state` on every query and notification. Treating
everything that is not `SUCCESS` as a failure is the obvious implementation and
it is wrong: WeChat explicitly warns against it, because an unpaid transaction
can still be paid.

| WeChat `trade_state` | Still payable? | Action | Session outcome |
| --- | --- | --- | --- |
| `SUCCESS` | no | settle the payment as captured | `completed` |
| `NOTPAY` | **yes** | close the transaction first | `failed` **only after the close succeeds** |
| `USERPAYING` | **yes** | wait and re-query | unchanged — do not settle, do not fail |
| `CLOSED` | no | nothing to close | `canceled` |
| `REVOKED` | no | micropay only; not produced by these scenes | `canceled` |
| `PAYERROR` | no | micropay only; not produced by these scenes | `failed` |
| `REFUND` | no | a refund exists against a paid transaction | settled, refund is its own record |

The `NOTPAY` row is the one that matters. WeChat's own instruction is to close
before declaring failure: `不建议直接判定为失败。NOTPAY状态表示订单尚未支付，仍存在
后续支付成功的可能性。如需将该订单标记为失败，建议先调用关单接口，待接口返回关单成功后，
再将订单状态置为失败`. So the path is:

```text
NOTPAY  →  close  →  close succeeded?  ── yes ──→  failed
                                     └── no (already paid) ──→  settle as captured
```

That "close failed because it was already paid" branch is not an error path — it
is the race resolving in the customer's favour, and it settles rather than
failing. It is the same guard the update path relies on.

**Settlement.** `Spree::PaymentSessions::WechatPay#prepare_for_settlement!`
warms everything settlement reads, so the webhook path's locked settlement
performs no network I/O — the same discipline `Spree::PaymentSessions::Stripe`
follows. Because WeChat issues no reusable instrument, the session leaves
`payment_source_for_settlement` returning nil and the payment stands on its own.

### Merchant order numbers

WeChat requires the merchant order number to be 6–32 characters from
`0-9a-zA-Z_-|*`, unique within the merchant account. Spree order numbers are
short and repeat across a cart's several payment attempts, so the gateway
generates its own: the order number, a separator, and a bounded random suffix —
kept inside 32 characters and inside the allowed alphabet, regardless of how the
store configures its order number prefix. One place builds them, and it is
tested against the length and character rules directly.

Refund numbers have their own rules and are built separately: up to 64 **bytes**
rather than characters, and `@` is allowed where it is not in an order number.
Two further rules are encoded rather than left to wherever refunds are called
from — a withdrawn refund that is retried must reuse its original number, while a
refund that WeChat closed needs a new one, and WeChat allows at most 50 partial
refunds against a single transaction.

A merchant order number cannot be recycled once it has been paid, closed or
reversed, which is why the update path generates a new one rather than reopening
the old transaction.

### Notifications

WeChat Pay has no equivalent of Stripe's webhook endpoint registration and no
per-endpoint signing secret. Every transaction carries the `notify_url` it wants
notified at, and the core URL already fits: it is HTTPS, has no query string,
and is stable per payment method.

Verification works differently in the two modes. The notification body is
encrypted regardless; the signature over it is what proves origin. In public key
mode the signature is verified against the configured public key, identifying
itself by the key id header. In platform certificate mode the signature is
verified against the platform certificate named by the serial header, which
means the certificate must be cached — a synchronous cache miss on the webhook
path is a network call inside the request core deliberately keeps short, so the
cache is warmed by a refresh job and read from `Rails.cache` on the hot path,
with the certificate download as a fallback rather than the norm.

`parse_webhook_event` verifies and decrypts, then maps the event to core's
normalized action and finds the session by merchant order number. An event for a
transaction this store does not own returns nil, which core acknowledges without
acting — the behaviour a shared callback URL depends on. A failed verification
raises `Spree::PaymentMethod::WebhookSignatureError`, which core turns into a
401.

### Webhook identity and idempotency

WeChat retries a notification fifteen times over roughly 24 hours and states
plainly that duplicates are expected. "Core's handler is re-entrant" is not a
specification, so the identities are named here and the guarantees are split
between what core already provides and what the gateway must add.

| Thing | Identity | Where it lives |
| --- | --- | --- |
| Payment event | `transaction_id` | WeChat's own payment identity |
| Payment correlation | `out_trade_no` | the session's `external_id` |
| Refund event | `refund_id` | the refund's `transaction_id` |
| Refund correlation | `out_refund_no` | the refund's metadata |
| Notification delivery | `id` (envelope) | not used for deduplication — see below |

**Already guaranteed by core, relied on but not reimplemented:**

- A payment is keyed on `(owner, payment_method, response_code)` with a unique
  index and a `RecordNotUnique` rescue, so a webhook racing the storefront's own
  confirmation converges on one payment row rather than two.
- Settlement runs inside the owner's row lock with a completed-state recheck, so
  a replayed capture cannot record a second capture event or double
  `captured_amount`.
- The order is completed only when it is not already complete.

**Added by this gateway, because core has no seam for it yet:**

- The refund action is a state *transition*, not a settlement, so it is
  idempotent by construction: the notification's target status is compared with
  the refund's current status and the transition is applied only when it moves
  the row. A replay of the same `REFUND.SUCCESS` is a no-op that still answers
  200.
- A refund notification for a refund this installation does not have follows the
  lookup chain above instead of being dropped. Finding nothing is a reportable
  event, not a crash and not a silent success.

**Deliberately not used: the envelope's `id`.** WeChat's `id` is per *delivery*,
not per event, and the retry schedule can present the same state change under a
new one. Deduplicating on it would therefore fail to deduplicate anything. The
identity that matters is the state the event describes and the row it describes
it about.

The sequence every notification follows, in order:

```text
verify signature  →  decrypt  →  resolve the business object by identity
   →  compare its current state with the event's  →  apply only a legal move
   →  answer 200
```

A verification failure short-circuits to 4xx/5xx so WeChat retries. Everything
after verification is idempotent, so a body that was already applied still
answers 200 — which is the behaviour that stops the retry storm, not an
optimisation.

### Async refunds (the core change)

`spree_refunds` has no status column. A refund's only state is whether
`transaction_id` is set, `credit_allowed` is
`amount - (offsets_total.abs + refunds.sum(:amount))`, and `Refunds::Create`
destroys the row when the gateway call fails.

WeChat's refund API accepts the request and settles later. Returning "processing"
as success is correct as far as it goes — the money is claimed and the balance
is right — but when WeChat later reports the refund abnormal, core has nowhere
to record it. The row is the only record, and deleting it erases the audit
trail along with the reversal.

The capability is therefore:

- `Spree::PaymentMethod#async_refunds?`, false in core, true on the WeChat
  gateway.
- A status on `spree_refunds` — `processing`, `completed`, `canceled` — with
  `has_status`, matching how every other status in 6.0 works. **No state
  machine**: 6.0 has none anywhere, and `has_status` plus explicit transitions
  is the house pattern.
- `credit_allowed` excludes refunds that are no longer live. Without this one
  line the capability is worse than useless: a refund canceled or refused would
  permanently reduce the balance the merchant can return.
- `Refunds::Create` puts the row in `processing` rather than `completed` when the
  gateway opts in and its response is not final, and the failure path stops
  destroying rows for such gateways — a failed async refund is a record to keep,
  not a row to erase.
- The normalized webhook result gains a refund action, carrying the refund the
  event concerns rather than a payment session, and `Spree::Payments::HandleWebhook`
  gains the branch that settles it.
- The admin refund serializer exposes the status; the storefront one does not.

This is the smallest shape that can represent the truth. It is deliberately
gated: with the flag false nothing about the existing path changes, so the
change cannot regress Stripe, and the pending Adyen port can adopt it later
without a second design pass.

#### Why there is no `failed` refund status

WeChat reports four refund statuses and only two are terminal: `SUCCESS` and
`CLOSED`. `PROCESSING` is non-final, and `ABNORMAL` — the money could not reach
the customer's bank because the card was cancelled or frozen — is **also
non-final**; a merchant who tops up and acts can still see it reach `SUCCESS`.

That asymmetry is why the canonical set is `processing` / `completed` /
`canceled` and not `processing` / `completed` / `failed`. Adding `failed` would
tempt a mapping of `ABNORMAL` onto it, and that mapping is actively dangerous in
two ways:

- It states something false about the money. An abnormal refund is not finished,
  and a merchant reading "failed" would reasonably conclude the customer was
  never paid back.
- It corrupts the balance. `failed` refunds are excluded from `credit_allowed`,
  so marking a still-live refund failed would release that amount back as
  creditable while WeChat could still complete the refund — the merchant could
  refund the same money twice.

So `ABNORMAL` stays `processing`, and the distinction is carried where provider
detail belongs: **the refund's own `metadata`**, which the model already has and
the admin serializer already exposes. The gateway writes the provider's words
verbatim rather than translating them:

```json
{
  "wechat_pay_refund_id": "…",
  "wechat_pay_refund_status": "ABNORMAL",
  "wechat_pay_refund_status_detail": "…",
  "wechat_pay_out_refund_no": "…",
  "wechat_pay_last_event_at": "…"
}
```

An operator then sees a refund that is still processing *and* that WeChat
reported as abnormal, which is the truth. The rule this encodes is general
enough to be a constraint on other gateways: **a non-terminal provider state
must never be mapped onto a terminal canonical one, however alarming the
provider's wording is.**

#### The refund status matrix

| WeChat `refund_status` | Terminal? | Spree status | What it means for the operator |
| --- | --- | --- | --- |
| `PROCESSING` | no | `processing` | Accepted, on its way |
| `ABNORMAL` | **no** | `processing` | Money could not reach the customer; act on the merchant platform or refund abnormally |
| `SUCCESS` | yes | `completed` | The customer has been paid back |
| `CLOSED` | yes | `canceled` | Refund abandoned after 7 days of insufficient balance; a new refund number is required to try again |

`SUCCESS` and `CLOSED` are the only two that move a refund out of `processing`,
which is exactly the set WeChat documents as terminal.

There is no third failure path to design: core's synchronous gateways destroy an
uncredited refund row on failure, and an async gateway never gets that signal
synchronously — the row is created, accepted, and then resolved by notification
or reconciliation.

#### Finding the refund a notification is about

This is the part the payment path gets for free and the refund path does not, so
it is specified rather than left to implementation.

A payment notification names `out_trade_no`, which is the session's
`external_id` — one lookup. A refund notification names `out_refund_no` and
`refund_id`, and neither is the session's identifier:

```text
Payment notification          Refund notification
   out_trade_no                  refund_id  +  out_refund_no
        ↓                                    ↓
  PaymentSession                        Spree::Refund
```

The chain, in the order it is attempted:

1. **`refund_id` → `Spree::Refund#transaction_id`.** Core stores whatever
   authorization `credit` returned as the refund's `transaction_id`, and the
   gateway returns WeChat's `refund_id` there. This is the primary lookup and it
   uses a column core already persists — no new field, no new table.
2. **`out_refund_no` → the refund's metadata.** The number is generated by the
   gateway and written to the refund's metadata when the refund is created, so
   it is a reliable second key when the first misses — which it will, for a
   refund whose acceptance response was lost to a timeout before core could
   record it.
3. **`out_trade_no` → the session → its payments → the refund.** The last
   resort, and the only way to recover a refund WeChat accepted but this
   installation never recorded. Matching is on amount as well as the transaction,
   and a match is treated as evidence to investigate rather than as a settlement.

The refund number is therefore not merely a WeChat requirement — it is the
gateway's own correlation key, which is why it is generated in one place and
written down before the API call rather than after it.

#### Reconciliation

WeChat's own guidance is not to rely on notifications alone, and the retry
schedule eventually gives up: fifteen attempts over roughly 24 hours, after which
a lost notification is lost. A scheduled job therefore sweeps refunds left in
`processing` past a threshold, queries each by refund number, and applies
whatever the query reports. The same job covers the timeout case — a refund whose
acceptance response never arrived — by querying before anything is retried.

Without this, a refund stays `processing` forever and the balance it holds is
never released, which is a silent merchant-facing defect rather than a
theoretical one.

### The five scenes

Verified against the official v3 documentation (2026-09-10). All five are `POST`
to `https://api.mch.weixin.qq.com` and share the required set `appid`, `mchid`,
`description`, `out_trade_no`, `notify_url`, `amount.total`.

This table is the **source of truth for implementation**: a scene's endpoint,
identifier, identity requirement, payload lifetime and launch contract are read
from here, and code that disagrees with it is wrong.

| Scene | Endpoint | Application identifier | Payer identity | Response payload | Token TTL | Payability cap | Launch contract |
| --- | --- | --- | --- | --- | --- | --- | --- |
| JSAPI | `/v3/pay/transactions/jsapi` | `jsapi_app_id` | openid | `prepay_id` | 2 h | 15 d | Sign, invoke the browser payment bridge |
| Mini program | `/v3/pay/transactions/jsapi` — **same path and schema** | `mini_program_app_id` | openid | `prepay_id` | 2 h | 15 d | Sign, then the mini program's own payment call, which carries **no** `appId` field |
| Native | `/v3/pay/transactions/native` | `bound_app_id` | none | `code_url` | 2 h | 7 d | Render as a QR code, poll the session |
| H5 | `/v3/pay/transactions/h5` | `bound_app_id` | none | `h5_url` | **5 min** | 15 d | Redirect the page |
| APP | `/v3/pay/transactions/app` | `app_app_id` | none | `prepay_id` | 2 h | 15 d | Hand signed parameters to the app's SDK; the signed line is the **bare** `prepay_id` |

**Corrected 2026-09-10 (Phase 2).** WeChat requires `appid` on *every* order,
including Native and H5 — what those scenes lack is a *payer* identity, not an
application identifier. The documentation is explicit that any of the three
kinds may be supplied as long as it is bound to the merchant number, so they use
a separate `bound_app_id` rather than one scene's identifier. This was wrong in
the first version of this table and the correction came from reading the Native
order page while implementing it.

Three consequences the design takes from this table:

- **JSAPI and the mini program are one integration, not two.** Same endpoint,
  byte-identical request schema; only the launch step and which application
  identifier is configured differ.
- **The token lifetime and the payability cap are different clocks**, and neither
  may be used for the other — see "Time and lifetime" above. This is the single
  most error-prone part of the table, because the token is what the storefront
  holds and the cap is what actually governs whether the customer can still pay.
- **H5 carries a mandatory scene object where the others carry an optional one.**
  `scene_info.h5_info.type` (`Wap`/`iOS`/`Android`) is required for H5, and
  `scene_info.payer_client_ip` is required whenever `scene_info` is sent at all —
  but for the browser and app scenes the object itself is optional. Building the
  payload per scene rather than once is therefore required, not merely tidy.

### Signing, verification and decryption

These are the parts with no library behind them, so the plan states the rules
that are easy to get wrong. Each was verified against the official pages listed
under References.

**Request signing.** Five lines, each terminated by a newline *including the
last*: method, absolute path, timestamp, nonce, and the request body byte-for-byte
as sent. RSA-SHA256 with the merchant certificate's private key, Base64-encoded,
carried in an `Authorization: WECHATPAY2-SHA256-RSA2048 …` header whose
`serial_no` is the **merchant** certificate's serial. The path is signed, which
is why partner mode (below) is a path change and not just a field change.

**Launch signing is not one signature but three different ones.** All are
RSA-SHA256 over a newline-terminated string, but the fourth line differs, and
getting it wrong produces a payment that silently never starts:

- JSAPI: `appId`, timestamp, nonce, then `prepay_id=<value>`.
- Mini program: the same string with the mini program's app identifier — but the
  launch call itself carries **no** `appId` field; it is implicit.
- APP: the fourth line is the **bare** `prepay_id` with no `prepay_id=` prefix.

The signature is produced by the merchant, server-side, and must use the same
certificate the order was placed with.

**Response and notification verification.** Three lines — timestamp, nonce, raw
body — verified with the WeChat Pay public key or the platform certificate's
public key. The body must be the untouched bytes, which the repository's core
webhook controller already provides via `request.raw_post`.

**Decryption.** The notification body is JSON with a `resource` envelope; the
payload inside is `AEAD_AES_256_GCM`, keyed on the APIv3 key, with
`resource.nonce` and `resource.associated_data` — the latter may legitimately be
empty. The notification cannot be sent at all unless the merchant has set an
APIv3 key, which makes it a required credential rather than an optional one.

**Acknowledgement.** HTTP 200 or 204 with **no body**, within five seconds —
which is exactly what core's webhook controller returns (`head :ok`), and why its
"verify synchronously, process asynchronously" shape fits. Failures answer 4xx or
5xx and WeChat retries 15 times over roughly 24 hours. Core's `HandleWebhook` is
already re-entrant for repeat deliveries.

**WeChat deliberately probes the verification.** A small number of callbacks
carry a signature beginning with `WECHATPAY/SIGNTEST/` that is invalid by
construction. The documentation says to treat it as an ordinary verification
failure — which means the gateway must **not** special-case it, and must answer
4xx/5xx rather than acknowledging it.

**One callback shape must be rejected explicitly.** If a refund were ever raised
against this merchant account through the older API generation, or if no
`notify_url` were supplied, WeChat sends an XML callback instead of the v3 JSON
one. This gateway always supplies `notify_url` on the v3 refund call, so it should
never see one — but a body that is not JSON must fail verification loudly rather
than crash inside a decryption routine.

### Certificate and key resolution

One abstraction resolves a `Wechatpay-Serial` header value to a verification key,
because the two modes are distinguished by that value alone: a serial shaped
`PUB_KEY_ID_<digits>` is the WeChat Pay public key, and **anything else means
platform certificates**. The official documentation recommends the public key for
new integrations and describes platform certificates as the legacy path, but both
are supported here because established merchants are already on certificates and
would otherwise be excluded.

Platform certificates are fetched from `GET /v3/certificates` (the same
authenticated call the credential validation makes), are valid for five years,
and rotate with a 24-hour overlap during which both the old and the new
certificate are returned. That overlap dictates the shape of the cache: it is a
**set keyed by serial, merged rather than replaced**. A refresh that swapped in
what it just downloaded would drop the certificate still being used to sign
in-flight notifications, and verification would fail for the length of the
overlap — a window measured in hours, not requests.

So a refresh reads the current set, adds what it downloaded, and drops only
entries whose own `expire_time` has passed. The write is a single cache write of
the whole set, so a reader never observes a half-updated collection. Refresh is
scheduled well inside the documented 12-hour ceiling, and the lookup on the
webhook path reads the cache only, never the network.

### Errors, timeouts and retries

WeChat returns structured error bodies with a code, a message, and a field path
pointing at the offending parameter. Those are surfaced in the gateway's own
words rather than swallowed into a generic failure, per the repository's
third-party API rules — a merchant who misconfigured the app identifier should
see which field is wrong.

**An unknown outcome is queried, never retried blind.** This is the rule that
matters most, and it is where a naive retry policy does real damage. A timeout or
a connection reset means the request may or may not have been accepted, and
re-issuing it is only safe if the operation is genuinely idempotent *and* the
parameters are unchanged. So the client distinguishes two kinds of failure:

| Outcome | Response |
| --- | --- |
| A definite error — 4xx with a structured body | Surface it. Do not retry |
| A network-level failure, no response | **Query first**, then decide |
| 5xx from WeChat | Retry with backoff, same number, same payload |

Query-first means: after a failed transaction creation, look the transaction up
by merchant order number; if it exists, use it rather than creating a second one.
After a failed refund request, look the refund up by refund number; if it is
already accepted, treat it as accepted. Only when the lookup finds nothing is the
request re-issued — and then with the original number and the original payload,
because WeChat permits re-issuing under an unchanged number and refuses one whose
parameters moved.

The concrete rules this encodes:

- **Re-issuing the same order is safe only with identical parameters.** An unpaid,
  unclosed transaction may be re-created under the same merchant order number,
  but any changed parameter — or a different endpoint — answers
  `OUT_TRADE_NO_USED`. So a retry of a failed *creation* reuses both the number
  and the exact payload, while the update path deliberately generates a new
  number instead.
- **A refund retry must reuse the same merchant refund number.** WeChat states
  this as a safety rule, not an optimisation: a new number for a retry risks
  refunding twice.
- **`NOTPAY` is not a failure.** See the payment state matrix — a transaction is
  only failed after it has been closed and the close succeeded.
- **Closing is the guard, and it is idempotent.** Both the update path and the
  failure path use the same close operation, and both tolerate being called twice.

### Observability

A payment gateway fails in ways nobody sees: a webhook that stopped arriving, a
certificate that rotated, a refund stuck in `processing`. Three signals are
emitted rather than left to log archaeology.

- **Structured failures through `Rails.error.report`**, carrying the WeChat error
  code, the merchant order or refund number, and the payment method — the same
  seam core uses on its own webhook path, so it lands wherever the host app
  already sends errors. No credentials, no key material, and no raw payloads in
  the reported context.
- **Instrumentation on the calls that matter** — transaction creation,
  notification verification, settlement, refund creation, certificate refresh —
  through the repository's existing instrumentation conventions, so the
  `spree_opentelemetry` gem can pick them up without this gem depending on it.
- **The two counters an operator actually acts on**: notifications that failed
  verification, and refunds left in `processing` past the reconciliation
  threshold. Both are reported by the jobs that already look at them, which keeps
  the instrumentation honest — nothing is counted that nothing checks.

### Testing

The suite is VCR-backed and offline, like the Stripe gem's: cassettes default to
`record: :none`, recording is opt-in, and recorded data is filtered so no
merchant identifier, key material, or openid is committed. No merchant account is
available for this work, so cassettes are **hand-authored to the documented
response shapes** and the docs each cassette encodes are cited in the spec that
consumes it. Signature verification is additionally covered by unit tests with a
locally generated key pair, which needs no provider and is the test that actually
proves the verification logic. A real merchant account, when one is available,
becomes a verification pass rather than the source of the fixtures.

## Migration Path

Phases, in order. Phase 0 exists because this plan's own history shows why it is
needed: the contradiction between the token lifetimes and the payability caps was
introduced by adding accurate facts to a document whose contract was not yet
frozen. Freezing the contract first is cheaper than discovering the next one
during implementation.

0. **Contract freeze.** No code. The API contract matrix, the payment state
   matrix, the refund state matrix, the webhook identity table and the credential
   schema are reviewed and agreed as the implementation's source of truth.
   Anything that changes afterwards is a change to this plan first. The one
   genuinely unresolved item — whether a lapsed `prepay_id` can be refreshed
   under the same merchant order number — is settled here if it can be, and
   explicitly carried as a known unknown if it cannot.
1. **Core capability and gem skeleton.** `async_refunds?` and the refund status
   change in core, with Stripe's behaviour unchanged and covered by spec. The gem
   skeleton: gemspec, engine, registration, the merchant context, the Faraday
   client, request signing, verification, decryption, and credential validation.
   Wire the gem into `server/Gemfile` in both branches so the monorepo dev
   environment loads it.
2. **Native scene end to end.** No openid, no authorization, so it exercises
   transaction creation, notification verification and decryption, settlement,
   session completion, the payment state matrix, idempotency, and order
   completion without the OAuth variable. This is where signing, certificate
   handling, merchant order numbers and the query-before-retry rule are proven.
3. **JSAPI.** The authorization-code exchange, the openid, and the launch
   signature — the scene a real Chinese merchant needs first.
4. **Mini program.** The same transaction pipeline and the same endpoint; only
   the application identifier and the launch contract differ. Deliberately after
   JSAPI, because the two share everything but the launch step and building them
   together would hide which part is which.
5. **H5.** The five-minute token lifetime and the renewal path, which is the one
   scene that exercises renewal as a first-class operation rather than an edge
   case.
6. **APP.** The third launch-signature variant, including the bare `prepay_id`
   that differs from the other two.
7. **Refunds.** The refund path against merchant order numbers, the refund
   notification and its lookup chain, the async status transitions, and the
   reconciliation job — built on the phase-1 core change.
8. **Documentation.** A merchant-facing page at
   `docs/integrations/payments/wechat-pay.mdx` alongside the existing Stripe,
   Adyen, PayPal and Razorpay pages, covering credential setup in both
   verification modes, which merchant-side capabilities each scene needs
   switched on, and — for JSAPI and mini program — the authorization redirect
   the storefront must perform. The storefront instructions are the part most
   likely to be got wrong, so they are written for each scene rather than once.
9. **服务商模式 (partner mode).** Out of scope for this plan. The seam exists from
   phase 1 so this becomes lifting the `merchant_mode` validation, extending
   `MerchantContext`, and mapping the merchant and identifier fields — not a
   rewrite. Note the asymmetry recorded in Key Decision 13: ordering moves to a
   partner path while refunds keep the ordinary one.
10. **付款码 (merchant-scanned barcode) — separate plan.** This product is on
    WeChat Pay's older API generation, not the v3 interface the other five use,
    with its own authentication, message format, and notification handling. It
    also needs Admin API and dashboard work to take a payment on an order from the
    back office, which is why it does not belong in this plan.

## Constraints on Current Work

- **Do not rename the gateway class or its namespace once shipped.**
  `spree_payment_methods.type` and `spree_payment_sessions.type` store STI class
  names (`6.0-payment-gateways-monorepo.md`, Key Decision 2).
- **Payment gateway credentials stay on `PaymentMethod` rows.** Do not add an
  `Spree::Integration` subclass for a gateway, and do not read gateway
  credentials through an integration lookup (`decisions.md`, 2026-07-30).
- **A gateway that cannot honour a capture method must reject it, not ignore
  it.** Any future gateway joining this one inherits the same rule: a
  configuration the gateway cannot keep is an error at configuration time.
- **A gateway's own limits are the gateway's to enforce.** WeChat refuses a refund
  more than a year after payment, while Spree's `credit_allowed` would happily
  offer one — an operator must see the refusal as WeChat's reason, not a generic
  gateway failure. The same applies to the 50-partial-refund ceiling and to any
  scene the merchant has not had switched on.
- **A non-terminal provider state must never be mapped onto a terminal canonical
  one.** WeChat's `ABNORMAL` refund is alarming and unfinished; mapping it to a
  `failed` status would both misstate the money and release balance that is still
  committed. The canonical status stays `processing` and the provider's own words
  go in `metadata`. Any gateway joining the async-refund path inherits this rule.
- **No state machines.** 6.0 removed them everywhere; statuses are declared with
  `has_status` and moved by explicit guarded transitions. A provider state
  machine in this gem would be a second, competing one.
- **Domain value objects use `ActiveModel::Model`, never `Struct`.** Applies to
  `MerchantContext` and to anything else that needs to behave like a record.
- **The async refund capability must stay opt-in.** Anything added to the refund
  path must behave identically for a gateway with `async_refunds?` false. The
  test for that is Stripe's existing refund specs, unchanged.
- **The gateway gem must not decorate core models.** A capability it needs from
  core is added to core, not patched in from the gem
  (`6.0-payment-gateways-monorepo.md`).
- **Gateway configuration lives in preferences, never in a table.** The gem
  ships no migrations. Cached certificates and tokens live in `Rails.cache`.
- **`time_expire` and any other timestamp sent to WeChat is derived from the
  store's time zone**, per the repository's time-zone rule, and rendered in the
  format WeChat requires.

## Open Questions

- **Can a lapsed launch token be refreshed under the same merchant order
  number?** **Answered for Native, 2026-09-10:** the order page says the returned
  `code_url` is valid for two hours and that "失效后需要重新请求该接口以获取新的
  code_url" — after it lapses, re-request this interface for a new one. Combined
  with the FAQ's rule that re-issuing under an unchanged number is permitted when
  every parameter is identical, renewal for Native is a re-issue. The
  implementation does exactly that and is covered by a spec. Still open for
  `prepay_id`: the JSAPI and APP pages do not repeat the sentence, so whether the
  same re-issue refreshes a `prepay_id` is unconfirmed. The fallback — close and
  replace — is implemented and already required for the amount-change case, so
  the JSAPI phases do not depend on the answer. Unblocked by: a merchant
  account.
- **Which scene gets the storefront work first?** Phase 2 proves the plumbing
  with Native, which no consumer-facing flow uses today. Whether the Next.js
  storefront should be extended for Native first (cheapest, proves the loop) or
  the JSAPI authorization flow should be built first (what a real Chinese
  merchant needs on day one) is a scheduling question for the storefront
  repository, not a design question here. Unblocked by: the storefront team's
  availability.
- **Should the storefront be able to discover which scenes are enabled?** The
  store payment-method serializer exposes only name, description, type,
  `session_required`, and `source_required`, so today the storefront must guess
  the scene from its own context and is told no by a structured error if it
  guessed wrong. `Spree::PaymentMethod#public_preferences` exists but is not
  serialized anywhere. Exposing it would be a core API change benefiting every
  gateway, so it does not belong in this plan. Unblocked by: a second gateway
  needing the same thing.
- **Does the 付款码 product belong on the old API generation permanently?**
  Confirmed as of 2026-09-10: the v3 documentation centre lists it as
  付款码支付（V2）and its only instruction is to follow the V2 guide — `POST
  /pay/micropay`, an XML body signed with a symmetric APIv2 key, no
  `notify_url` at all and therefore no payment callback. If WeChat publishes a v3
  equivalent, phase 10 collapses into a small addition to this gem; until then it
  is a second client, a second credential, and a second signing scheme. Unblocked
  by: WeChat's roadmap, or a merchant who actually needs back-office barcode
  payment.
- **Is a Ruby client library worth writing and publishing separately?** There is
  no official Ruby SDK (WeChat Pay publishes Java, PHP and Go) and no maintained
  community gem — the newest v3 gem is roughly two years old with a repository
  that now 404s, and the most popular is V2-only and unreleased since 2020. This
  plan builds the client inside the gem, which is the smaller commitment. Whether
  it should instead be extracted so other Ruby projects can use it is a
  distribution question with no consumer yet. Unblocked by: a second Ruby
  consumer, or a maintainer offering to take it. See "Prior art" under
  References for what the existing Rails-side stack consists of.
- **Should merchant certificates be uploadable, or pasted?** The gateway needs
  the private key as PEM text. A text area in the generic preferences form works
  and ships today; a file upload needs a dashboard plugin and a place to put the
  material, which reintroduces exactly the storage question this plan avoids.
  Unblocked by: merchant feedback that pasting a PEM block is unacceptable.

### Prior art (2026-09-10)

The Rails-side WeChat ecosystem was surveyed before deciding to implement the
client in this gem. The canonical reference is
[Eric-Guo/wechat-starter](https://github.com/Eric-Guo/wechat-starter) — a Rails
7.1 template application (351 stars, MIT) that wires up an official account, a
UI kit, OAuth and payments. Its locked dependencies are the ecosystem's whole
Rails stack:

| Gem | Version | What it does | Why it is not usable here |
| --- | --- | --- | --- |
| `wx_pay` | 0.21.0 | WeChat Pay | V2 only — XML body, APIv2 key, MD5/HMAC signing. Last released 2020-07-23; repository last pushed 2024-04-16 |
| `wechat` | 0.17.5 | Official account: messaging, JS-SDK | Requires `activesupport >= 6.0, < 8`. Spree 6.0 runs Rails 8.1, so **it cannot be installed at all** |
| `omniauth-wechat-oauth2` | 0.2.3 | OAuth2 for the official account | The locked stack resolves `omniauth 1.x`, which requires `rack < 3`; Rails 8.1 is Rack 3. The gem itself permits a newer omniauth, so this is a resolution problem rather than a hard block |
| `weui-rails` | 1.1.3 | UI kit | Irrelevant — a headless gateway has no views |

Two things follow, and they are the reason this section is here rather than in a
footnote.

**The two gems this plan would actually want are unusable, for different
reasons.** The `wechat` gem's upper bound of `activesupport < 8` excludes the
framework version this plan targets by a whole major release — a hard block at
`bundle install`, not a maintenance concern. The OAuth gem is the softer case:
its pinned chain does not resolve on Rack 3, though a newer `omniauth` could fix
that. And the one gem that does payments, `wx_pay`, is V2 — which is the part
that matters here, because nothing in this stack ships a v3 client at all.

**What is worth learning from it, and what is not.** The template shows the
shape of a WeChat-for-Rails application end to end, and its OAuth handling is a
reasonable reference for what the code-to-openid exchange looks like. What must
**not** be copied is the credential handling: it configures the merchant id, API
key and AppSecret through `figaro` environment variables
(`wechat_pay_mch_id`, `wechat_pay_api_key`, `wechat_pay_notify_url`). This plan
deliberately puts credentials in payment-method preferences instead, per the
cardinality decision in `decisions.md` (2026-07-30) and the integrations plan's
rule against env-var credential contracts for per-store providers — a single
merchant account configured by environment would be wrong the moment a store
runs two, and it would be invisible to the admin.

Its payment transport is `rest-client`, which is also not what this plan uses:
the repository's third-party API rule prefers an official SDK and otherwise
Faraday or `Net::HTTP`, and `rest-client` is neither maintained nor the house
choice.
