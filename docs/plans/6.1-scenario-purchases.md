## Summary

Twelve of the mini program's payment endpoints are the same operation six times over, each in two payment channels. `vip/payByWxMp`, `vip/payByChinaumsWxPay`, `rights/payCouponByWxMp`, `rights/payByChinaumsWxPay`, `gift-card/payByWxMp`, `gift-card/payByChinaumsWxPay`, `integral-mall/payByWxMp`, `integral-mall/payByChinaumsWxPay`, `coupon_combo/payCouponComboByWxMp`, `coupon_combo/payCouponComboByChinaumsWxPay`, `teamBuy/payTeamBuyByWxMp`, `teamBuy/payTeamBuyByChinaumsWxPay` — in every case the shopper is buying something that is not a shippable product, paying for it once, and receiving an entitlement when the payment settles. Spree has the payment half (`Spree::PaymentSession` and a gateway contract that already handles five WeChat scenes) and none of the first half. This plan adds the first half once instead of six times.

## Key Decisions (do not deviate without discussion)

- **One table with a `kind`, not six tables.** `spree_scenario_orders` carries `kind` (`vip`/`rights`/`gift_card`/`integral_mall`/`coupon_combo`/`team_buy`), the buyer, the amount and currency, the payment session it is settling through, and a `payload` for the kind-specific details. Six tables would each need their own payment wiring, status handling and admin surface for no gain.
- **The payment channel is a column, not a route.** `payment_channel` (`chinaums`/`wechat`) keeps "each scenario in two channels" out of the URL structure. Twelve endpoints become one create, one per-channel selection and the ordinary payment-session flow.
- **It settles through the core payment-session flow; it does not have its own.** `Spree::PaymentSession` already models a session with a status and a settle step, and `Spree::PaymentMethod` already exposes the capability opt-ins a gateway declares — `source_required?`, `session_required?`, `setup_session_supported?`, `async_refunds?`, `available_for_order?` (`spree/core/app/models/spree/payment_method.rb:165,207,211,215,227,288`). The scenario order points at a session and reacts to it.
- **A scenario purchase creates no `Spree::Order` unless it must.** VIP, points and coupon bundles are entitlements, not shipments: giving them an order would drag tax, shipping, inventory and fulfillment into a purchase that has none of those. Where a scenario genuinely produces physical goods — a welfare gift card that ships, a group-buy order — it uses an ordinary order instead, and the scenario order records the link.
- **The gateway gem gains nothing.** The extra `scene` values the mini program needs (`mini_program`, `native`, `h5`, `app`, `jsapi`) are already read from `external_data.scene` and `external_data.code` by the WeChat Pay gateway. This plan extends the core payment-session endpoint's accepted parameters; the gateway is untouched.
- **The frame is a gem, `spree_scenario_purchases` (2026-09-22).** It consumes `Spree::PaymentSession` and `Spree::Payment` as they are and decorates no core model, so unlike the coupon holding it does not need core's tables — only two columns on core's own payment rows, below. Open Question 1 answered as the plan recommended.
- **A scenario purchase is a third thing core's payment rows are for (2026-09-22).** `Spree::Payment#owner` already answers `order || cart || order_group`, and `Spree::PaymentSession#owner` answers `order || cart`; `spree_payments` and `spree_payment_sessions` each gain a nullable `scenario_order_id`, and `Spree::ScenarioOrder` is registered as an owner of both. This is what makes the key decision above true rather than aspirational: the gateway settles through `owner.with_lock` and `owner.payments.find_or_create_by!`, so a purchase with no order is payable only once the payment row can be for one. The gateways are untouched, and the registration is a string — a deployment without the gem never loads the association.
- **A kind declares both directions, and the reversal seam is settled now (2026-09-22).** Every kind answers `price(context)`, `issue!(order)`, `reverse!(order)` and `eligible?(customer)`: taking an entitlement back is each kind's own business — points reverse through the ledger, a coupon through its holding, a membership by the term it granted — so the frame carries the seam rather than inventing a reversal it cannot perform. Open Question 3 answered; no kind is registered in this step, so what ships is the contract.
- **The session's `scene` and `code` needed no core change (2026-09-22).** The store's session endpoint already permits an open `external_data`, and the WeChat gateway already reads `scene` and the scene's own extras from it — so step 3 as written turned out to be this frame passing them, not a change to core's endpoint. The sandbox proof remains outstanding and is not something this environment can perform.

- **Entitlement is granted once, on settlement, idempotently.** Every kind has an issue step that a retried settlement must not repeat, following `Spree::GiftCards::IssueFromOrder`'s idempotency rather than inventing a second pattern.

## Design Details

### The table

```ruby
create_table :spree_scenario_orders do |t|
  t.references :store, index: true
  t.references :customer, index: true
  t.references :order, index: true                  # null unless physical goods are involved
  t.references :payment_session, index: true
  t.string   :kind, null: false                     # vip/rights/gift_card/integral_mall/coupon_combo/team_buy
  t.string   :payment_channel, null: false          # wechat only; chinaums is a seam (gateway withdrawn, see decisions.md)
  t.string   :status, null: false                   # pending/paying/paid/canceled/expired
  t.decimal  :amount, null: false, default: 0
  t.string   :currency, null: false
  t.string   :payment_session_id
  t.jsonb    :payload                               # guarded by respond_to?(:jsonb), per AGENTS.md
  t.timestamps
end
```

Inherits `Spree.base_class`, includes `Spree::SingleStoreResource` and `Spree::Metadata`, uses `has_status` with no state machine, uniqueness scoped by `spree_base_uniqueness_scope`, and publishes lifecycle events. `amount` and `currency` are copied at creation so the row still explains itself after a price list changes.

### Lifecycle

1. `POST /api/v3/store/scenario_orders` with `kind`, `channel` and a kind-specific `context`. The kind's own service prices it — this is where a VIP term, a point quantity or a bundle definition is read — and the row is created `pending`.
2. A payment session is created against the store's payment method for that channel. `pending` → `paying`.
3. Settlement arrives through the existing webhook (`spree/api/app/controllers/spree/api/v3/webhooks/payments_controller.rb:22-57`) or the session-complete call. `paying` → `paid`.
4. The kind's issue step runs, idempotently, inside the settlement transition: grant the VIP entitlement, credit the points, issue the cards, issue the bundle codes, or mark the group-buy member as paid.
5. Failure to settle within the window moves the row to `expired`; a cancel moves it to `canceled`. `getNoOvertimePaymentGoods` and `getOvertimePaymentInfo` read exactly this state, so the mini program's unpaid-goods screens are scopes over this table rather than a second concept.

The kinds are registered so a new one is a new class, not a new branch: each declares its price, its issue step and its eligibility. That is the extension point, and it is what keeps this plan from growing when the seventh scenario appears.

### What each kind issues

| Kind | Issued on settlement | Owning plan |
| --- | --- | --- |
| `vip` | A membership term, optionally tied to a site | `6.1-membership-tiers-and-rights.md` |
| `rights` | A member right, or a coupon granted as a right — including the member add-on pack (会员加量包), which is a tier-bound coupon bundle and not a kind of its own (ruled 2026-09-17) | `6.1-membership-tiers-and-rights.md`, `6.1-coupon-wallet.md` |
| `gift_card` | A gift card, or a welfare grant; issued on settlement, not by `Spree::GiftCards::IssueFromOrder`, which stays the cart channel's issuer | `6.1-gift-card-purchase-and-transfer.md` |
| `integral_mall` | Points spent and goods ordered, or points bought | `6.1-points-and-growth-value.md` |
| `coupon_combo` | Coupon codes from the bundle | `6.1-coupon-wallet.md` |
| `team_buy` | The member's place in a group, or an ordinary order | `6.1-group-buying.md` |

**`vip` is the worked example of Decision 4, and it is ruled (2026-09-17).** A
membership purchase is a scenario order rather than an ordinary one, because
nothing about it ships. The client proves the shape: buying a term is one call
whose payload is a package id, the site, the coordinates, a referral code and
whether the buyer keeps it or gives it away — no cart, no line item, no address,
no quantity (`miniprogram/pagesB/components/member/pay-suspension/pay-suspension.js:143-148`).
An `orderNum` comes back and goes straight to the gateway (`:155,166-172`). Core
does have a no-address delivery of its own
(`FulfillmentProvider::Digital#requires_address?` is false), and it is still not
the answer: it reaches the customer through a cart and a checkout this app never
builds, and the same frame is wanted for kinds that have no delivery profile at
all.

**A kind's own reads stay with the kind's owning plan.** The pre-purchase check
(`vip/addOrderCheck` — sold out, and does a term already overlap) and the
post-settlement read-back (`vip/getSvipOrderBase` — what the purchase released)
are questions only the kind can answer, so they are registered beside it rather
than becoming generic scenario-order endpoints. This plan owns the frame, the
lifecycle, the channel column and the customer-scoped list; a kind owns its
pricing, its issue step and its own reads.

### Store API surface

| Method and path | Purpose |
| --- | --- |
| `GET /api/v3/store/pay_config` | One payload: available channels, the amounts and supported terms per kind, and whether the customer has a payment PIN. Replaces `getPayConfigV2` plus `getPaySettingByUserId` |
| `POST /api/v3/store/scenario_orders` | Create, with `kind`, `channel`, `context` |
| `GET /api/v3/store/customers/me/scenario_orders` | The customer's own scenario purchases, with the status filters the app's unpaid-goods screens need |
| `GET /api/v3/store/scenario_orders/:id` | One, guest-accessible by token like an order |
| `POST /api/v3/store/scenario_orders/:id/cancel` | Abandon an unpaid purchase |
| `DELETE /api/v3/store/scenario_orders/:id` | Remove one from the customer's own list — the client's `delIntegralOrder` (ruled 2026-09-18: deletion is a property of the resource, not of the `integral_mall` kind, so no kind grows its own) |
| `POST /api/v3/store/payment_sessions` | **Existing endpoint, extended** to accept `scene` and `code` |
| `POST /api/v3/store/payment_sessions/:id/complete` | **Existing** |

The balance payment the mini program calls `balancePayOrder` **is not this plan's** (ruled 2026-09-18). An earlier draft read it as a scenario purchase whose channel is the customer's stored value; it is a payment against an **order**, so it belongs to `6.1-store-api-miniprogram-gaps.md:47`, which owns the route and settles through `Spree::StoreCredits::Apply` — the service where the payment PIN is enforced (`6.1-phone-verification-and-payment-pin.md:37`). A scenario-style settlement here would have spent a customer's balance without that check, and the client's own distinction agrees: a scenario purchase is a thing bought, and `balancePayOrder` pays for an order already placed.

**Every scenario's payment leg is this plan's** (ruled 2026-09-18) — `vip/payByWxMp`, `rights/payCouponByWxMp`, `coupon_combo/payCouponComboByWxMp`, `integral-mall/payByWxMp`, `teamBuy/payTeamBuyByWxMp`, `gift-card/payByWxMp` and their ChinaUMS twins, the latter unservable while that gateway is withdrawn. They are the `wechat` value of `payment_channel` — the column the key decision above already establishes — rather than endpoints designed one by one per kind.

## Migration Path

1. `spree_scenario_orders` with the model, `has_status`, the kind registry and no kinds registered. Ship the frame first. **Being built** (2026-09-22).
2. The `pay_config` read, replacing two mini-program calls with one. **Being built** (2026-09-22).
3. Extend the core payment-session endpoint with `scene` and `code`, and prove the WeChat Pay gateway's mini-program scene end to end against a sandbox. **Half of this turned out to be unnecessary and half is out of reach here** (2026-09-22): the endpoint already accepts them inside `external_data`, so the frame passes them and core is unchanged; the sandbox proof needs merchant credentials this environment does not hold and stays with the plan.
4. Register kinds one at a time, each with its owning plan: `gift_card` and `coupon_combo` first (their substrates are the furthest along), then `vip`, then `integral_mall`, then `team_buy`.
5. Dashboard: a scenario-order list under the order area, filtered by kind, so a merchant can see what was sold and what failed to settle.
6. Regenerate types, Zod, OpenAPI and SDK tests as each kind lands.

## Constraints on Current Work

- **Do not add a payment endpoint per scenario or per channel.** One create, one channel parameter.
- **Do not give a scenario purchase an order line, a shipment or a tax treatment** unless it delivers physical goods, in which case it is an ordinary order with a link from here.
- **Do not modify `spree/providers/wechat_pay` or any gateway gem** to support this. If the session contract is insufficient, the missing piece is a core capability and goes into core, as asynchronous refunds did.
- **Every issue step must be idempotent**, must run inside the settlement transition rather than in an `after_commit` hook chain, and must publish an event rather than send a notification directly.
- **Never grant twice on a retried webhook.** The gateway can and will deliver the same notification more than once.
- **Do not take `balancePayOrder` back, and do not settle a balance anywhere but `Spree::StoreCredits::Apply`.** Paying for an existing order with a balance is the gaps plan's order-level route (ruled 2026-09-18); this plan's settlement path is for purchases, and a balance spent here without that service would bypass the payment PIN.

## Open Questions

1. ~~**Is this an extension gem or core?**~~ **Settled 2026-09-22: a gem, `spree_scenario_purchases`** — it decorates no core model, so the argument that put the grant row in core does not apply. What it does need from core is stated as its own decision above: two nullable owner columns on the payment rows.
2. ~~**Does the mini program need a payment PIN check before a balance payment, and where is it enforced?**~~ **Settled 2026-09-18.** It does, and it is enforced in the tender through a core registry seam plus one call site in the balance settlement, not in the API layer — the settlement paths outnumber the endpoint (`6.1-phone-verification-and-payment-pin.md`, and the decision entry in `fork-decisions.md`). The authorization step joins the lifecycle above as a check the settlement makes, not a step the client performs.
3. ~~**What happens to an already-granted entitlement when a scenario purchase is refunded?**~~ **Settled 2026-09-22: the frame carries a reversal seam and each kind performs its own** — `reverse!(order)` beside `issue!(order)` in the kind contract, because only the kind knows how to take its entitlement back. No kind is registered yet, so what ships now is the contract rather than any reversal.
