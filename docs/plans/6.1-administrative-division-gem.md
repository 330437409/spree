## Summary

The architecture plan's inventory calls this row "**extraction, not design**", and that is the whole plan: the four-level Chinese administrative tree is already specified inside the seller plan's `### AdministrativeDivision` section, and the repository's only other take on the same idea — a static 34-province name map — went with `6.1-cainiao-logistics-provider.md` when that plan was superseded on 2026-09-18. The client adds a second shape: it fetches the tree from three endpoints in two different forms and never bundles a province list of its own.

Two facts from the restored client decide the public contract, and neither is in the design being moved:

- **The province list sorts by pinyin and derives its A–Z anchors from it — and the pinyin is not on the model.** `pagesB/location/list/list.js:250-258` reads `firstPinYin` off every province-level row, sorts by it and slices its first character for the anchor strip (`list.wxml:106-111`). Two corrections to the earlier reading: this is the **location list page**, not the picker — the picker (`pagesB/components/common/select/select.js:29-34,199-243`) is a three-level province/city/district cascade that neither sorts nor shows anchors — and the rows it sorts are `site/getRegionTree`'s province entries, **each of which carries a `siteList`** (`list.wxml:75-93`). The division model as specified has `code`, `name`, `level`, `depth` and no pinyin, so the tree half of that payload cannot be answered from it; the site half is the seller plan's `site/getByProvince` read, not a division resource's.
- **The client's cascade is lazy by parent id, and one of its three callers searches by name.** `pagesB/components/common/select/select.js:131-138` loads children with `{ pid: <parent id> }`; `:116-123` fetches the same picker's options by `{ keywords: <name> }` from a different endpoint that answers with a vendor `adcode` the plan set forbids storing (`Decision 9`, seller plan `:132-136`).

## Key Decisions (do not deviate without discussion)

- **The model moves; the design does not get rewritten.** `Spree::AdministrativeDivision` keeps its columns as specified in the seller plan's `### AdministrativeDivision` section — `parent_id`, `level` (`country`/`province`/`city`/`district`/`township`), `depth`, `code`, `name`, `dataset_version`, `source`, `source_updated_at` — and its code scheme from that plan's `Decision 7`: GB/T 2260 for province/city/district, the bureau's township codes, `CN` for the root. A redesign here would invalidate the seller plan's binding and matching design, which is already at v1.2.
- **The seller plan keeps everything above the tree.** Bindings on `StockLocation`, the polygon and its validator, reverse geocoding and its cache, `Decision`, `resolve_seller` and its endpoint all stay where they are specified. What moves down is the tree, its import and its mapping assets.
- **The tree gains pinyin, because the client reads it.** `first_pinyin` (and a full `pinyin` for keyword search) become columns on the division, supplied by the import dataset rather than computed at request time.
- **A division is addressed by `code`, not by a database id.** The seller plan's own Store API contract already answers a division as `code` + `name` + `level`, and a bureau code is stable across re-imports in a way a row id is not — the whole point of `dataset_version` is that the dataset churns while the codes hold.
- **Reference data is imported, never edited, and never improvised.** `Decision 15` of the seller plan makes `dataset_version` an immutable release id, so a mid-month correction is a new release; `Decision 9` makes the vendor mapping a versioned data asset. This plan ships the tree and the vendor code maps in that family — and **not** the ISO→bureau province crosswalk, whose only consumer left with the superseded Cainiao plan (2026-09-18); it lands if another consumer appears.
- **The province-only variant is gone, not retired.** It lived in `lib/spree_cainiao/province_names.rb` inside a plan that is now superseded, so there is no name table to replace and no second design to consume the tree.
- **Addresses do not gain division references.** The client stores region **names** on a customer address (`pagesF/address/details/details.js:57`, `shipping.js:482,521,550`) and core stores ISO codes only (`6.0-drop-country-state-models.md:75`). Adding a division FK to `spree_addresses` would be a core-table change for a value nothing joins on, so the tree stays read-through for addresses and the only division references in the system remain the seller plan's `StockLocation` bindings.
- **The "five amendments" are read as the seller plan's promotion to foundation status**, listed in the Migration Path below; the phrase appears once (`6.1-miniprogram-extension-architecture.md:107`) and is defined nowhere, so the reading is recorded in `fork-decisions.md` rather than inherited.
- **One filtered collection answers all three endpoints (ruled 2026-09-18).** The client's three callers differ in filter, not in shape, so three endpoints would be three serializations, three cache keys and three surfaces to keep in step. **Accepted trade-off:** the client's translation is a query parameter rather than a path.
- **The dataset ships inside the gem under `data/administrative/`, imported by a rake task (ruled 2026-09-18).** The alternatives — Ruby constants under `lib/`, or host-application seeds — were rejected because a foundation gem four other plans consume has to be self-contained, and a 3,000-row tree is not code. **Accepted trade-off:** every gemspec in the repository globs `{app,config,db,lib,vendor}/**/*`, so the new gem's glob gains `data` and a packaged-gem check is the only thing that catches a regression.
- **Pinyin rides the dataset (ruled 2026-09-18).** Place names are exactly where romanisation polyphones bite, and a gem-computed value would also move whenever the gem versions; the dataset is versioned as a whole, so its pinyin is versioned with it. **Accepted trade-off:** two more columns to maintain when the dataset is prepared.
- **The gem is `spree_administrative_divisions` (ruled 2026-09-18)**, at `spree/extensions/spree_administrative_divisions/`. It matches the model's name and collides with none of Spree's existing geographic vocabulary (`market`, `zone`, `delivery zone`).

## Design Details

### The model

Moved verbatim from the seller plan's `### AdministrativeDivision` section, with
two columns added:

```ruby
create_table :spree_administrative_divisions do |t|
  t.bigint   :parent_id, null: true            # nil on the CN root — bigint, not uuid: every table in this repository has a bigint primary key (corrected 2026-09-18)
  t.string   :level, null: false               # country / province / city / district / township
  t.integer  :depth, null: false               # 0..4, denormalised for deepest-match ordering
  t.string   :code, null: false                # GB/T 2260 (6), bureau township code (9), CN for the root
  t.string   :name, null: false
  t.string   :first_pinyin, null: false        # the picker's sort key and A–Z anchor
  t.string   :pinyin                            # full romanisation, for keyword search
  t.string   :dataset_version, null: false     # immutable release id, e.g. nbs-2026-09-01
  t.string   :source, null: false              # provenance, e.g. nbs-2026
  t.datetime :source_updated_at
  t.timestamps
end
```

- `UNIQUE(code)` including the `CN` root, and an index on `(depth)` as the seller plan states (`:218`, `:226-227`, `:503-504`). Global reference data: **no `store_id`**, like `Spree::Country`/`Spree::State` — this is the one place the `SingleStoreResource` rule does not apply, and the seller plan says so explicitly (`:208`).
- The tree is five levels deep, so the ancestor chain is a fixed-size walk and no recursive query is ever needed — which is why the seller plan's membership test is one `IN` over ≤5 nodes (`:398-401`).
- Irregular structures are tolerated rather than modelled: municipalities, SARs and province-administered counties omit levels, so the chain builder skips absent ones (the seller plan's Open Question 2).
- **Do not route GB/T codes through `Spree::IsoData` or `has_iso_geography`.** That concern is ISO-specific by construction — it validates a code against the `countries` gem and answers with `Spree::Country`/`Spree::State` value objects (`spree/core/app/models/concerns/spree/has_iso_geography.rb:1-10`) — and a 6-digit GB/T code is not an ISO subdivision code. The division model is its own reference-data model beside that concern, not an instance of it.

### The tree resource

| Method and path | Replaces |
| --- | --- |
| `GET /api/v3/store/administrative_divisions` | `site/getRegionTree`, `common/getRegionTreeGw`, `address/district` — filters: `parent_code`, `level`, `keywords`; `pid`-style lazy loading is `parent_code`, and `keywords` searches `name` and `pinyin` |

- Each node answers `{ code, name, level, first_pinyin, has_children }`. `has_children` is the picker's own need — a cascade that lazily loads a leaf would otherwise spin.
- The default answer is the province list (`level=province`), which is what the client's first call wants; the address picker stops at `district`, and the seller-join form stops at `district` too (`pagesB/me/join/join.js:63-82`), while the service-area binding needs `township`. Levels are filtered by the caller rather than by three endpoints.
- Read-only, publishable-key auth, cached: the dataset changes only when `dataset_version` does, so the cache key is `dataset_version` + the filter, and it never needs invalidation within a release.

**As built (2026-09-19).** The resource is a gem-local controller rather than a core one — `spree_administrative_divisions` ships it and draws its route through `Spree::Core::Engine.add_routes`, the hook this repository's own extension already uses, so no core routes file is touched. It inherits the Store API's base, which is what gives it the publishable key, the guest gate and the error shape.

Three details the implementation settled:

- **`has_children` is answered once per page.** A node asking its own `children.exists?` is a query per node, and the province list alone is thirty-one of them; the controller looks the set up once and the serializer reads it.
- **The cache key is the release plus the filter**, as designed, which makes a new import a new key rather than an invalidation: the entries of the previous release simply age out. One key does have to be cleared — the memo of *which* release the table holds — and the import clears it, because a rake task that writes a release and leaves the reader believing in the old one would strand the whole tree.
- **An unknown `parent_code` answers an empty list, not the root.** The obvious implementation (`where(parent_id: <resolved>)`) turns a code that resolves to nothing into `where(parent_id: NULL)`, which is the root's own predicate — so a question about a node that does not exist would have answered the top of the tree. The spec that caught it is now the regression test.

### Reference data: where it lives and how it arrives

This is new ground — **no gem in this repository ships reference data today**, and no `data/` directory exists under `spree/`. Three things have to be decided together and stated here:

1. **The dataset files** live in the gem under `data/administrative/` as versioned files, the shape the seller plan's `Decision 9` already prescribes for the vendor mappings — and the vendor mapping files live here too, since the ruling moved them with the tree; the seller plan ships the mapper that reads them.
2. **The gemspec must ship them.** Every gemspec in the repository globs `{app,config,db,lib,vendor}/**/*` (`spree/providers/wechat_pay/spree_wechat_pay.gemspec:25` and its siblings), so `data/` would be silently dropped from a packaged gem. The glob gains `data`.
3. **An import rake task** seeds and updates the tree from those files and bumps `dataset_version`; nothing in the admin UI edits it (the seller plan's Admin UI section says the same, and the task is this gem's). Per the repo's migration rules, a data transformation is a rake task and never a migration.

Pinyin comes from the same dataset rather than a runtime gem: the client needs it on every node, the dataset is versioned as a whole, and computing it at read time would put a romanisation dependency in the request path.

### The province map left with its plan

The repository's second take on Chinese geography was a static 34-entry map from ISO subdivision code (`BJ`) to Chinese name, inside `6.1-cainiao-logistics-provider.md`, because `Spree::Address#state_validate` clears `state_name` when a code is present and `state.name` answers in English. **That plan was superseded on 2026-09-18**, so the map is not amended and not retired — it is gone with the consumer that needed it, and nothing here replaces it:

- The ISO→bureau crosswalk the retirement would have needed (a Chinese address carries `state_code = BJ`, not `110000`) has **no consumer left**, because its only one was the Cainiao address params. It is not built; if a future consumer needs to cross from an ISO code to a bureau code, it joins the versioned mapping assets beside the Tencent and Amap files, 34 rows in one file.
- What the tree still answers is the question every other surface asks: a name for a division, by code or by proximity — the client's pickers, the address forms and the seller binder all read it.

### Polygons stay the seller plan's, and the shape boundary is stated

The client's delivery areas are a flat list of `"lng,lat"` strings, longitude first (`pagesF/address/shipping/shipping.js:389-403`), while the seller plan's stored geometry is GeoJSON in GCJ-02 with a bbox pre-check (`:229-247`). The conversion belongs in the serializer at the boundary where the client is replaced; the gem stores GeoJSON and nothing else, and no legacy coordinate-list shape reaches the database.

## Constraints on Current Work

- **Do not redesign the model.** Its columns, levels and code scheme are the seller plan's and are already built on by the binding, matching and polygon designs.
- **Do not write a second region table.** The repository's only other one left with its superseded plan, and a future consumer (regional pricing, invoicing, address pickers) reads this gem — that is the whole reason it is a foundation gem rather than a section of the seller plan.
- **Never store a vendor code.** `adcode`, Tencent and Amap codes are mapping assets, never columns and never request payloads that reach a write.
- **Do not add division references to core tables.** `spree_addresses` and `spree_orders` stay untouched; the only division reference in the system is the seller plan's `StockLocation` binding.
- **Do not put this tree behind `Spree::IsoData`** or `has_iso_geography`; it is a separate reference-data model.
- **Do not let this gem become a third geographic-eligibility mechanism.** The DeliveryZone exemption is argued and written in the seller plan (`:559-569`) and is not re-argued here.
- **Reference data is imported, never edited in the UI**, and a correction is a new `dataset_version`, never an edit inside one.
- **Wire the gem in three places or its specs never run** — and note that two shipped gems currently miss one of them.

## Open Questions

The four questions this plan opened — the endpoint's shape, where the dataset lives and how it is packaged, where pinyin comes from, and the gem's name — were settled on 2026-09-18 and now sit in **Key Decisions** with their trade-offs.

~~One item is genuinely deferred: **which bureau dataset release to start from, and what cadence refreshes it.**~~ **Answered by the first import (2026-09-19), and the answer closes the question rather than opening a cadence.** The shipped release is the bureau's **2023-06-30** snapshot — 31 provinces, 342 cities, 2,975 districts and 41,352 townships — and it is likely to stay the newest one available: **since October 2024 the National Bureau of Statistics publishes the classification rules but no longer the codes themselves**, so there is no next annual release to move to. A future refresh therefore means a different source (a commercial data vendor, or the mapping assets that already live beside this dataset for Tencent and Amap), and the release id, the import and the endpoints are unchanged by that: a new source becomes a new `dataset_version` directory.

Three further things the first import settled, all recorded in the shipped files rather than in prose:

- **The publisher's codes are truncated at the top two levels and are widened on preparation.** The source writes 北京市 as `11` and 市辖区 as `1101`; the release ships the six-digit GB/T forms this plan's Decision 7 names, so the level is readable from the code's width alone.
- **Three cities are merged with their own repeat.** 东莞市, 中山市 and 儋州市 administer no districts and the publisher's tree repeats each under its own code, once as a city and once as the single "district" inside it. A code names one node, so the shallower occurrence is kept and the repeat is listed in the file's `dropped` field; their townships — 36, 23 and 18 respectively — still attach to the city. Without this, the unique index would have decided which of the two survived — silently, and differently on a second run — which is also why the import now **refuses** a release that carries a duplicate code rather than importing it half-way.
