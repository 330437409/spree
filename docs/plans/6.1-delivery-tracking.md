## Summary

The mini program calls about ten endpoints to show a buyer where their order is: a trajectory, a delivery position, the courier's name and phone, and a signed-for detail. Spree already records most of the facts. `spree_deliveries` carries the tracking number, the tracking URL, the carrier, the service, a status, an estimated delivery time and a delivered time, with the status vocabulary already enumerated (`spree/core/app/models/spree/delivery.rb:22-25`: pending, pre_transit, in_transit, out_for_delivery, available_for_pickup, delivered, return_to_sender, failure, unknown), and the migration is in place. Two things are missing and they are different in kind. The scan history is **already designed** — `6.0-delivery-scan-events.md` owns `spree_delivery_events`, its dedup fingerprint, the monotonicity guard and the scan value object, and it reserves the buyer-facing timeline as its own phase two. The live rider position has **no representation anywhere**: there are no coordinates on `Spree::Delivery`, on `Spree::Fulfillment` or on `Spree::StockLocation`, and coordinates exist in the whole schema only on `spree_addresses`. That is the genuinely new capability, and this plan is mostly about it.

## Key Decisions (do not deviate without discussion)

- **The scan model is not redesigned here.** `6.0-delivery-scan-events.md:86-116` specifies `spree_delivery_events` with its columns, indexes and fingerprint dedup, the `Spree::Deliveries::Scan` value object, the `scans:` keyword on `Deliveries::UpdateTracking`, the monotonicity guard, and the two nested admin and seller index routes (`:199-202`). Nothing in that design is repeated. This plan consumes it and adds only what it does not cover.
- **Current status never comes from the event log.** That plan states it as a constraint on all current work, and it is load-bearing for performance and for correctness: `spree_deliveries.status` is authoritative and the events explain how it got there. A trajectory view reads the events; a badge reads the delivery.
- **A carrier provider must not send `scans:` before the guard ships.** Also from that plan's constraints. Without the guard, an out-of-order scan can move a delivery backwards.
- **Status mapping and reconciliation belong to the plan that owns the carriers, and that is now `6.1-local-delivery.md`.** It maps each platform's vocabulary per member — no two of them share one — and keeps the fee reconciliation, since 已取消仍扣费 and 改派重复扣费 are the documented daily exceptions. The Cainiao plan that used to hold this delegation is superseded (2026-09-18), so nothing is delegated to it any more and none of it is re-implemented here.
- **A position is not a scan.** A scan is a discrete event with a status and a place in the lifecycle; a position is a sampled coordinate with a time. They have different producers, different rates, different retention and different privacy exposure. Putting a coordinate on the scan row would make an unbounded stream look like a bounded history and would inherit the wrong retention rule.
- **The courier's coordinates are personal data.** A rider's location is the courier's personal data even when the delivery is the buyer's. The buyer sees a position only while the delivery is out for delivery, the retention is bounded and configurable, and the courier's phone number is masked in the buyer-facing payload — the mini program showing `getDeliveryPhone` is a business requirement to state, not an entitlement to assume.
- **The buyer's view is scoped through the order.** Trajectory and position are reachable from an order the customer owns or from a signed-in guest token, never by a bare delivery id, matching how the existing Store order resources are gated.

## Design Details

### Core: the position ingress

```ruby
create_table :spree_delivery_positions do |t|
  t.references :store, index: true
  t.references :delivery, index: true
  t.decimal  :latitude,  precision: 10, scale: 6
  t.decimal  :longitude, precision: 10, scale: 6
  t.datetime :recorded_at, null: false
  t.string   :courier_name
  t.string   :courier_phone
  t.jsonb    :details                    # guarded by respond_to?(:jsonb)
  t.timestamps
end
# index (delivery_id, recorded_at)
```

This is a core capability rather than a gem table for the same reason asynchronous refunds were: it is an interface a provider calls, and a gem may not add columns or tables that core behaviour depends on. The ingress is a small service and a single API or webhook entry point that a provider posts to; the rider view in the extension reads it.

Retention is not a detail. A position stream is unbounded where a scan history is not, so the plan carries a pruning job with a configurable window — `ActiveJob::Continuable` for the sweep, since it iterates rows.

### Extension: the rider view and the Store surface

`spree_delivery_tracking` ships no migrations unless the operator needs provider-specific fields; it holds the presenter that turns a delivery plus its recent positions into the payload the mini program renders, the courier lookup, and the pruning schedule if the operator prefers it out of core.

The Store API surface the mini program needs:

| Method and path | Purpose |
| --- | --- |
| `GET /api/v3/store/orders/:id/trajectory` | The whole order's timeline across its deliveries. Covers `orderTrajectory` and `orderTrajectorySnowBeer`, which differ only in which carrier is behind them |
| `GET /api/v3/store/orders/:id/deliveries/:delivery_id/events` | One delivery's scan history. **This is the scan plan's reserved phase two**, so it is built there if that plan is implemented first, and here only if it is not |
| `GET /api/v3/store/orders/:id/deliveries/:delivery_id/position` | The live position, masked courier details, and an explicit `as_of` timestamp |
| `GET /api/v3/store/orders/:id/signing` | The signed-for detail (`getOrderSignDetail`) |

`getDeliveryInfo`, `getDeliveryPhone` and `getDeliveryPosition` are the same three fields viewed from three screens; they become fields on the delivery payload rather than three endpoints. Whether the courier's phone is returned in full or masked is Open Question 3.

Admin and seller already have nested scan index routes from the scan plan; this plan adds no new admin surface except a configuration screen for the retention window.

## Migration Path

1. Confirm the scan plan's status. It is Draft and has **no implementation** — a search for `DeliveryEvent` in `spree/` returns nothing. If it lands first, the timeline is free; if not, this plan has to build the timeline too, and that is a scope change to agree before starting.
2. Core: `spree_delivery_positions`, the ingress service, the pruning job, and the retention preference.
3. The provider that posts positions — `6.1-local-delivery.md`'s members, which poll a rider position while a delivery is out for delivery and post it here, under the same ordering constraint.
4. Extension: the trajectory presenter, the masked courier payload, and the Store API surface.
5. Verify the whole path against a real delivery, because a tracking view that is subtly wrong (positions out of order, a stale status, a position after delivery) is worse than no view.
6. Regenerate types, Zod, OpenAPI and SDK tests.

## Constraints on Current Work

- **Do not read the current delivery status from the event or position tables.** `spree_deliveries.status` is authoritative.
- **Do not send `scans:` from a provider before the monotonicity guard exists.**
- **Do not re-implement status mapping or fee reconciliation.** `6.1-local-delivery.md` owns both, per member.
- **Do not put coordinates on the scan row, on `Spree::Fulfillment` or on `Spree::StockLocation`.** A position is its own row with its own retention.
- **Do not expose a delivery position after the delivery is complete**, and do not expose a courier's unmasked phone number without an explicit decision.
- **Do not add a `latitude`/`longitude` pair to `spree_deliveries`** as a shortcut for "the last known position". That is a cache of a stream and it will disagree with the stream.

## Open Questions

1. ~~**Who owns the buyer-facing timeline — this plan or the scan plan's phase two?**~~ **Settled 2026-09-18: this plan owns it.** The scan plan reserved it when it had no code, and it still has none; this plan is named "the buyer timeline", already carries `GET /api/v3/store/orders/:id/trajectory` and the position reads, and has the producer (`6.1-local-delivery.md`) that the scan plan was waiting for. The scan plan's own phase-two paragraph now points here (`6.0-delivery-scan-events.md:86-93`), so the reservation is closed on both sides rather than left as two owners.
2. **What is the position retention window, and who decides it?** A stream of coordinates is a liability with a cost. Options: a fixed short window in core with a store preference to shorten it, or a per-store configurable window with no default. Unblocked by the operator's data-protection position.
3. **Is the courier's phone number shown in full?** The mini program has `getDeliveryPhone` and `getDeliveryPhoneSnowBeer`, so the current system does. A full number is the courier's personal data and a harassment surface. Unblocked by a product decision; masking is the recommendation.
4. ~~**Is there a same-city delivery provider in the loop at all, or only Cainiao?**~~ **Answered 2026-09-18: one is being added, and the rider view is buildable.** `6.1-local-delivery.md` dispatches to a local instant-delivery network, its first member is 达达, and the position arrives by **poll** there and by **callback** on UU — so the ingress accepts both shapes and the rider view has a producer either way. The client's own evidence settles the question this asked: it polls a rider position every 30 seconds and renders a rider's name, phone and rating, which only a real rider network can fill.
5. **Does the position ingress need to be in core?** It is argued here as an interface a provider calls, which is the core-first rule. If the only producer is a single extension gem, an extension table would be mechanically possible — but then core behaviour that wants a position would have to decorate it.
