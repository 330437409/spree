## Summary

The row looks like a gem and decomposes into **one addition and one small consumer**: **a customer-scoped direct-upload path**, and the feedback endpoint the architecture plan reassigned here because it posts pictures through it. The concern already exists — `Spree::Api::V3::DirectUploads` calls `ActiveStorage::Blob.create_before_direct_upload!` and answers `{direct_upload: {url, headers}, signed_id}` — and its own doc comment says the exchange is audience-neutral and *"what differs is the gate each branch puts in front of it, which stays on the including controller as its `scoped_resource`"* (`direct_uploads.rb:4-11`; the gate it names abstractly is the store branch's `require_authentication!` rather than that mechanism, below). It is included twice today, admin and seller, and **the store side has exactly one presigner, which is a cart's PO document** — `POST /api/v3/store/carts/:cart_id/po_document` (`routes.rb:66`), gated by `CartResolvable` and minting on private storage (`carts/po_documents_controller.rb:15-17,37-51`). So the addition is a **customer-scoped** store route, not the first store route, which is what the architecture plan predicted: "the direct-upload concern exists but is gated to admin and seller, so a customer-scoped upload path is the only addition. Do not add a file table" (`:138`).

Five consumers are waiting on it, and one of them is already shipped with no way to fill it:

- **Reviews** attach up to nine photos per review and say so (`6.1-product-reviews.md:176-181`, capped to match `appraise.wxml:105`) — the plan that names this one as the upload path's owner, and the first consumer to land.
- **The distribution** real-name flow needs the **private** variant, with the client's own second contract (`newUrl`, not `url`, `idInfoBehavior.js:121`), landing on that plan's own `spree_distributor_verifications` private attachment (`6.1-distribution-and-commissions.md:60`); `Spree::SellerRequirementSubmission` is its precedent, not its target (`seller_requirement_submission.rb:39`).
- **Feedback** (`suggestionFeedback/addSuggestion`) posts pictures with the complaint.
- **Two avatar flows** upload with no bucket prefix at all, and the client disagrees with itself about whether the response is absolute (`edit.js:108-109`, `mall.js:492` versus `feedback.js:73`) — the contract this plan states is the one to implement, not the two it finds.
- **`Spree::ClaimLineItem#images`** — core's own customer-supplied damage photos, `has_many_attached` since it shipped, and **the Store API's claim create permits no `images` parameter at all** (`claims_controller.rb:66-81`). A model with an attachment and no path is the strongest evidence that the missing piece is the path, not the storage.

The subscribe-message half is **not** a second mechanism: `6.1-notifications.md` owns the platform's single system-notification sender, the phone plan contributes its `sms` channel, and this plan contributes **`wechat_subscribe`** as the second. So this plan ships a channel implementation and nothing that sends on its own. (The marketplace relay beside it is a buyer-seller conversation, not a sender — the architecture plan's capability row used to point at it, and that was a misreading corrected on 2026-09-18.)

## Key Decisions (do not deviate without discussion)

- **One core addition: `POST /api/v3/store/direct_uploads`**, a `Store::DirectUploadsController` including the shipped concern and gated the way every customer-scoped store controller is — `prepend_before_action :require_authentication!` (`store/customer/addresses_controller.rb:7`) — because `scoped_resource` is the **admin and seller API-key scope mechanism** (`scoped_authorization.rb:31`), not a customer gate; the concern's comment names the gate abstractly and leaves the idiom to the branch. Not a gem, because there is nothing else in this plan worth a gem: the route, the gate and the storage service are the whole of it, and the architecture plan's storage row already says "do not add a file table".
- **Public storage for what a customer displays; private for what identifies them — and the service is chosen when the blob is minted, not when it is attached.** Reviews, feedback and avatars use the public service (`Spree::ClaimLineItem#images` declares none and falls back to the default, which is it; the reviews plan chooses it explicitly); identity documents use `Spree.private_storage_service_name` (the `SellerRequirementSubmission` precedent). The mechanism is the part this plan had to correct: shipped controllers say twice that *"attaching a signed id never moves a blob between services"* (`admin/direct_uploads_controller.rb:22-26`, `carts/po_documents_controller.rb:15-17`), so the route takes the consuming kind and presigns on the service that consumer declares, exactly as the admin controller's own `create` override does (`:39-49`).
- **The client keeps its own consent bookkeeping; the server learns what it needs to send.** The template ids are hard-coded client-side today — 24 event keys over 42 ids in the live environment, 36 of them distinct, in `static/config/appConfig.js:71-95`, whose values are an environment pair — and the client reports the grant per event. The server therefore needs one thing per event: **which template id to use**, and that map lives on a **`Spree::Integration`** (ruled 2026-09-18) — the one credential home for configuration of this kind. **Corrected 2026-09-18:** an earlier draft justified that placement by saying the mini program's app secret "has to live there anyway", which is not true of this credential — the app id and secret pair sits on the WeChat Pay **gateway's preferences** (`gateway.rb:23-24`, deliberately, per the upstream decision recorded at `gateway.rb:5-9`), and `spree/providers/social_auth` reads it from there as the owner of the one `access_token` service. The template map is configuration rather than a secret, so an integration row is still the right home; the false justification is what is withdrawn. That the *sending* is `spree_notifications`' is not in question.
- **The dictionary gets no endpoint, and the reason is the client's, not Spree's.** The mapping grades it B and calls it "Spree 模型枚举" (`:629`), but two of the three types have **no Spree field at all**: nothing in `spree` carries `gender` or a remark type, while `trade_payment_way` is a label map the client patches in JS (`"11"` → 支付宝, `orderInfoBehavior.js:49-51`). What the client asks for is the **labels**, and the values themselves travel on resources it already fetches — except the two it *posts* (the address's gender and the order's remark type, `shipping.js:415-428`, `orderInfoBehavior.js:37-42`), which are fields the API must accept. So the decision is: no dictionary resource, because a `spree_dictionaries` table would be a vocabulary invented beside the models — and **those two fields are named here as a gap for whichever plan owns the address and the order surfaces**, not silently absorbed.
- **`sensors/*` is recorded as answered, not restated.** The gaps plan owns the reads ("serve from `products/index`") and forbids ingestion; the reviews plan has already disposed of `getCommentGoods`; and two of the family have a non-sensors twin the client already calls when the zone's own flag is false (`home.js:1017` gates, `:1030` is the ordinary call), which shows the endpoints are recommendation slots rather than an analytics surface. **This plan builds no `sensors` namespace**, so the payload is not defined in two places.
- **The click-id pair builds nothing.** Two D-graded endpoints whose reporting goes from the client to Sensors directly.
- **Uploads are validated where the attachment is declared — and the route pre-checks anyway.** `Spree::AttachmentContentTypeValidator` handles a direct-upload blob, but by **discarding the declared content type and sniffing the bytes** against an allowlist (`attachment_content_type_validator.rb:5-12,57-69`), and it tolerates an abandoned upload (`:86,150`). That runs only once the bytes are stored, which is why the shipped store presigner pre-checks size and type at the route (`carts/po_documents_controller.rb:30-36`) and why this one does too. The owning resource keeps the cap that names its own limit (nine for a review).
- **The relative-path contract is replaced, not preserved.** The client's `bucketInfo + path` dance exists because the legacy gateway answered a path and a prefix separately; the direct-upload contract answers a signed blob id and a URL, and the two avatar callers show the old contract is already ambiguous. The client is rewritten against one shape, as the architecture plan requires for every surface.

## Design Details

### The upload path

```
POST /api/v3/store/direct_uploads
  { blob: { filename:, byte_size:, checksum:, content_type: } }
→ { direct_upload: { url:, headers: }, signed_id: }
```

- The controller is `Spree::Api::V3::Store::DirectUploadsController < Store::ResourceController`, `include Spree::Api::V3::DirectUploads`, with `require_authentication!` as its gate — the concern's comment says only that the gate belongs on the including controller, and this is the store branch's way of putting one there.
- The client uploads to the returned URL directly and attaches with the signed id: `images: [<signed_id>, ...]` on the review create, capped at nine by the review's own validator. **`signed_id` is the contract between the two plans**, and `6.1-product-reviews.md` may now rely on it.
- **The private variant is not a second route, but it is a second decision at mint time**: the request names the consuming kind, and the route presigns on the service that consumer declares — because attaching a signed id never moves a blob between services (`carts/po_documents_controller.rb:15-17`). The admin controller's `create` override is the precedent for choosing per request (`admin/direct_uploads_controller.rb:39-49`).
- **`Spree::ClaimLineItem#images` becomes the second caller** and the change is core's: the Store API's claim create gains an `images` parameter and the claim workflows accept it. That is a core change this plan names rather than quietly widening.

### The subscribe-message channel

- The gem gains a channel implementation whose send takes a customer, an event key and a payload, and resolves the template id per store.
- The consent the client already reports — `pickType` plus a `templateIds` array of `{openType, templateId}` (`report.js:149-187`; the `templateIdsTrue`/`templateIdsFalse` names are the client's own local state) — is **data the server stores per customer and event**, because WeChat permits at most one message per granted template and a sender that does not know the grant will fail silently.
- Every plan that needs a notification asks this channel by its own event key: the seckill's 开售提醒, the group buy's result, the membership's gift, the invoice's re-send. **None of them gets a sender.**

### What the dictionary becomes

Nothing. The client asks for three vocabulary types and wants **labels**; the values themselves travel on the resources it already fetches, except the two it posts — the address's gender and the order's remark type — which are fields the address and order surfaces must accept. The plan records both halves so the next reader neither re-opens the endpoint nor mistakes the two fields for an oversight.

## Migration Path

1. **The store direct-upload route and its gate**, with the customer resolved from the request context and the service chosen at mint time.
2. **The contract, written down** — request, response, `signed_id`, the public/private split, and the nine-image cap — because the reviews plan waits on exactly this and must not have to guess it. Its Migration Path step 3 then consumes it.
3. **The consuming attachments**: the reviews' images, the feedback endpoint's pictures, the two avatars, and the distribution plan's private identity documents.
4. **The core widening for `ClaimLineItem`** — the Store API's claim create and its workflows accept `images`, since the model has carried the attachment all along.
5. **The `wechat_subscribe` channel in `6.1-notifications.md`**: the implementation, the per-store template map, and the stored consent.
6. Regenerate types, Zod, OpenAPI and SDK tests.

## Constraints on Current Work

- **Do not add a file table, and do not build a second storage mechanism.** One bucket, one blob row, the shipped concern, one new gate.
- **Do not add a second notification mechanism.** The subscribe message is a channel inside `spree_notifications`.
- **Do not add a `sensors/*` namespace**, and do not define the recommendation payload a second time: the gaps plan owns those reads and forbids ingestion.
- **Do not build a dictionary table.** The labels are the client's, and the two values it posts are fields on the address and the order rather than a vocabulary resource.
- **Do not reproduce the `bucketInfo + path` contract.** One shape, and the client is rewritten against it.
- **Do not let an upload route replace a resource's own validation — and do pre-check at the route.** The consuming attachment owns its content type and its cap; the route pre-checks size and type anyway, because an attachment's validator runs only once the bytes are already stored (`carts/po_documents_controller.rb:30-36`).
- **Do not resolve the seller here**, and do not scope an upload by one: a customer's photo belongs to the customer, not to a seller.
- **Do not let this plan's absence block a consumer silently.** A consumer that needs the route names it in its own header, the way the reviews plan names this one.

## Open Questions

Two of this plan's five questions were settled on 2026-09-18: **it stays a plan and ships no gem** — what it delivers is a *contract*, and the reviews plan explicitly declines to specify one, so the contract needs a document — and **the per-store template map lives on a `Spree::Integration`**, the one credential home, which is where the mini program's app secret has to live anyway.

Three remain. **Which storage service each consuming kind declares** — this draft splits public for display and private for identity, while the alternative, everything private with signed URLs, is stricter and costs a signing path the client does not have. **Whether `bar/bingUserBar` and the `threeOrder` templates belong here** — the former reads as a membership or venue binding rather than a platform service, and the latter is an open question in the architecture plan whose two subscribe templates are already in the client's map. And **where the address's gender and the order's remark type are added**: this plan names them as fields the API must accept — the dictionary's own ruling depends on saying so — but it owns neither the address nor the order surface, so the addition belongs to whichever plan does.
