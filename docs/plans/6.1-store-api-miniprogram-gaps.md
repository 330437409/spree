## Summary

Of the 566 endpoints the 酒小二 mini program calls, 107 correspond to something Spree already models — 27 exactly, and 80 only nearly. This plan closes the 80. It is deliberately not an extension gem: the work lands in `spree/api` and `spree/core` because a customer-facing read or write that every storefront needs belongs in the Store API, and because an extension gem may not patch core models. Nothing user-visible in the mini program works before this plan does, which is why it is Wave 0 of `6.1-miniprogram-extension-architecture.md`.

## Key Decisions (do not deviate without discussion)

- **Extend Store API v3 in place; build no `/v2-app-mall` facade.** A facade over 80 partly-matching endpoints would re-implement the legacy contract and still need every change below, paying twice.
- **A read that Ransack cannot express becomes an explicit parameter or a dedicated collection action, never a filter the allowlist cannot enforce.** The batch product load is the worked case: `self.whitelisted_ransackable_attributes` on `Spree::Product` (`spree/core/app/models/spree/product.rb:369`) lists `description name slug discontinue_on status available_on created_at updated_at seller_id` — **no `id`** — so `goods/getGoodsByIds` cannot be served by `?q[id_in][]=` until either the allowlist gains `id` or the endpoint gains a first-class parameter.
- **A seller-scoped catalogue is scoped through variants, never `Product#seller_id`.** A site is a seller and a seller holds *offers* on the operator's master catalog, so `Product` rows are store-wide and their own `seller_id` is nil (`fork-decisions.md`, 2026-09-17). `seller_id` is nonetheless on the product Ransack allowlist (`spree/core/app/models/spree/product.rb:369`), which makes `?q[seller_id_eq]=` look like the seller scope while returning the operator's own listings — a silent wrong result, because the relation is valid and returns rows. The scope is `Product.joins(:variants).merge(Variant.for_seller(seller))` (`spree/core/app/models/spree/variant.rb:211`), and the price and stock a seller's storefront shows are its offer's, not the master product's.
- **A customer-facing cancellation goes through the existing cancel workflow, not a new one.** `docs/plans/5.5-6.0-order-cancellation-and-approval.md:69` already anticipates this — "a future customer self-cancel makes the actor on the order" — and the Store API has no cancel route today (`spree/api/config/routes.rb`, Store `orders` is `only: [:show]`).
- **Writes declare `resource_permitted_attributes` and never override `permitted_attributes`**, per `AGENTS.md`, so extension-contributed attributes survive. This matters here because three of the extensions in this set add writable product and cart attributes.
- **Every serializer change runs the full type generation pipeline** (typelizer → Zod → integration specs → swaggerize → SDK tests) and the OpenAPI diff is reviewed, because the regeneration is deterministic: a diff means the response really changed.
- **Cart selection is persisted on the cart line item, and completion copies only the selected lines.** The choice is durable state the client writes before checkout, not a flag applied at checkout: `cart/getCartInfo` returns a `choose` boolean per line beside a server-computed `chooseTotalQuantity`, and `cart/chooseCart` writes it as `{ choose, idSet }` — one bulk write over a set of line ids, not a per-line call. The settle page is reached as `?type=cart` and `order/cartSubmit` sends only settlement fields (address, coupon, points, delivery time), so **no request in the checkout path carries the chosen ids** — the server resolves the selection itself. The flag therefore belongs to the cart's line item and not the order's: 6.0 separates the two models and completion copies (`6.0-cart-order-split.md`, Key Decision 3), so an unselected cart line is never copied and the order never holds one. This confines the selection's reach to cart-side calculation.
- **A cart's money answers are computed over its selected lines, so the selection is an input to calculation and not a filter over it.** The client renders a minimum-order verdict the server derives from the chosen set: `cartHintHandle` compares the cart's money figure against the period minimum and only speaks when the chosen count is above zero (`miniprogram/pagesF/static/behaviors/cartBehavior.js:106-113`), and the caller passes `chooseTotalQuantity` (`miniprogram/pagesF/cart/cart.js:405`). A cart page and a settle page that disagree about the amount is the failure this prevents — the two read the same figure at different moments, so there is one calculation, scoped once.
- **Choosing between promotions is a shopper preference over a server-computed candidate list, not a typed code, so `carts/discount_codes` does not cover it.** The control appears only when a line has **more than one** candidate (`item.promotionList.length > 1`, `miniprogram/pagesF/static/template/cart-goods.wxml:17`), which a coupon entry would never require, and it opens a radio list of the server's own candidates with the current one pre-selected (`components/promotion/switch-promotion/switch-promotion.wxml`). The write carries both identities of the same candidate — `{ id: cartId, promotionId, promotionCode }`, where the code is read off the chosen entry in the list the server supplied (`cartBehavior.js:278-291`) — so the code is a second name for a candidate and never customer input; the cart has no code field at all. The list is per line and server-supplied (`cart.js:395`), each entry carrying `id`, `label` and `code`, beside a group-level `promotionDetail` describing the one currently applied (`cart.js:400-402`). Nothing in this is expressible today: Spree applies promotions by rule and has no notion of a candidate set for a line, let alone a remembered preference among them. This is a rule-engine addition — a preference the promotion engine honours — and the shape of the preference (per line, per group, or per cart) is part of the work, not an implementation detail.
- **The checkout page's aggregate already exists and it is the price preview; do not build a page-shaped endpoint beside it.** The settle page loads with one request per entry path — `calc/buyCalc` or `calc/cartCalc` (`miniprogram/pagesF/settlement/settlement.js:239,271`) — and reads **fifty-eight** page-level fields straight off that one response, including the payment methods (`payConfigV2VoList`), the coupon candidates and the coupons barred from this cart (`couponDetailList`, `banCouponDetailList`, `bigCouponId`), the points verdict (`integralTotal`, `integralNum`, `integralFlag`), the delivery promise (`deliveryTime`, `speedDelivery`), the invoice types (`invoiceType`, `invoiceSpecialType`), store-credit availability and its refusal reason (`balanceType`, `balanceReason`, `balanceNotPassword`), the discount lines (`minusList`) and the membership flags (`svipSite`, `svipUser`) — the full list is the whitelist at `settlement.js:445`. Addresses are the one thing outside it, and correctly so: they come from the address book, a customer resource the same component reads on other pages too (`components/addr/choose/choose.js:56`). So the recommendation below is not a new aggregate but an extension of the preview: one call that answers what the page needs, computed once, because every field in it is a verdict the calculation already had to reach.
- **The menu is a composite of catalogue, customer history, recommendation and marketing zones, so it is not a Store API resource.** A root menu node carries a category id **and** a `menuType` that selects one of three different fetch strategies for its children: `combo` and `guess` go to the combo-zone list, `market` goes to the market activity goods page, everything else goes to the ordinary children endpoint (`miniprogram/pagesA/make-order/make-order.js:566`). Several of those types are not catalogue nodes at all — `user` and `often` are computed from the customer's own purchase history, `guess` is a recommendation, `market` is an operator activity zone (`make-order.js:294,475`) — and second-level zone headers carry their own types (`all`, `recommend`, `common`, `market`, `make-order.wxml:47`). A node type that switches fetch strategy, over zones that mix the catalogue with CRM and merchandising, is a presentation contract this app owns; no storefront-neutral `menu` action can hold it. The catalogue half it does need — a category tree with children and counts — is the part worth adding to `categories`. The sort terms are not a new concept either: the two lists are the client's own constants (`make-order.js:27-63`), and `order_category/menuChildrenSortTermNew` is defined and never called, so the sorts actually sent are comprehensive, sales, price high-to-low and price low-to-high — plus the customer's own purchase count, which only means anything inside the history zone above. Of those, the two price orders already exist as `ascend_by_price` and `descend_by_price` on the product allowlist (`spree/core/app/models/spree/product.rb:370-376`) and comprehensive is the endpoint's default order; only a sales count and the per-customer purchase count need a sortable aggregate, and the second belongs to a zone that is not a catalogue node.

### Work that is not an API gap

Three groups in the 80 are deliberately excluded from this plan because they belong to another owner:

- **WeChat Pay (4 endpoints)** — already built in `spree/providers/wechat_pay`.
- **Mini-program login (3 endpoints)** — extends `spree_social_auth`.
- **Verification codes and the payment PIN (1 endpoint here, 8 in total)** — `6.1-phone-verification-and-payment-pin.md`.

## Migration Path

1. **Product and catalogue reads** — batch load, share metadata, purchase history, sale attributes, and the category tree with children and counts. Lowest risk and no schema change, and it unblocks the product pages.
2. **Cart** — the line selection and its bulk write, batch operations, the price-without-a-cart preview, the cart count. The preview is the single most-called new endpoint.
3. **Checkout and order reads** — the settlement-page fields on the price preview, then the order serializer additions (payment deadline, delivery, invoice, the confirm-receipt identifiers).
4. **Order writes** — customer cancellation, hide-from-list, balance payment at order level.
5. **Customer** — account closure, new-customer detection, profile fields.
6. **Wishlist grouping and gift card self-service**, the latter gated on `6.1-gift-card-purchase-and-transfer.md`.
7. Regenerate types, Zod, OpenAPI and SDK tests after each step; review the OpenAPI diff.

## Constraints on Current Work

- **Do not add a customer-visible write to the Store API without an explicit `resource_permitted_attributes` list** and a spec proving a foreign store's ID returns 404 rather than updating another tenant's record.
- **Do not add `id` to the product Ransack allowlist as a convenience.** If batch load is expressed as a filter, it must be scoped so it cannot enumerate another store's catalogue; a first-class `ids` parameter on a scoped collection is the safer shape.
- **Do not build a second password reset or a second login path** for the mini program. Reuse `password_resets` and extend `spree_social_auth`.
- **Do not give the Store API a bulk envelope** (a shape that returns per-item results for a batch of writes) — `6.0-admin-api.md` still has that as an open question, and a second dialect would be worse than the current one-line-per-request shape.
- **Do not model cart selection as two checkout modes.** The cart carries one selection state — a per-line tick, a bulk write over a set of line ids, a server-supplied chosen count — and no "check out everything" mode beside it; the client has no select-all control at all, only per-line ticks and a per-group bulk tick, so "check out all" is that state with every line ticked. The selection write is a bulk write but needs no per-item result envelope — the client reloads the cart afterwards rather than reading per-line outcomes (`miniprogram/pagesF/static/behaviors/cartBehavior.js:52-54`) — so the "no bulk envelope" constraint above is untouched.
- **Do not compute a cart's money over its whole line set and filter it afterwards.** The selection is an input to calculation (see Key Decisions), so a cart has one amount, produced once, and both the cart page and the settle page read it. Two code paths that reach the same figure by different routes will disagree on the next promotion change.

## Open Questions

All four questions are settled as of 2026-09-17 by reading the mini program at `miniprogram/`; every client path below is relative to it, and each ruling is in Key Decisions. The original questions are kept for the record.

1. ~~**How is "check out only the ticked lines" modelled?**~~ **Settled 2026-09-17: Option A — a `selected` flag on the cart line item — and the flag is the cart's, not the order's.** The client decides it, on four findings. The choice is durable cart state: `cart/getCartInfo` returns a `choose` boolean per line beside a server-computed `chooseTotalQuantity` (`pagesF/cart/cart.js:216,319,408`), and `cart/chooseCart` writes it in bulk over a set of line ids (`{ choose, idSet }`, `pagesF/static/api/cartApi.js:7-9`, `pagesF/cart/cart.js:588-605`). Checkout carries no id list at all: the settle page is opened as `?type=cart` with no ids (`pagesF/cart/cart.js:757-759`), `orderSubmit` builds its payload from `calcParams` plus order-level fields only (`pagesF/settlement/settlement.js:868-887`), and `calc/cartCalc` sends the same shape (`:271-279`) — the buy-now path is the one that names goods explicitly, through `calcGoodsList` (`:673-674`), which is exactly the difference between "these items" and "my ticked items". The client **repairs** the selection rather than merely reading it: when the server marks a chosen line disabled it calls `chooseCart` with `choose: false` for those ids and reloads (`pagesF/cart/cart.js:216-224`), which is behaviour a transient UI flag would not need. And the selection is not one of two modes — the cart has per-line ticks and a single bulk tick per combo group (`comboChooseCart` sends every line of the group, `:510-521`) with no global select-all control anywhere, so "check out everything" is this one state with every line ticked. Option B is out because there is exactly one cart per site (`getCartInfo` takes only `siteId`, `:209-214`) and the choice lives inside it as a per-line flag; Option C is out because the choice exists and is enforced long before checkout, not at it.

   **The scope of the change is smaller than the question assumed.** Its objection — that a `selected` boolean puts a UI concept in the data model and forces every promotion, tax and shipping rule to ignore unselected lines consistently — describes a platform where the cart *is* the order. In 6.0 they are separate models and completion copies (`6.0-cart-order-split.md`, Key Decision 3), so an unselected cart line is simply never copied (`workflows/spree/carts/complete.rb:308-316` iterates `cart.line_items`; the same scope filters it) and no order ever holds one. The selection's reach is therefore **cart-side calculation only**, which is where the client's own server already applies it.
2. ~~**Is the promo-selection endpoint worth building?**~~ **Settled 2026-09-17: yes, and it is the second option — the shopper chooses between automatic promotions.** The question asked whether `cart/changePromotion` is "apply my coupon" (already covered by `carts/discount_codes`) or "choose between two automatic promotions" (a rule-engine change). It is the second, and more sharply than the question supposed: the control is rendered only when a line has more than one candidate, it presents the server's list as a radio group with the current choice pre-selected, and the write names one entry of that list. The candidate set, the current choice and the labels are all server-side, so the work is not a preference column alone — the promotion engine has to be able to answer "which promotions could apply to this line, and which one does the shopper want", and re-price with the answer. Conflict risk is real and is why this is a decision rather than a detail.
3. ~~**Does the mini program need a page-level aggregate at all?**~~ **Settled 2026-09-17: it needs one, it already has one, and it is the price call — so extend the preview rather than build a page-shaped endpoint.** The settle page makes one request to load (`calc/buyCalc` or `calc/cartCalc`) and reads fifty-eight page-level fields off the response, covering payment methods, coupon candidates, points, the delivery promise, invoice types and store credit. Addresses come from the address book as a separate customer resource, which is the right split and stays. The recommendation is therefore narrowed: the aggregate is not a new endpoint but the set of verdicts the preview returns, kept in one computation precisely because the page reads one figure.
4. ~~**Is the menu-shaped category response a Spree feature or an app-level concern?**~~ **Settled 2026-09-17: an app-level concern, with the catalogue half belonging here.** A menu node's `menuType` chooses between three fetch strategies, and `user`, `often`, `guess` and `market` are customer history, recommendation and operator merchandising rather than catalogue nodes, so a storefront-neutral `menu` action would be modelling one app's page composition. What this plan takes is the part every storefront wants: a category tree carrying children and counts. The "sort-term concept that does not exist yet" is dropped — the client never asks the server for sort terms, and the four it sends are orderings over existing fields.
