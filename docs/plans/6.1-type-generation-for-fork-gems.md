## Summary

The fork's API surface is no longer only upstream's. Thirty-one store serializers live in the
extension gems — the membership wallet, the tier ladder, the scenario purchase, the points
account — and every one of them is reachable through the same `/api/v3/store` the mini program
calls. The type pipeline does not see any of them: `Typelizer` is configured with one directory,
`spree/api/app/serializers/spree/api/v3`, so the Store SDK has types for `Product` and `Order`
and nothing for `MembershipCard`. The client therefore hand-writes those shapes, and the two
drift apart exactly as the generated ones cannot — a field renamed in a serializer reaches the
client as a runtime surprise rather than a type error.

This closes that gap: the fork gems register their own serializer directories with Typelizer, the
generation runs in an application where every gem is loaded, and the types land in the SDKs the
client already imports.

## Key Decisions (do not deviate without discussion)

- **The store namespace is the API's own, wherever the serializer lives.** Core's store
  serializers are `Spree::Api::V3::XSerializer` and its admin ones `Spree::Api::V3::Admin::XSerializer`;
  the fork gems wrote `Spree::Api::V3::Store::XSerializer`, a third convention that the writer's
  name mapper turns into a `Store::X` type — a name no core type has, and one the client would
  have to import differently from every other shape. The gems' store serializers come back to the
  API's own namespace, so a type is `MembershipCard` beside `Product`. **Accepted cost:** 31 files
  renamed, plus every reference to them (`serializer_class`, the `Spree.api.*_serializer`
  dependency strings, specs) — mechanical, and the gem suites are the check.
- **The registration is one scan of the loaded engines, not nine announcements (ruled 2026-09-23).**
  A new initializer beside upstream's generator config asks `Rails::Engine.subclasses` which engines
  have an `app/serializers/spree/api/v3` directory and adds those to `Typelizer.config.dirs`. An
  application that does not load a gem reports nothing for it — which is what keeps `spree/api`'s
  own test app generating the core types alone — and a tenth fork gem is picked up without touching
  the file. **Accepted trade-off:** the registration is a discovery rule rather than a declaration,
  so a gem that means *not* to be codegen'd would have to say so.
- **The convention is the one upstream mostly follows: bare, not `Store::` (ruled 2026-09-23).**
  Core has ninety-seven serializers at `Spree::Api::V3::XSerializer` and four under
  `Spree::Api::V3::Store::`, and the four generate visibly worse names — `Store::Share` becomes
  `StoreShare` in the SDK, ambiguous beside the `StoreCredit` model type. The gems follow the
  ninety-seven.
- **Generation runs where every gem is loaded: the starter.** Typelizer *prunes* its output
  directory (`Typelizer::Writer#cleanup_output_dir` removes the directories of the interfaces it
  wrote), so running it from an application that lacks some gems would delete those gems' types
  rather than leave them. The starter (`server/`, the fork's own deployment shape) loads all of
  them, and the generated files are committed exactly as the core ones are.
- **The generated output is committed and CI typechecks it, as today.** No new CI step is needed:
  `pnpm typecheck` already runs over the packages that consume the types, and a serializer change
  that was not regenerated then fails there — the same protection core's serializers have.
- **The SDK's re-export list stays explicit (ruled 2026-09-23).** `packages/sdk/src/types/index.ts`
  names the generated types by hand, and the gem types join that list in the same change. A
  wildcard re-export would publish every type a serializer change happens to produce, and the
  package's surface is worth keeping deliberate. **Accepted cost:** one line per new type, which is
  exactly the moment a human should be looking at what the client is about to import.
- **The rename, not a mapper (ruled 2026-09-23).** A three-line name-mapper override would hide
  `Store::` at generation time and leave the third namespace in the code — two places to understand
  a name that should have one. The rename is mechanical and the gem suites verify it.
- **A wrapper script is what regenerates, and the hook calls it (ruled 2026-09-23).** The
  generation needs an application with every gem installed, which `spree/api`'s own test app is
  not — so `scripts/types/generate` runs it in the starter when one is present and refuses with a
  reason when it is not. The Lefthook hook's trigger widens to the gems' serializer directories and
  calls that script, so a gem serializer change regenerates the types the way a core one does.
  **Accepted cost:** one small edit to upstream's `lefthook.yml`.

## Design Details

### The registration

```ruby
# spree/api/config/initializers/typelizer_fork_gems.rb
Rails.application.config.after_initialize do
  next unless defined?(Typelizer)

  Typelizer.configure do |config|
    config.dirs |= Rails::Engine.subclasses.filter_map do |engine|
      path = engine.root.join('app/serializers/spree/api/v3')
      path if path.directory?
    end
  end
end
```

`configure` yields the same singleton the upstream initializer configures, and `|=` rather than
`<<` because `after_initialize` runs again on every boot.

The admin serializers need no equivalent decision: `spree/extensions/*/app/serializers/spree/api/v3/admin/`
already uses core's `Spree::Api::V3::Admin::` namespace and the admin writer's existing mapper
handles it.

### What the rename touches

- 31 serializer files across nine gems, moving from `module Store` to the bare namespace.
- The controllers that name them (`serializer_class`), the `Spree.api.*_serializer` keys in
  `spree/api/lib/spree/api/dependencies.rb` and the gems' own dependency registrations.
- Specs that reference a serializer class by name.

Nothing on the wire changes: the namespace is Ruby-side only, and the route, the payload and the
type name all stay what they are.

### The pipeline, end to end

1. `cd server && bundle exec rake typelizer:generate` — every gem's serializers are loaded, so all
   of them are emitted: `packages/sdk`, `packages/admin-sdk`, `packages/seller-sdk`.
2. `cd packages/sdk && pnpm generate:zod` — the Zod schemas follow the TS types.
3. The generated files are committed (`packages/*/src/types/generated/`, `packages/sdk/src/zod/generated/`),
   and `pnpm typecheck` in CI proves the packages still compile against them.

## Migration Path

1. **Rename the gems' store serializers** to `Spree::Api::V3::XSerializer`, updating every
   reference. The gem suites (and the core suite, which loads the membership specs' dummy) are the
   check.
2. **Register the directories** from each gem's engine.
3. **Generate in the starter** and commit the output; add the new type names to the SDK's
   re-export list (or make it a wildcard).
4. **Wire the hook** so a gem serializer change regenerates the types the way a core one does.
5. **Document the command** where the fork's own workflow lives, including the fact that it needs
   an application with every gem installed.

## Constraints on Current Work

- **A gem that adds or changes a serializer ships its regenerated types in the same change.** The
  rule that binds core serializers binds the gems' from step 3 on; the difference is only where
  the generator runs.
- **Never run the generator from `spree/api` once the gems are registered** unless that application
  loads them: it would prune their types. The core-only run stays valid only while the gem
  directories are unregistered, which ends with this plan.
- **No serializer keeps a `Store::` namespace.** A new one follows core's convention; the naming is
  what makes the type names uniform.
