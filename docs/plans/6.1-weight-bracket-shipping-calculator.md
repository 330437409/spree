## Summary

Spree ships six shipping calculators and none of them prices by weight bracket.
`FlatRate`'s weight preferences **suppress** a method outside a range; they do not
price within one, and they are deprecated in favour of `DeliveryMethodRule`.
`FlexiRate` counts items, `PerItem` counts items, `PriceSack` reads the item
total, `FlatPercentItemTotal` reads a percentage. That leaves the pricing model
most of the world outside the United States and the European Union actually uses
— **首重 + 续重**, a price for the first weight bracket plus a price for each
additional weight step — unexpressible without stacking one method per bracket
and hoping the boundaries line up.

This plan adds `Calculator::Shipping::WeightBracket`: a first bracket (its weight
ceiling and its price), an additional step (its weight and its price), and
ceiling rounding on the step, which is how carriers bill. Rates differ by
destination, and that is expressed by giving each `Spree::DeliveryZone` its own
delivery method with its own bracket — the zoning machinery already exists and
needs nothing new.

This is a general-purpose core addition, not a Cainiao one. It is what makes
`6.1-cainiao-logistics-provider.md` able to price a merchant's actual courier
contract instead of approximating it.

## Key Decisions (do not deviate without discussion)

- **Amounts are in the store's own weight unit, compared as raw numbers
  (2026-09-10).** `Spree::DeliveryMethodRules::WeightRule` records the house
  semantics: "Compares raw numbers in the store's implicit weight unit — the same
  semantics as variant weights themselves." `Stock::Package#weight` is
  `contents.sum(&:weight) + tare`, and nothing in the platform converts. A
  calculator that insisted on grams would silently misprice a store configured in
  pounds, which is the failure mode hardest to notice. It follows the platform,
  and the docs say plainly that the numbers mean the store's weight unit.
- **Rounding is ceiling, and it is the billing rule rather than a preference
  (2026-09-10).** A partial continued step is charged as a whole step, because
  that is what a courier does. Offering floor or round-half would let a merchant
  silently under-collect and would misdescribe their own contract.
- **The brackets are prices, not eligibility (2026-09-10).** The calculator does
  not carry a minimum or maximum weight. Bounds belong to
  `DeliveryMethodRule`s, which is the direction core already moved in — `FlatRate`'s
  weight preferences are deprecated for exactly that reason, and new code must
  not recreate them.
- **One bracket per method; zones carry the rest (2026-09-10).** A contract with
  一区/二区/三区 has a different bracket per destination zone, so the merchant
  creates one delivery method per zone, each pinned to its own
  `Spree::DeliveryZone` and carrying that zone's bracket. No nested preference,
  no new UI, and it matches how a merchant already describes their own contract
  to a courier.
- **Multi-rung first weights (多首重) are deferred, and the limitation is
  documented rather than hidden (2026-09-10).** Some contracts price 0–1kg,
  1–2kg and 2–3kg as separate rungs before the continued step begins, and
  Cainiao's own rate card models exactly that shape. A single first bracket
  reproduces a multi-rung contract **exactly when the early rungs step by the
  same amount as the continued price** — common, but not universal — and
  undercharges when they step by more. Modelling the rungs needs a structured
  list preference, which the dashboard's generic preference form does not render
  well. Until then a merchant on an uneven contract has a working escape hatch:
  one method per rung, each with its own `DeliveryMethodRule` weight bounds. The
  README names the limitation and the workaround.
- **No per-currency brackets in the first version (2026-09-10).**
  `Calculator::CurrencyAmounts` gives amount-based calculators a per-currency
  `amounts` hash, but a bracket is a *set* of amounts, and a nested per-currency
  bracket table is past what a preference form can express.
  `supports_currency?` therefore accepts the store's default currency only, so a
  foreign-currency cart is never quoted a number in the wrong currency — the
  method is simply not offered there, which is honest and visible.
- **It belongs in core (2026-09-10).** No credentials, no external service, and
  useful to every store that ships by weight — the same reasoning that puts
  `FlatRate` in core. A gem would fragment the calculator registry for no gain.

## Design Details

```ruby
module Spree
  module Calculator::Shipping
    # A first bracket and a continued step, priced per destination zone.
    class WeightBracket < ShippingCalculator
      preference :first_weight, :decimal, default: 0
      preference :first_price, :decimal, default: 0
      preference :additional_weight, :decimal, default: 0
      preference :additional_price, :decimal, default: 0

      def self.description
        Spree.t(:shipping_weight_bracket)
      end

      def compute_package(package)
        weight = package.weight.to_d
        return preferred_first_price.to_d unless continued_charging?(weight)

        preferred_first_price.to_d + steps_for(weight) * preferred_additional_price.to_d
      end
    end
  end
end
```

Behaviour:

| Condition | Result |
| --- | --- |
| `weight <= first_weight` | `first_price` |
| `additional_weight` is zero or negative | `first_price` — a bracket with no continued step charges once, and no division by zero is possible |
| `first_weight` is zero with a continued step | the whole weight is chargeable in steps, which is pure per-weight pricing and a legitimate configuration |
| `weight` is zero | `first_price` — see the zero-weight decision below |
| otherwise | `first_price + ceil((weight - first_weight) / additional_weight) * additional_price` |

`steps_for` uses `BigDecimal` throughout and never rounds below zero.

**Zero weight is charged the first bracket.** `Stock::Package#weight` is zero when
nothing in the package has a recorded weight, which is the state of a store
mid-setup. Refusing to quote would take the delivery method away from the
storefront with no explanation; quoting the first price is wrong but visible, and
a merchant who wants unweighed packages refused adds a
`DeliveryMethodRule` with a `minimum_weight`. The README says so. This matches
`FlatRate`, which also charges its amount for an unweighed package.

**Registration and the admin form.** The calculator is appended to the existing
registry in `spree/core/lib/spree/core/engine.rb`:

```ruby
Rails.application.config.spree.calculators.shipping_methods << Spree::Calculator::Shipping::WeightBracket
```

Nothing else is needed on the admin side, and this is the decisive reason the
pricing model belongs in a calculator rather than in a rate provider:
`GET /api/v3/admin/delivery_methods/calculators` already returns each
calculator's `serialized_preference_schema`, and the dashboard renders a
preference form generically. The four preferences appear in the delivery
method's pricing form with no dashboard work. A `DeliveryRateProvider` has no
preference schema at all and its pricing form is hidden by design, so the same
model implemented there would have needed a configuration surface invented for
it.

`Spree.t(:shipping_weight_bracket)` is added to the locales the dashboard ships,
because the picker reads `calculator_class.description`.

**Currency.** `supports_currency?` is overridden to accept the store's default
currency only, per the decision above. `Spree::ShippingCalculator` defaults it to
`true`, which is right for percentage and per-item math and wrong for a bracket
whose numbers are only meaningful in one currency.

## Migration Path

1. **Calculator** — the class, the registration line, the locale entries, and the
   `supports_currency?` override.
2. **Specs** — the boundary cases that matter: exactly at `first_weight`, one gram
   over, a partial step rounding up, a whole number of steps, a zero
   `additional_weight`, a zero `first_weight`, a zero-weight package, and a
   non-default currency being refused.
3. **Docs** — a developer doc covering the store weight unit, one method per
   zone, the multi-rung limitation and its one-method-per-rung workaround, and
   the zero-weight behaviour.

One PR, and it is independent of every other plan.

## Constraints on Current Work

- **Do not add weight conversion to this calculator.** Weight is raw numbers in
  the store's implicit unit, exactly as `WeightRule`, `FlatRate` and the variant
  columns already treat it. A conversion here that the rest of the platform does
  not share is worse than no conversion.
- **Do not add weight bounds as preferences.** Eligibility is a
  `DeliveryMethodRule`'s job; `FlatRate`'s weight preferences are deprecated
  precisely because bounds were conflated with pricing.
- **Do not change any existing calculator's behaviour while landing this.** The
  six shipped calculators and their specs are the guard.
- **Do not put a `DeliveryMethodService` row on a method priced by a calculator.**
  `Stock::Estimator#calculate_delivery_rates` calls
  `delivery_method.offers_service?(estimate)` for every provider, and an
  `Internal` estimate carries `carrier: nil, service_level: nil` — so a service
  row with a real courier matches nothing and removes the method from checkout
  silently. This is unrelated to the calculator but sits in the same code path
  and is the next trap a reader will walk into.
- **Ceiling is not configurable.** If a carrier ever bills by floor or half-up,
  that is a new calculator with a name that says so, not a preference added here.

## Open Questions

- **Multi-rung first weights (多首重).** The shape Cainiao's own rate card uses:
  a list of `{end_weight, price}` rungs, then a `continue_start_weight`,
  `continue_weight` and `continue_price`. Modelling it needs a structured
  preference — a `:array` or `:hash` — and a dashboard control that renders one.
  Deferred until a merchant with an uneven contract asks, with the
  one-method-per-rung workaround documented in the meantime.
- **Volumetric weight (体积重).** Chinese couriers commonly bill the greater of
  the actual weight and the volumetric weight — `length × width × height ÷ 6000`
  or `÷ 5000`, per carrier. The data already exists: `Spree::PackageType` holds
  carton dimensions and `Stock::Package#dimensions` returns the default package's
  box, so a `volumetric_divisor` preference charging
  `max(actual, volumetric)` is a small addition. **Not in the first version**, and
  named here because it is standard rather than exotic, and a merchant will hit
  it.
- **Per-currency brackets.** The `CurrencyAmounts` pattern applied to a set of
  amounts rather than one. Waits on a preference form that can render a nested
  table.
- **Whether the calculator should also serve freight.** `DeliveryRateProvider::Freight`
  handles the quoted-after-review case; a forwarder's step pricing might fit here
  instead. Out of scope, noted so the two do not drift into each other.
