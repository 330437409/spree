## Summary

When a customer enters the storefront to buy, the system routes them to the
seller that serves the customer's location. A seller ("供应商" in the
operator's vocabulary, `Spree::Seller` in core) declares a **service area** —
an administrative-division node at any level (province / city / district /
township) bound to one of its **warehouses** (`Spree::StockLocation`), plus an
optional polygon geofence that further constrains it. The customer's location
is resolved to an administrative path by reverse geocoding, the deepest
covering warehouse wins, and the result is a structured `Decision` (not a bare
seller). A customer in no seller's area falls back to the national store
bound to the "全国" root; beyond that, "no service" is a defined, monitored
state, never a silent pick.

This is a China-market plugin: the four-level administrative-division tree
(省 / 市 / 区县 / 乡镇街道办, which now belongs to
`6.1-administrative-division-gem.md`), reverse-geocode providers (Tencent LBS
and Amap), polygon geofences, and the lookups a client calls to find out which
seller serves it. The production client is a WeChat mini-program outside this
repository; a restored copy lives in `miniprogram/` here, and it is what every
behavioural claim in this plan is checked against. It ships as an extension gem
under `spree/extensions/`, on a small core addition, and is never proposed to
the official Spree codebase.

**Two halves, and only the second is a scope.** Discovery answers *which seller
serves this coordinate* — once, when the client has no seller yet. Scope answers
*which seller this request is about* — on every call, from an identifier the
client already sends. The v1.2 draft specified the first and left the second to
`fork-decisions.md`; **this revision lands both**, because the second is what the
rest of the set reads and the architecture plan promoted this plan to the
keystone on the strength of it.

The design centres on one coordinate system (GCJ-02) and four domain
invariants so that a given coordinate always resolves to the same seller. The
two geocoding directions are deliberately named apart: **warehouse address
geocoding** (forward — an address becomes coordinates) and **buyer reverse
geocoding** (coordinates become an administrative path).

## Domain Invariants

These are the contracts the whole design hangs off. They are not optional.

1. **Every sellable seller has at least one active warehouse with a
   service-area binding.** A seller with no bound, active warehouse cannot be
   routed to.

2. **An administrative node has at most one active service-area binding.**
   Exactly one active warehouse may be bound to a node. This is a database
   constraint, not a review-time hope — without it, the "deepest binding wins"
   query can return two candidates at the same depth and the routing becomes
   database-order dependent.

3. **For the same coordinate and unchanged routing data, resolution is
   deterministic.** A resolution returns the same seller every time. Invariant
   2 is what makes this hold; a final `id` tiebreak on the query is the
   backstop.

4. **Service-area routing selects a Seller; fulfillment routing independently
   selects a fulfillment `StockLocation`.** The warehouse returned by this
   feature is the *binding* warehouse — the one whose node covers the customer
   — and is not necessarily where the order is later packed or shipped from.
   `6.0-order-routing.md` owns the second decision and must stay decoupled
   from this one.

The routing candidate set is therefore exactly:

```text
StockLocation.active
AND seller.sellable
AND administrative_division_id IS NOT NULL
```

An inactive warehouse, a suspended or on-holiday seller, and an unbound
warehouse are each excluded by that expression — and none of them deletes the
binding: `administrative_division_id` and the polygon stay on the row as
history. Deactivating a warehouse is what releases its node for another seller,
because the index counts only `active` (and non-deleted) rows — on PostgreSQL and
SQLite by predicate, and on MySQL by the service, since MySQL has no partial
indexes.

## Key Decisions (do not deviate without discussion)

1. **The seller's location for routing is its warehouse's address, geocoded.**
   A seller has no coordinate of its own in this design; its routable position
   is `StockLocation#address` turned into `latitude` / `longitude`. Core already
   lets a seller manage multiple warehouses and their addresses — the plugin
   adds coordinates and a binding, never a second address concept. **The client
   does carry a seller-level map point** (`siteCenterLocation` → `site.lng` /
   `site.lat`, `static/state/siteState.js:51,69-75`), used as the map centre
   when the buyer's point falls outside the seller — so the payload this plan
   serves either maps it to the binding warehouse's geocoded pair or the model
   gains a seller-level centre; it is a display point, never a routing input.

2. **The binding lives on the warehouse, one node per warehouse.**
   `Spree::StockLocation` gains `administrative_division_id` (any level). A
   seller serving two non-adjacent districts must have a warehouse in each.
   "Every seller must bind a service area" means a sellable seller has at
   least one active warehouse with a bound node.

3. **Binding any level covers the whole subtree; the deepest binding wins.**
   Binding a city covers every district and township beneath it. When several
   warehouses cover a point, the one bound deepest wins — which is exactly the
   agency hierarchy: a township agent beats its district agent, which beats
   the city agent. The national store is a seller bound to the root node, so
   the fallback is the same rule, not a special case.

4. **One active service-area binding per administrative node — mandatory.**
   A partial unique index enforces it: at most one active, bound warehouse per
   node. Routing is therefore unambiguous at every depth. The operator still
   reviews sellers; the index is the machine guarantee that no two warehouses
   can silently share a node.

5. **A polygon geofence is a hard AND constraint, and a miss falls back up the
   tree.** Effective coverage of a warehouse is `administrative subtree ∩
   polygon`. If the deepest warehouse's polygon excludes the point, the next
   covering warehouse (the parent-level agent) is tried, and so on up to the
   root. If the root's binding also fails (or no root binding exists), the
   result is "no service" — not a silent fallback to some other seller.

6. **Canonical coordinate system is GCJ-02.** WeChat `wx.getLocation`, Tencent
   LBS and Amap all natively speak GCJ-02, so it is the internal representation
   for reverse geocoding, polygon tests, and distance. All inbound coordinates
   are normalised to GCJ-02 through one `CoordinateNormalizer`. **The client
   does not declare a source** — it has no such field: `type: "gcj02"` is a
   literal at each of the nine `wx.getLocation` call sites
   (`static/utils/report.js:71,294`, `static/behaviors/locationComBehavior.js:98`
   and six more), and every coordinate it sends is `{lng, lat}`
   (`report.js:299-304`). So GCJ-02 is what the *platform* guarantees, the
   `coordinate_system` parameter is **our contract for clients that are not the
   mini-program** (H5, an operator's own tool), and it defaults to `gcj02`
   rather than being required.

7. **Administrative divisions are local, versioned reference data with
   National Bureau of Statistics codes.** The four-level tree (province /
   city / district / township) plus the "全国" root is stored locally and
   carries a `dataset_version` and `source`; province/city/district use
   GB/T 2260 codes, townships use the bureau's township codes, the root is
   `CN`.

8. **Reverse geocoding is provider-pluggable, store-configured, with a primary
   and a fallback.** Tencent LBS and Amap adapters ship; each store configures
   a primary provider (and its API key) and an optional fallback. On primary
   failure the fallback is tried; a stale cache hit is served before failing
   the request. Results — including "cannot resolve" negatives — are cached by
   geohash, keyed with the provider, coordinate system and dataset version.

   **Amended 2026-09-19: the first version ships the Tencent LBS adapter only.**
   The seam, the store configuration and the provider-keyed cache are exactly as
   written — Amap is deferred, not designed away, and its arrival is another
   adapter plus its mapping file rather than a change to `Resolve`. The
   fallback path stays in the code and stays configured; in the first version it
   has no second provider to try, which is a state the code already handles.
   The reason is operational rather than technical: the API key and its quota
   are the operator's resource, and a second vendor earns its place the day
   someone holds a key for it. Open Question 3 narrows with it.

9. **Vendor→bureau code mapping is a data asset, separate from the adapter.**
   An adapter turns a vendor HTTP response into a provider DTO; an
   `AdministrativeCodeMapper` (driven by data files, one per vendor) maps the
   vendor's codes to bureau codes. Mapping is never improvised in code, and
   swapping providers cannot corrupt stored bindings.

10. **Polygons are GeoJSON, validated on write, tested with RGeo in Ruby.**
    No PostGIS: Spree supports PostgreSQL, MySQL and SQLite. A polygon stores
    its bounding box beside it for a cheap pre-check, is validated (closed,
    non-self-intersecting, finite, in-range) with its ring winding
    **canonicalised rather than rejected**, and its parsed geometry is memoised
    per request.

11. **Routing returns a `SellerRouting::Decision`, not a bare seller.** The
    decision carries the seller, the binding warehouse, the matched division,
    the match depth/type, the polygon result and the distance; the API
    serializer maps it to JSON. The service never knows about HTTP.

12. **Spherical distance is display-only, and in this client it is a tracking
    value rather than a discovery one.** Matching is decided entirely by binding
    level and polygon. Distance is computed with the `geocoder` gem that is
    already a core dependency and shown to the customer — and the plan states
    where, because the draft overstated it: the mini program's only distance
    copy is "距离您" on the **order-tracking map** while an order is in the
    `sending` state, and the value arrives with the order
    (`pagesF/components/order/order-map/order-map.wxml:8-10`,
    `order-map.js:186-192`). Nothing in the location, address or seller flows
    shows a distance today, so the `Decision`'s `distance_km` is served for a
    client that will use it rather than one that already does.

13. **The plugin is an extension gem in `spree/extensions/`, never in core or
    `spree/providers`.** Placement ruled 2026-09-17 (`fork-decisions.md`). The gem
    extends `Spree::StockLocation` and adds its own models from the outside,
    and is never proposed to `upstream/spree`.

14. **The `StockLocation` geocoding columns are a shared contract.**
    `latitude`, `longitude`, `geocoded_at`, `geocode_provider` and
    `geocode_status` are one StockLocation geocoding contract. Two extensions
    must never migrate the same names separately: whichever of core,
    `6.0-order-routing.md` or this plugin lands them first owns the migration,
    and the others consume it. Names are not to be duplicated or renamed.

15. **`dataset_version` is an immutable dataset release id, not a year-month.**
    Values look like `nbs-2026-09-01`, so a mid-month correction is a new
    release rather than a silent change inside one version — the cache key and
    the code-mapping files then always name the same dataset.

16. **Forward and reverse geocoding are named apart, never both "geocoding".**
    Warehouse address geocoding (forward) turns an address into coordinates;
    buyer reverse geocoding turns coordinates into an administrative path.
    They have different jobs, providers and failure modes.

17. **The resolved seller is request scope, and this plan lands it** (ruled
    2026-09-17, `fork-decisions.md`; this is the second of the five amendments the
    architecture plan lists). The endpoint below is only the discovery half —
    *which seller serves this coordinate*. The other half is the boundary: a
    seller is resolved **once per request** and read from there, the way
    `Spree::Current.store` is read, with `resolve_seller` feeding it rather than
    standing in for it. The input is the `siteId` the client already sends on
    every request and rebinds after a lookup; the value lands in
    `Spree::Current.seller`, beside `store` and `channel`, so the seller and the
    pricing contexts' channel are two members of **one** scope rather than two
    mechanisms (`fork-decisions.md`, the pricing ruling of 2026-09-18). Everything in
    this set reads the seller from here and nothing resolves it again.

18. **The core-facing pieces land in core, and the gem ships only its own
    models** (the third amendment, reconciled). The request-scope attribute and
    its boundary concern, and the `StockLocation` geocoding columns with their
    forward-geocoding job, are additions to core — the first because a gem may
    not add an attribute to a core class, the second because the marketplace's
    own `seller_id` on `spree_stock_locations` went through a core migration
    rather than a gem's. What the gem owns is everything above and around them:
    the binding, the polygon and its validator, the reverse geocoders, the code
    mapping, the decision and the endpoint. Gem-owned classes live in the gem's
    own namespace, not inside core's: `Spree::SellerRouting::Locate` rather than
    `Spree::Sellers::Locate`, which would sit inside a namespace core already
    uses, and a feature-prefixed validator rather than one wearing core's
    `StockLocation*` name. **Amended 2026-09-19:** the polygon, its validator and
    the write-time normalisation are the exception, and they are in core —
    a validator attaches to a core model, which a gem may not reopen, so it
    belongs with the column it protects. The names stay the gem's, so the
    namespace is shared rather than duplicated.

19. **The binding is the coverage source of truth for discovery, and
    `Spree::DeliveryZone` keeps its upstream meaning — the two are not bridged**
    (ruled 2026-09-18, the plan's Open Question 5). A zone answers *may this
    delivery method serve this address*, matches country, state or postal code
    (`delivery_zone_member.rb:5`), and is authored in the delivery profile; the
    binding here answers *which seller serves this point*, matches a division
    subtree and a polygon, and is authored in the stock-location form. They are
    two questions, not two copies of one, and **nothing derives one from the
    other**: a bridge would have to express a district-or-deeper binding through
    member types that stop at the state, so it would either lose the precision
    the binding exists for or require a new member type in an upstream model.
    This deployment authors no zone for coverage at all — the client carries no
    postal codes and delivery is instant and local — so a merchant configures
    coverage once, here, and a zone remains available to a merchant who prices a
    shipping method by region. The exemption from `6.0-delivery-zones.md:128` is
    unchanged, and the division gem's "no third geographic-eligibility
    mechanism" constraint is untouched because this is not an eligibility
    mechanism: it is seller discovery.

20. **The binding and its geocoding columns stay on `spree_stock_locations`,
    and Decision 14's shared contract is kept rather than replaced** (ruled
    2026-09-18, the plan's Open Question 7). Upstream's `6.0-order-routing.md`
    mentions `latitude`/`longitude` only inside its own open question, deferred
    to phase two, and for a different consumer (ranking candidate locations for
    allocation rather than locating a shop a buyer can find) — and
    **`spree_stock_locations` carries neither column today**, while the reusable
    geocoding primitive that does ship is `Spree::Address`'s columns and
    `Spree::Addresses::GeocodeAddressJob`. So: if upstream lands the two columns
    first, this plan consumes that migration and adds only its own
    (`administrative_division_id`, `polygon`, `polygon_bbox`, `geocoded_at`,
    `geocode_provider`, `geocode_status`); if this plan lands first, they are its
    migration and upstream's rule consumes it. **The two consumers read the same
    fact** — where the location is — so the "two meanings" risk is a naming risk,
    not a semantic one, and if a future upstream point genuinely differs from the
    shop's public point, the answer is a second suite of columns on the anchor
    that owns the service area, not a rename of these.

21. **Two tiers, and the campaign tier stays excluded with the CMS bucket**
    (ruled 2026-09-18, the plan's Open Question 8). The client resolves delivery
    area as shop → special → seller, but a **special is inside the decoration
    bucket the architecture plan excludes** (`content · pages`, graded C), and
    nothing in this set claims it. When it returns it needs no new area concept:
    a special belongs to one seller and is delivered by a set of its shops, so
    its coverage is the **union of those shops' polygons — derived, never
    stored** — and the only new fact would be the campaign-to-warehouse
    membership, which is merchandising rather than geography. Until then the two
    address checks that name it answer from the seller tier: `address/checkShop`
    checks the shop's own coverage, and `address/checkSpecial` checks the
    seller's, which is a superset of any zone the excluded feature would have
    defined.

22. **The gem is `spree_service_areas`** (ruled 2026-09-18, the plan's Open
    Question 1), at `spree/extensions/spree_service_areas/`. It describes what
    the gem owns rather than one of its consumers, matches the naming of the
    providers beside it, and leaves `spree_delivery*` free for the delivery work
    the local-delivery plan may want later.

23. **Coverage outside China is a country list, designed rather than built**
    (ruled 2026-09-19). The binding answers *which seller serves this point* by
    naming a node of the Chinese tree, which suits a shop delivering a few
    kilometres: the node is precise, a polygon narrows it, and the distance is
    real. A seller shipping from abroad has no such shape — its coverage is the
    countries it sends to — so the extension is a second form of the same fact on
    the same row: a warehouse's coverage is its node and polygon **or** the
    countries it serves, defaulting to the warehouse's own `country_code`, which
    the table already carries. Routing needs nothing new for it: the point is
    placed the same way, a point outside the tree resolves to its country rather
    than to nothing, and the match reports `match_type: 'country'` — a value the
    decision already has.

    **Not built, because nobody needs it yet**: this client is China-domestic, and
    neither the mini program nor any plan beside this one carries a cross-border
    flow. **The store's `Spree::Market` is not this.** A market is the *store's*
    region — which countries the store sells into, with its currency, tax and
    return window — and nothing links a seller to a market; upstream records that
    a market-scoped assortment waits for its own design
    (`catalog_assignment.rb`). Gating which sellers a customer sees on a market
    would make one concept answer two questions, in the wrong plan's hands.

## Design Details

### Architecture

```text
Client (WeChat mini-program / H5)
        │  lat/lng + coordinate_system
        ▼
Store API  resolve_seller
        │
        ▼
CoordinateNormalizer ──► canonical GCJ-02
        │
        ▼
ReverseGeocode::Resolve ──► cache (geohash) ──► Tencent / Amap
        │                                            (primary → fallback)
        ▼
Administrative path (bureau codes)
        │
        ▼
SellerRouting::Locate ──► deterministic deepest-match + polygon
        │
        ▼
SellerRouting::Decision ──► API serializer ──► JSON
```

The two routing layers are deliberately separate: this feature resolves a
*Seller* from a customer's location; `6.0-order-routing.md` later resolves a
*fulfillment location* from that seller's inventory. The binding warehouse is
returned for display and observability only.

### Seller scope at the request boundary

Discovery and scope are two questions with two inputs, and this plan answers
both:

```ruby
# Discovery — once, when the client has no seller yet
GET /api/v3/store/location/resolve_seller?latitude=&longitude=

# Scope — on every request, read like Current.store
Spree::Current.seller   # from the request's siteId at the boundary (core)
Spree::Current.channel  # the pricing contexts' channel, resolved in the same place
```

- **The seller arrives by header**, the shape core already ships twice: a
  concern on the Store branch's two anchors (`Store::BaseController` and
  `Store::ResourceController` — parallel chains, so a concern on one is not on
  the other) reads the header once and writes the attribute. The precedent is
  `ChannelResolution` (`spree/api/app/controllers/concerns/spree/api/v3/channel_resolution.rb`),
  which resolves the channel from the key, then the `X-Spree-Channel` header,
  then the store default, and writes `Spree::Current.channel`. The Seller branch's
  `SellerContext` already names the seller header `X-Spree-Seller-Id`; this plan
  reuses that name rather than inventing a second one, and the client's `siteId`
  maps to it in the client — one line of the rewrite, not a second contract.
- **It lands in core, not in the gem** (Decision 18): one attribute in
  `Spree::Current` and one new concern included by two anchors. A gem adding an
  attribute to a core class is the decoration the architecture plan forbids, and
  the capability is generic — every request in this application is seller-scoped.
- **A missing seller is an error where one is required**, never a default: the
  failure this plan exists to prevent is a request priced and allocated from the
  wrong seller.
- **The channel's half already exists, and this plan does not rebuild it.** The
  pricing contexts' channel is what `ChannelResolution` already resolves; the
  pricing plan reads it and adds nothing. What this plan adds is the seller, the
  second member of the same scope.

### AdministrativeDivision

**The tree has moved (2026-09-18).** It is specified, owned and shipped by `6.1-administrative-division-gem.md`, which keeps the table below and adds `first_pinyin` and `pinyin` — the client's picker sorts by the former and builds its A–Z anchors from it. What stays here is everything above the tree: the binding columns, the polygon, geocoding and `resolve_seller`. The table below is kept as the record of what this plan binds to and reads.

`Spree::AdministrativeDivision` — global reference data (no `store_id`, like
`Spree::Country`/`Spree::State`). The `adm_` prefix travels with the model into
`spree_administrative_divisions`; if that gem answers without ids, the prefix is
dropped there rather than left dangling here.

| Column | Type | Notes |
|---|---|---|
| `parent_id` | bigint, nullable | nil on the "全国" root. **Corrected 2026-09-18**: the table said `uuid`, which no table in this repository has — the primary keys are bigint throughout, and a uuid foreign key would have nothing to point at. The gem ships bigint |
| `level` | string | `country` \| `province` \| `city` \| `district` \| `township` |
| `depth` | integer | 0..4, for deepest-match ordering |
| `code` | string, unique | bureau code; 6 digits province/city/district, 9 digits township, `CN` for root |
| `name` | string | |
| `dataset_version` | string | immutable release id, e.g. `nbs-2026-09-01`; a new value per import |
| `source` | string | provenance (e.g. `nbs-2026`) |
| `source_updated_at` | datetime, nullable | last update in the source dataset |

`depth` is denormalised because "deepest binding wins" needs an orderable,
indexed value. The tree is five levels deep, so the ancestor chain is a
fixed-size walk, not a recursive query. `UNIQUE(code)` holds including the
`CN` root.

### StockLocation extension + geocoding

**These columns land in core, and the migration is core's** (Decision 18). They
are added to `spree_stock_locations`, an upstream table, and the fork's own
precedent for that is a core migration — `seller_id` on the same table arrived
that way (`spree/core/db/migrate/20260820000001_add_seller_business_identity_and_stock_locations.rb:8`)
— not a gem migration into a core table, which is what the v1.2 draft proposed
and what the architecture plan's extension boundary forbids. The gem consumes
them.

| Column | Type | Notes |
|---|---|---|
| `latitude` / `longitude` | decimal | geocoded from the address columns |
| `administrative_division_id` | bigint, nullable | the warehouse's service-area node. **Corrected 2026-09-19** from `uuid`, as the division table's own `parent_id` was: every table here has a bigint primary key, so a uuid foreign key would point at nothing |
| `polygon` | json | GeoJSON polygon, GCJ-02, nullable |
| `polygon_bbox` | json | `{ min_lat, max_lat, min_lng, max_lng }`, GCJ-02 |
| `geocoded_at` | datetime, nullable | |
| `geocode_provider` | string, nullable | which provider produced the coordinates |
| `geocode_status` | string | `pending` \| `success` \| `failed` — so ops can see *why* a warehouse has no coordinates |

**Field ownership.** The five geocoding columns (`latitude`, `longitude`,
`geocoded_at`, `geocode_provider`, `geocode_status`) are one shared
StockLocation geocoding contract rather than this plugin's private columns —
see Decision 14.

`belongs_to :administrative_division, optional: true`. A partial unique index
enforces invariant 2:

```sql
-- PostgreSQL and SQLite: a partial unique index
CREATE UNIQUE INDEX index_stock_locations_on_active_service_area
ON spree_stock_locations (administrative_division_id)
WHERE active = TRUE AND deleted_at IS NULL
  AND administrative_division_id IS NOT NULL;
```

**Two corrections the v1.2 draft needed, both of the kind that fail silently.**
`deleted_at IS NULL` belongs in the predicate because `Spree::StockLocation` is
paranoid (`acts_as_paranoid`, `stock_location.rb:20`): a soft-deleted row that
never flipped `active` would otherwise keep its node claimed forever, invisible
to the candidate query and impossible to rebind. Every partial index this
repository already ships carries the guard. And **MySQL does not support partial
indexes at all**, which matters because the plan argues portability as the reason
to skip PostGIS. **Amended 2026-09-19, after the MySQL lane disproved what this
paragraph used to claim.** The first migration took the plain unique index core's
API-key migration takes, and this plan recorded the cost as "the rule degrades to
one binding per node, and the active-only half is the service's" — which was
wrong in the direction nobody checked: a plain index is *stricter* than the rule,
not weaker, so a warehouse could not be rebound to a node its own retired row
still held, and creating the second binding raised a database error rather than a
validation one. MySQL now reaches the same predicate the other two engines get
from a partial index, through a stored generated column that holds the node only
while the row is an active, undeleted binding. **All three engines mean the same
thing by the index**, and the guarantee is still stated per engine rather than
assumed.

**Binding lifecycle.** A binding is never deleted when a seller or warehouse is
retired — `administrative_division_id` and the polygon stay on the row as
history. What changes is eligibility: the candidate set above excludes an
inactive warehouse, a suspended or on-holiday seller and an unbound warehouse
alike. Because the partial unique index counts only `active` (and non-deleted)
rows, deactivating a warehouse is also what releases its node for a different
seller; binding a node still held by an active warehouse is refused, and the
admin form surfaces that as a validation error rather than a database error. On
every engine the index expresses the `active` half — MySQL through the generated
column above — and the validation is what makes the refusal readable rather than
a database error.

**Warehouse address geocoding (forward)** runs in
`Spree::StockLocations::ForwardGeocodeJob`, async on
address-field change. It is **debounced** — a save that touches several address
columns enqueues at most one job per location (guarded by a per-location
dedup, not one job per field) — uses `discard_on ActiveJob::DeserializationError`,
and retries with backoff — `Spree::BaseJob` already gives the last two. It calls
`Geocoder.coordinates(location.address.geocoder_address)` and writes the pair
plus `geocoded_at`, `geocode_provider` and `geocode_status`. Two naming
corrections the draft needed: `geocoder_address` is `Spree::Address`'s method,
reachable here through `StockLocation#address` — not a `StockLocation` method —
and the job belongs beside the columns in core (Decision 18), mirroring
`Spree::Addresses::GeocodeAddressJob`.

### Coordinate system + normalization

Canonical: **GCJ-02**. A single `Spree::CoordinateNormalizer` is the only place
coordinates are converted:

```ruby
Spree::CoordinateNormalizer.normalize(latitude:, longitude:, source:) # => [lat, lng] in GCJ-02
```

`source` ∈ `gcj02` (identity), `wgs84` (WGS-84 → GCJ-02), and any provider that
later joins. The normalizer runs **before** reverse geocoding, polygon tests
and distance, so every downstream consumer works in one system. No consumer
guesses a coordinate system.

### Polygon model + validation

`polygon` is a GeoJSON polygon (an array of linear rings) in GCJ-02.
**Where this landed, and why it moved (2026-09-19).** The validator, the geometry it needs and the write-time normalisation are **in core**, beside the column they protect, rather than in `spree_service_areas` as Decision 18 said. The reason is mechanical: a validator has to be attached to `Spree::StockLocation`, which is a core model, and a gem may not reopen one — this fork's own extension (`spree_crm`) ships no decorators at all, and the architecture plan's boundary forbids it. The classes keep the plan's feature-prefixed names (`Spree::SellerRouting::Polygon`, `Spree::SellerRouting::PolygonValidator`) so the gem can reopen the same namespace for `Locate`, `Decision` and the endpoint without a second concept.

**The geometry is hand-rolled rather than RGeo's (2026-09-19).** The plan chose in-memory RGeo for portability; the same portability is reached without adding a dependency to core: the shapes are hand-drawn and small, so self-intersection is a segment-crossing test and containment is a ray cast, both of which are standard arithmetic. `rgeo` remains an option for the gem if the routing slice needs more geometry than this — but core does not carry it for one column's validation.

`Spree::SellerRouting::PolygonValidator` refuses, on write:

- fewer than 4 points, or a ring that is not closed;
- self-intersection or otherwise invalid topology;
- `NaN`, non-finite values, or out-of-range latitude/longitude.

Ring winding is **canonicalised, not rejected**: the validator normalises
orientation on write and refuses only genuinely unusable geometry, so a map
editor — or a newer version of one — cannot fail an operator's polygon over a
ring orientation nobody chose.

`polygon_bbox` is recomputed on every polygon write. At match time a
`bounding_box_contains?` pre-check runs before the RGeo `contains?`, and the
parsed geometry is memoised per request so a polygon is parsed once, not per
candidate. RGeo is used in-memory (no PostGIS), keeping the plugin portable
across PostgreSQL, MySQL and SQLite.

### Reverse-geocode provider + code mapping

```ruby
module Spree
  module ReverseGeocode
    class Provider
      # @return [Spree::ReverseGeocode::Result] provider DTO with raw codes
      def reverse_geocode(latitude:, longitude:)
        raise NotImplementedError
      end
    end
  end
end
```

Three collaborators, never one fat class:

- **Provider** (`Tencent` — the one that ships; `Amap` when a key for it exists,
  see Decision 8) — HTTP call → provider DTO (raw vendor codes).
- **AdministrativeCodeMapper** (`TencentMapper`, `AmapMapper`) — data-file-driven
  vendor code → bureau code, keyed by `dataset_version`.
- **Normalizer** — provider DTO + mapped bureau codes → canonical path hash
  `{ country:, province:, city:, district:, township: }`.

Mapping data lives in `spree_administrative_divisions`' `data/administrative/{tencent,amap}/`
as versioned files, not in Ruby — the datasets travel with the tree, and this gem
ships the mapper that reads them. `ReverseGeocode::Resolve` orchestrates: geohash
key → cache lookup → primary provider → fallback provider → normalise → cache
(including negatives). A store configures
`preferred_reverse_geocode_provider`, `preferred_reverse_geocode_fallback_provider`
and per-provider API keys.

### Cache

`Spree::ReverseGeocodeCache` rows are keyed by a composite of:

```text
provider + coordinate_system + dataset_version + geohash
```

so switching provider, changing coordinate systems or re-importing the
division dataset (a `dataset_version` bump) never reuses stale results.
`geohash` precision ~7 (≈150 m × 150 m). The cache stores **negative results**
too — a coordinate that resolves to no township is cached so edge areas do not
hammer the provider. TTL defaults to 30 days and is configurable; a
`dataset_version` bump invalidates everything regardless of TTL.

When the primary provider fails: try the fallback; if both fail and a cache
hit exists (even stale), serve it and flag `stale: true`; only when there is
no cached result does the request fail.

### Routing — deterministic algorithm + Decision

`Spree::SellerRouting::Locate` is the single service, in the gem's own namespace
rather than inside core's `Spree::Sellers::`. It returns a
`Spree::SellerRouting::Decision` value object:

```ruby
Spree::SellerRouting::Decision.new(
  seller:,                 # Spree::Seller, nil when no match
  stock_location:,         # binding warehouse, nil when no match
  division:,               # matched AdministrativeDivision, nil when no match
  depth:,                  # Integer, nil when no match
  match_type:,             # 'township'|'district'|'city'|'province'|'country'|nil
  polygon_result:,         # 'matched'|'not_required'|nil
  distance_km:             # Float, nil when no match
)
```

Algorithm:

```text
resolve(lat, lng, source):
  lat, lng = CoordinateNormalizer.normalize(lat, lng, source)
  path = ReverseGeocode::Resolve.call(lat, lng)          # bureau codes, cached
  chain = [country, province, city, district, township]  # skipping absent levels
  candidates = StockLocation.active
                             .joins(:administrative_division)
                             .where(administrative_division_id: chain.ids)
                             .where(seller: sellable_sellers)
                             .order(depth: :desc, id: :asc)   # id: deterministic backstop
  for warehouse in candidates:
      if warehouse.polygon.present? &&
         !warehouse.bounding_box_contains?(lat, lng)      # cheap pre-check
         next
      if warehouse.polygon.present? &&
         !point_in_polygon?(lat, lng, warehouse.polygon)  # RGeo, memoised
         next
      return Decision.new(seller: warehouse.seller, ...)  # hit
  return Decision.new(seller: nil, ...)                   # no service
```

Coverage-as-subtree needs no recursive query: the point is already resolved to
its leaf, and a warehouse covers it exactly when its bound node is on that
leaf's ancestor chain — a membership test over ≤5 nodes expressed as one `IN`.

### Root / national seller

The national store is a seller whose warehouse is bound to the `country` root
node (`CN`). Invariant 2 guarantees at most one such binding, so the fallback
is unambiguous. The `chain` already contains the root, so no separate
`root_seller` variable exists — if the root binding passes its polygon test
(or has no polygon), it is selected like any other node. If the root binding
is absent or its polygon excludes the point, the result is a `Decision` with
`seller: nil` ("no service"), a monitored state the client renders in its own
words rather than a silently chosen seller. **The client's states are three, and
the plan does not paraphrase them**: `openStatusNew === null` with 当前城市未开通服务
and 您定位的位置{城市}超出…的服务范围 (`pagesF/address/shipping/shipping.wxml:150`,
`pagesB/location/not-open/not-open.wxml:4,9`); the address-outside-range state
with 当前地址超出配送范围 (`shipping.wxml:141-145`); and the campaign-scoped
超活动范围 (`pagesC/special/special.wxml:19`). All three read the same
`matched: false`, and which copy a surface shows is the client's business.

### Outside China (designed, deliberately unbuilt)

Decision 23. What a foreign seller would add, so that whoever builds it starts
from the shape rather than from the question:

- **The row**: `stock_locations` gains a country list (a JSON array, guarded like
  every other JSON column), defaulting to the warehouse's own `country_code`. A
  warehouse in Singapore serving Malaysia and Indonesia is one row with three
  codes; a warehouse that serves only where it stands needs no value at all.
- **The match**: the tree already walks `country → province → … → township`, and
  the chain ends at the country node for a point inside China. A point outside it
  resolves to a country node instead of to no division, so the same `IN` over the
  chain matches a warehouse whose country list contains that country — one
  algorithm, two kinds of coverage, no second lookup path.
- **What it waits on**: nothing on this side except the need itself. On the
  geocoding side it waits on the **country**: Tencent answers a nation name, so
  the mapper owes a name → ISO mapping, and the normalizer's hard-coded `CN` root
  becomes the resolved country.
- **What it must not become**: a polygon abroad. Drawing a geofence around a
  country is expressing a country list as geometry, and it would drag in
  projection, coastline and a boundary dataset for an answer three letters long.

### Store API contract + error model

`GET /api/v3/store/location/resolve_seller?latitude=&longitude=&coordinate_system=`

Read-only, publishable-key auth, **guest access** — it is called before a
customer exists, so the controller calls `allow_guest_storefront_access!` to opt
out of the Store branch's login gate
(`storefront_gating.rb:12,26-29`); without it the endpoint answers 401 to the
one caller it has. `coordinate_system` ∈ `gcj02` (default) | `wgs84`, and the
client's `{lng, lat}` (`report.js:299-304`) map onto `longitude`/`latitude` in
one line — the client is rewritten against this contract, and the mapping is
stated rather than left to a guess.

Success (200):

```json
{
  "matched": true,
  "match_type": "township",
  "polygon_result": "matched",
  "seller": { "id": "sel_…", "slug": "…", "name": "…", "…": "…" },
  "administrative_division": { "code": "…", "name": "…", "level": "township" },
  "warehouse": { "name": "南山区仓" },
  "distance_km": 4.8
}
```

No service (200, explicit):

```json
{ "matched": false, "match_type": null, "seller": null, "…": null }
```

Errors:

| Status | Meaning |
|---|---|
| 400 | missing or non-numeric parameter, unknown `coordinate_system` — the shape `handle_parameter_missing`/`handle_argument_error` already render |
| 422 | latitude/longitude out of range — `render_validation_error`'s `:unprocessable_content` |
| 503 | provider(s) unavailable and no cached result — **a status v3 does not use today**, so it is introduced here deliberately |
| 200 + `"stale": true` | served from cache while provider(s) are down |
| 429 | too many lookups from one client in a minute — `rate_limit_exceeded`; the cache bounds the cost, this bounds what one caller can spend through it |

**The error needs a code, not just a status.** v3 errors are
`{ error: { code:, message:, details: } }` against a **closed** vocabulary
(`error_handler.rb:8-95`) with no entry for "geocoding unavailable", so the
provider failure adds one — named here because a plan that adds a status without
its code ships a 503 the client cannot switch on. The success payload is flat
like v3's singleton reads (`resource_controller.rb:31`), and prefixed ids are
used throughout (`sel_…`, as `Store::SellersController#find_resource` already
resolves them).

The `Decision` is the single source of truth; the serializer renders it. HTTP
caching keys on coordinate + store + a **routing-configuration version** — a new
concept, since core's ETag machinery keys on a resource
(`http_caching.rb:76-80`) — so a binding change cannot be served stale from a
CDN. Note the version must also join the `Vary` set core sends
(`http_caching.rb:28`) or be in the URL; the coordinate is in the query, which is
what makes the cache correct at all.

### The site record read (owned here, ruled 2026-09-18)

A "site" is a seller, and the client reads its record from five calls: `home/allConfig` (whose `siteDetails` it assigns wholesale to its global site — `report.js:24-35` destructures it and calls `setSiteInfo`, which replaces the whole object over a default that already declares `siteSvip: !1`, `siteState.js:55,68-79`), `site/getDetails`, `site/getCount`, `site/getOftenHot` and `site/getSiteDeliveryBySiteId`. Three plans consume fields off that record — the membership flag, the invoice capability and the request context — and until now no plan served it. This plan does, because it already resolves which seller a request belongs to and already owns the site lookups beside it.

| The client's call | Our surface |
| --- | --- |
| `site/getDetails`, and `siteDetails` inside the app bootstrap | `GET /api/v3/store/site` — **the record**: the seller's public profile, its operator block (`siteName`, `companyName`, `imgUrl`, `businessModel` 7 合营 / 8 加盟 / 9 自营, from `getSiteDeliveryBySiteId`) and the flags below |
| `site/getSiteDeliveryBySiteId` | the same route's `operator` block — the client reads four fields of it, on one page (`qualification/desc.js:36-52`) |
| `site/getCount`, `site/getOftenHot` | the **existing** `GET /api/v3/store/sellers` (`6.0-multi-vendor-marketplace.md:727`, upstream's) with a scope over the sites that serve the resolved point — no second list, and this plan adds no field to it |
| `home/allConfig` | not a route of this plan's: it is the app's bootstrap composite, and what it owes here is that its `siteDetails` is **this record's serializer**. Its other fields (`weComEntrance`, `noticeNew`, `godSite`) are named rather than assumed |

**The three flags are columns on the seller, and this record is where they travel.** `siteSvip` (whether the site sells memberships — already ruled a seller column on 2026-09-17), `invoiceType` (which invoice forms the site supports) and `provideSpecialTicke` (whether it offers 专票). The client's own construction decides the carrier: they are fields of the site payload by construction, read in more than twenty places, and the two competing carriers the audit recorded are not rivals at all — `store/sellers` is the route a customer asks about a *seller* on, and this record is the payload the *site* arrives on. No plan adds a flag to the upstream sellers payload.

**What this slice added, and what it left to the invoicing plan.** `site_svip` and `business_model` are the two columns on the seller that landed here, because both are this plan's to define. The two invoice fields the ruling above lists — `invoiceType` and `provideSpecialTicke` — are `6.1-china-invoicing.md`'s shape (its own decision: CSV strings plus a 专票 switch, stored on the seller and answered on the price preview), so they arrive with that gem's columns rather than being guessed at here. Until then the site record carries no invoice capability, and the settle page is unaffected: it reads those two off the price preview, not off this record.

**Why this is not the pricing plan's.** `6.1-seller-scoped-pricing.md` reads the request's context, not the record: it resolves which seller prices a catalogue read, and it says so in writing (`:33-36`). This section owns the record those reads describe.

### The discovery reads

The endpoints beside `resolve_seller` — what the client asks when it has no
seller yet, or when it needs to check one. Four reads, and the reason they are
one section is that each is a different question over the same two tables: the
bindings and the tree.

**Sites around a point — `GET /api/v3/store/sites?latitude=&longitude=`.** The
未开通 page asks with a coordinate and wants the sites serving that province,
because a customer who is in no seller's area still has to be shown what exists
around them. It is the routing question asked coarsely: the point is placed in
the tree, the province is taken from its chain, and the sellers with an active
warehouse bound to that province **or below it** are the answer.

**A subtree is a code prefix, which is why this needs no recursive query.** The
codes are hierarchical by construction — province `110000`, city `110100`,
district `110101`, township `110101001` — so "this node or anything under it" is
`code LIKE '1101%'` for a city and `code LIKE '11%'` for a province. One indexed
`LIKE`, no CTE, and the same fact that makes a row's level readable from its code
(the division gem's README says so) pays for this read too.

**Cities with sites — `GET /api/v3/store/sites/cities`.** The location list page
sends nothing and reads the cities in which any site has a binding. Same tables,
one level up: the rollup is the code prefix *truncated*, so it is a `DISTINCT` on
a substring rather than a second tree walk.

**A seller's delivery areas — `GET /api/v3/store/site/coverage`.** The address
form's third tier: which divisions this seller actually delivers to, as codes and
names, for the client to check an address against before saving it. It is the
seller's own bindings read back, not a computation.

**Two checks, one shape — `GET /api/v3/store/location/coverage?latitude=&longitude=&warehouse_id=`**
answers `address/checkShop` (does this warehouse serve the point) and, without a
warehouse, `address/checkSpecial` (does the seller — Decision 21 keeps the
campaign tier excluded and answers its check from the seller, which is a
superset). `common/checkSite` is the same table read the other way round and gets
its own route: `GET /api/v3/store/service_areas/taken?division_code=` answers
whether an active warehouse already holds that node, which is the seller-join
form's echo of Invariant 2.

**`getCount` and `getOftenHot` add no route.** The plan already ruled that they
are the existing `GET /api/v3/store/sellers` — a page's `meta.count` is the count
and its `data` is the list — so this section builds no second list and adds no
field to that payload.

### Security / rate limiting

The endpoint is public but each miss costs a provider call, so it is rate
limited per store and per client; the reverse-geocode cache is the primary
cost control. Input is strictly validated (numeric ranges, coordinate-system
allowlist) before any provider call.

### Performance

- geohash cache collapses neighbourhoods to one provider call;
- `polygon_bbox` pre-check avoids RGeo for most candidates;
- parsed geometry is memoised per request;
- indexes: `administrative_division (depth)`, and the partial unique index
  doubles as the lookup index on `(administrative_division_id) WHERE active`.

## Constraints on Current Work

- **Do not bridge the binding and a `Spree::DeliveryZone`, in either
  direction.** The binding answers which seller serves a point and is the
  coverage source of truth for discovery; a zone answers whether a delivery
  method may serve an address and keeps its upstream members. No code derives
  one from the other, no dashboard screen presents them as one coverage, and a
  plan that finds itself wanting a division-aware zone is rebuilding this
  binding (Decision 19).
- **Do not build a parallel seller-address model.** The seller's location is
  `StockLocation`'s existing address columns; the plugin only adds coordinates,
  a binding and a polygon.
- **`geocoder` is already a core dependency** and already does forward
  geocoding; it *can* compute spherical distance, but nothing in this repository
  calls that today, so the first caller is this plan's — do not add a competing
  geospatial gem for distance. RGeo is introduced only for polygon geometry.
- **Do not let a gem patch a core model or add an attribute to a core class.**
  The request scope, the `Spree::Current` attribute and the `StockLocation`
  columns are core's (Decisions 17 and 18); the gem ships the binding, the
  polygon, the geocoders, the mapper, the decision and the endpoint.
- **Do not resolve the seller twice.** The boundary resolves it once per request
  and everything after reads `Spree::Current.seller`; a gem that resolves it
  again for itself is the failure the architecture plan names at `:164`.
- **Do not collide with `6.0-order-routing.md`.** That plan's open question
  also wants lat/lng on `StockLocation` for a `closest_location` fulfillment
  rule. If core lands the columns first, this plugin consumes them instead of
  adding its own; if the plugin lands first, it adds them the same way.
- **Never store vendor administrative codes.** All stored codes are bureau
  codes; vendor→bureau mapping is a data asset, so swapping providers cannot
  corrupt existing bindings.
- **Field ownership on `spree_stock_locations` is contractual** (Decision 14).
  Do not add, duplicate or rename `latitude`, `longitude`, `geocoded_at`,
  `geocode_provider` or `geocode_status` here if core or
  `6.0-order-routing.md` already ships them.
- **Never auto-delete a binding.** Retiring a seller or deactivating a
  warehouse removes it from routing; the bound node and polygon stay for
  history.
- **The reverse-geocode vendor→bureau mapping (especially township level) is a
  required data asset built before the adapters ship**, not a nice-to-have:
  without it a customer standing in a bound township matches nothing.
- **Keep seller routing and fulfillment routing decoupled.** The warehouse this
  feature returns is the binding warehouse; `6.0-order-routing.md` owns
  fulfillment location choice.
- **Reuse `StockLocation#kind`; do not invent a second location concept.** The
  model already declares `KINDS = %w[warehouse store fulfillment_center]`
  (`spree/core/app/models/spree/stock_location.rb:7`) and includes
  `has_iso_geography` (`:28`, which normalises and validates the country and
  state codes and nothing else); the pickup side is its own columns and scopes —
  `pickup_stock_policy` (`:43`), `pickup_ready_in_minutes` (`:44-46`),
  `pickup_enabled` (a schema column, `server/db/schema.rb:3066`, with a scope at
  `:56`). A shop is a `StockLocation` with
  `kind: 'store'` and pickup configured; a forward warehouse is `'warehouse'` or
  `'fulfillment_center'`. Do not add a Shop model, and do not add a pickup
  concept — the Store API already serves `pickup_locations` and
  `pickup_points`.
- **This plan claims an exemption from the DeliveryZone constraint, and the
  exemption must be written here.** `docs/plans/6.0-delivery-zones.md:128`
  requires that "No new `Spree::Zone` references anywhere. New geographic
  eligibility goes through DeliveryZone (shipping) or `TaxRate.for_address`
  (tax)." The administrative-node binding plus polygon is a third
  geographic-eligibility mechanism, so the justification has to travel with the
  binding: this resolves a *buyer coordinate* to a *seller* before a cart
  exists, while `DeliveryZone` resolves a *postal address* to a *delivery
  method* during quoting, and the two sit a level of granularity apart. Do not
  create a `Spree::Zone` record and do not write service areas into
  `DeliveryZone`.
- **Do not change `DeliveryOriginGroup#covers_location?`.** It answers true for
  any seller-owned location (`spree/core/app/models/spree/delivery_origin_group.rb:46`),
  and `docs/plans/6.0-multi-vendor-marketplace.md:259` makes that deliberate: a
  narrowed group must not make a seller's stock unallocatable. The method is
  load-bearing in allocation (`Spree::Stock::Coordinator:59`,
  `Spree::FulfillmentProvider::Base:61`), so narrowing it by service area would
  break fulfillment. A seller outside their service area is filtered out of
  *discovery*, never out of *allocation*.
- **Field ownership (Decision 14) needs one clarification.** `latitude` and
  `longitude` are named the way `6.0-order-routing.md:690` prefers them, because
  that plan's open question also wants them and may land first.
  `geocoded_at`, `geocode_provider` and `geocode_status` have no official
  counterpart: mark them as this plan's own columns, reusable by core later,
  rather than as a shared contract core is expected to honour.

- **Seller discovery is not market membership.** A store's `Spree::Market`
  answers which countries the store sells into — currency, tax, return window —
  and nothing links a seller to it. Do not gate which sellers a customer sees on
  a market: that question is this binding's, and Decision 23 records the shape it
  grows into outside China.

## Open Questions

1. ~~**Gem name.**~~ **Settled 2026-09-18: `spree_service_areas`**, at
   `spree/extensions/spree_service_areas/` (Decision 22).
2. **Irregular administrative structures.** Municipalities (北京/上海), special
   administrative regions and province-directly-administered counties omit
   levels. The chain builder must tolerate missing levels without mis-matching
   (e.g. a district whose parent is the province directly); verify against the
   bureau dataset during implementation.
3. **Township-level reverse-geocode coverage.** Tencent returns township-level
   components, but coverage is less uniform than at district level. Confirm it
   resolves township-level codes across the target region before freezing the
   mapping dataset — and the same check for Amap if and when it ships (Decision
   8, amended 2026-09-19).
4. **IP geolocation.** The WeChat mini-program supplies coordinates, so IP-based
   fallback (for H5/web entry) is deferred; if needed it becomes a third
   provider beside Tencent and Amap.
5. ~~**What is the relationship between `Spree::DeliveryZone` and an
   administrative-node binding?**~~ **Settled 2026-09-18: they answer two
   questions, and nothing bridges them** (Decision 19). The binding is the
   coverage source of truth for seller discovery; a zone keeps its upstream
   meaning as a delivery method's eligibility list and is authored in the
   delivery profile. A bridge was rejected for a mechanical reason: zone members
   stop at the state, so expressing a district-or-deeper binding through them
   either loses the precision the binding exists for or needs a new member type
   in an upstream model. This deployment authors no zone for coverage at all —
   the client carries no postal codes — so the "configured twice" worry does not
   arise in practice, and the rule is written down rather than left to habit.
6. ~~**Cainiao's province map is a second, shallower variant.**~~ **Settled
   2026-09-18**: the plan that carried the map is **superseded**, so there is no
   second variant to consume the tree and no ISO→bureau crosswalk to build — its
   only consumer was that plan's address params. Nothing here remains open.
7. ~~**Do the coordinates and the binding belong to `StockLocation` at all if
   core ships them first?**~~ **Settled 2026-09-18: they stay on
   `spree_stock_locations`, and Decision 14's shared contract is kept** (Decision
   20). Upstream's `6.0-order-routing.md` (upstream's plan) mentions the columns
   only inside its own open question, deferred to phase two, and the table carries
   neither today — while the geocoding primitive that does ship is
   `Spree::Address`'s. Whichever side lands first owns the migration and the other
   consumes it. Two consumers reading one fact is not two meanings; if a future
   upstream point genuinely differs from a shop's public point, that is a second
   suite of columns on the anchor that owns the service area.
8. ~~**The client resolves delivery area in three tiers; this plan models two.**~~ **Settled 2026-09-18: two tiers, and the middle one stays excluded** (Decision 21). The evidence below is kept because it is what makes the answer obvious. **Campaign zones are answered, not extended**: a campaign zone belongs to one seller and is delivered by a set of its shops, so its coverage is the union of their polygons — derived, never stored — and the only new fact would be the campaign-to-warehouse membership, which is merchandising. `address/checkShop` checks the shop's own coverage and `address/checkSpecial` checks the seller's.
   The mini-program picks its coverage source from the context it is in — a
   specific warehouse (`shopId`), else a campaign zone (`specialId`), else the
   seller (`siteId`): `pagesF/address/shipping/shipping.js:339`, backed by
   `shop/getAreaShopById`, `special/getShop` and `site/getSiteDeliveryAreas`.
   **Two corrections to this plan's earlier reading of that page**: the client's
   seller tier is a *display* check — it draws the seller's polygon only when the
   located point already equals the current `siteId` — and the actual routing act
   on that page is `site/getByLngLat`, which the drafting missed and which is the
   endpoint `resolve_seller` replaces (it answers a seller **and** a warehouse in
   one object: `{id, siteName, city, openStatusNew, areas, shopId, shopName}`,
   `report.js:291-320`). `special/getShopByPoint` is its poorer cousin — a bare
   `shopId` (`pagesC/special/special.js:352-370`), the contract Decision 11
   exists to avoid.
   The warehouse tier and the seller tier are exactly what this plan already
   binds. The middle tier is not, but it needs no new area concept: a campaign
   zone belongs to one seller and is delivered by a **set** of that seller's
   warehouses, so its coverage is the union of their polygons
   (`shipping.js:355-369` passes an array to `setMapArea`; `special/getShop`
   returns one shop per element). It is derived, not stored. What it needs is
   the campaign-to-warehouse membership, which is merchandising rather than
   geography. Confirm whether campaign zones are in scope before extending the
   binding model.
