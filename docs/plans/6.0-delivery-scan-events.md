## Summary

Spree 6.0 keeps no carrier scan history. `Spree::Delivery` holds the carrier
axis as *current state* — `status`, `delivered_at`, `estimated_delivery_at` and
a single `details` JSON column — and `Spree::Deliveries::UpdateTracking`
overwrites that state on every report, deliberately: a carrier resends the whole
picture each time, so accumulating in `details` would mean each provider gem
reimplementing merge and de-duplication. The EasyPost reference provider goes
further and keeps only five keys, reading the `tracking_details` array solely to
find the timestamp of the delivering scan.

The result is that a parcel's journey is not recoverable. A customer who expects
a stop-by-stop timeline cannot be served, and a merchant filing a damage or
loss claim has no record of where the parcel went. This plan adds an
**append-only child record**, `Spree::DeliveryEvent`, fed by an optional
`scans:` argument on `Deliveries::UpdateTracking`, and a **monotonicity guard**
so an out-of-order carrier report cannot regress a parcel that has already
arrived.

## Key Decisions (do not deviate without discussion)

- **Events are append-only history, never a second source of the current
  state (2026-09-10).** `decisions.md` 2026-08-11 forbids splitting the carrier
  axis across rows — "status here, delivered_at there" recreates the
  two-sources problem the 6.0 status rework removed. Events do not split it:
  `delivery.status` and `delivery.delivered_at` remain the only answers to
  "where is it now" and "when did it arrive", and a table of past scans has no
  authority over either. Two constraints are written into this plan to keep
  that true, and both are listed under "Constraints on Current Work".
- **`scans:` is an optional keyword, not a new requirement (2026-09-10).** A
  provider that sends nothing behaves exactly as it does today. This is what
  lets the EasyPost gem adopt the interface later without a coupled release,
  and it keeps the change inside one workflow.
- **Core stores scans; the provider names them (2026-09-10).** Core ships no
  carrier vocabulary, exactly as it ships none for `tracking_status` today. A
  provider maps its carrier's raw vocabulary onto
  `Spree::Delivery::STATUSES` for `status`, and passes the carrier's own words
  through as `description` for display. Carriers already separate the two: the
  instant-delivery platforms the client uses return a status code beside its
  Chinese label (达达's `order_status` `3` beside 取货中), and a waybill carrier
  returns an `action` code beside a description.
- **The fingerprint is a digest computed in core, overridable by a supplied
  id (2026-09-10).** Carriers resend scans, so de-duplication must be enforced
  by a database unique index rather than by the writer. A provider that has a
  stable carrier-side scan id supplies it and core uses it; otherwise core
  derives the fingerprint from `occurred_at` (normalized to the second) plus
  `status`, `description` and `location`. The fallback is the *only* option for
  the platforms this application actually dispatches to: 达达's callback carries
  `order_status`, `update_time` and the rider's name and mobile, and no scan id
  at all. Collapsing two genuinely identical scans reported in the same second
  is an accepted, vanishingly rare loss — and the reassignment case is why the
  fingerprint must not be `(status, occurred_at)` alone (达达 re-sends a status
  with a *different* rider; see `6.1-local-delivery.md`).
- **The monotonicity guard lives in core (2026-09-10).** The rule is about the
  correctness of `delivery.status` and therefore of the fulfillment's
  `delivered` rollup and of `delivered_at`, which the returns window counts
  from. It is not provider-specific and must not be reimplemented per gem. It
  also repairs a live defect: `UpdateTracking#apply_carrier_report` writes
  whatever status it is handed, and
  `Fulfillments::RecalculateDelivery` reopens a `delivered` fulfillment when any
  sibling delivery is undelivered — so a late `in_transit` webhook can already
  step a completed order back to `fulfilled` and clear `delivered_at` today.
- **The timeline is a paginated nested endpoint, never an embedded array
  (2026-09-10).** A parcel accumulates dozens of scans; three parcels would put
  a hundred and twenty events into every order response, including the order
  list that never displays them. Events are read through
  `.../deliveries/:id/events`, beside the `deliveries` resource they belong to.
- **No lifecycle event per scan (2026-09-10).** `UpdateTracking` writes through
  `update_columns` on purpose — "a lifecycle event per scan would run the full
  order status rollup for writes that cannot change any status". `DeliveryEvent`
  therefore does **not** include `publishes_lifecycle_events`. The
  `after_update_tracking` hook and the `fulfillment.delivered` event remain the
  notification surface for this axis.
- **The Store API surface was phase two (2026-09-10), and the timeline it
  reserved now belongs to `6.1-delivery-tracking.md` (ruled 2026-09-18).**
  Delivering the timeline to buyers needs new Store API surface — deliveries are
  embedded in the store fulfillment serializer and have no standalone store
  endpoint today — and that surface is the tracking plan's, which already owns
  `GET /api/v3/store/orders/:id/trajectory` and the position reads. This plan
  stays phase one: record the data, expose it to staff, and verify the
  normalization against real carrier traffic before anyone shows it to a
  customer.

## Design Details

### Model: `Spree::DeliveryEvent` (`spree_delivery_events`)

| Column | Notes |
| --- | --- |
| `store_id` | `null: false`, via `Spree::SingleStoreResource` — same shape as `Delivery` and `ShippingLabel`, and it makes store-scoped queries free |
| `delivery_id` | `null: false` |
| `occurred_at` | `datetime`, `null: false` — when the carrier says the scan happened, authoritative for ordering |
| `status` | `string`, `null: false` — one of `Spree::Delivery::STATUSES` |
| `description` | `string` — the carrier's own wording, shown verbatim |
| `location` | `string`, nullable — not every carrier supplies one |
| `details` | `json` — the raw scan payload as the provider received it |
| `fingerprint` | `string`, `null: false` — the de-duplication key |
| timestamps | |

Indexes: unique on `(delivery_id, fingerprint)` for idempotency; non-unique on
`(delivery_id, occurred_at)` for the timeline read.

Associations: `belongs_to :delivery`, and on `Spree::Delivery`
`has_many :delivery_events, dependent: :delete_all`. `delete_all` rather than
`destroy_async`: an event has no callbacks and no meaning without its delivery.

Includes `Spree::SingleStoreResource` and `has_prefix_id` (events are exposed
through the API, so prefixed IDs are mandatory). Deliberately does **not**
include `Spree::Metadata` or `Spree::HasCustomFields` — `details` already holds
the raw payload, and a scan is not merchant data. Deliberately no
`publishes_lifecycle_events`, per the decision above.

The name avoids two collisions recorded in `fork-decisions.md` 2026-09-03: the
deferred `spree_fulfillment_trackings` cannot describe a `Return`-owned parcel,
and `Tracking`/`TrackingStatus` already mean the fulfillment's 5.6 string field
and one column of the delivery.

### Value object: `Spree::Deliveries::Scan`

A plain `ActiveModel::Model` + `ActiveModel::Attributes` class (never a
`Struct`), holding what a provider hands over before core persists it:

```ruby
attribute :occurred_at, :datetime
attribute :status, :string
attribute :description, :string
attribute :location, :string
attribute :external_id, :string      # the carrier's own scan id, when it has one
attribute :details, default: -> { {} }
```

Validates `occurred_at`, `status` (against `Spree::Delivery::STATUSES`) and
`description`. The namespace matches the workflow and service it travels with.

### `Spree::Deliveries::UpdateTracking`

```ruby
def perform(delivery:, tracking_status: nil, estimated_delivery_at: nil, delivered_at: nil,
            details: nil, notify_customer: true, scans: nil)
```

- A new `step :record_scans` runs after `apply_carrier_report`.
- `record_scans` is skipped when `scans` is blank, which is what keeps existing
  providers working untouched.
- Rows are built from `Spree::Deliveries::Scan` and written with `upsert_all`
  against `unique_by: [:delivery_id, :fingerprint]`, per the house rule that bulk
  creation uses `insert_all`/`upsert_all` backed by a real uniqueness index.
  `upsert_all` bypasses ActiveRecord timestamps, so `created_at`/`updated_at`
  are written explicitly.
- Fingerprints are computed in core unless a scan arrives with an `external_id`.
- An unknown `status` on an individual scan is **not** a workflow failure: it is
  recorded as `unknown` rather than `failure(...)`, which would reject the whole
  report — the current status and the estimate it carried are worth keeping even
  when one scan cannot be named. `ensure_known_status` continues to guard
  `tracking_status`, the axis that actually moves.

### The monotonicity guard

Written into `apply_carrier_report` as a rule about the status write only:

> When the delivery is already `delivered`, a report that is not `delivered`
> and whose report time is earlier than the delivery's `delivered_at` does not
> change `status`, `estimated_delivery_at` or `delivered_at`. Its scans are
> still recorded.

The report time is the newest `occurred_at` among the report's scans, falling
back to the time the report is being applied. Staff confirmation
(`Fulfillments::MarkDelivered`, and the per-delivery `mark_delivered`) is
unaffected: a human saying a parcel arrived outranks a carrier that never sent
the last scan, and that is existing, documented behaviour.

This is what stops the reopen: with the guard, an out-of-order `in_transit`
can no longer leave the delivery `undelivered`, so
`Fulfillments::RecalculateDelivery` has nothing to reopen.

### Provider contract

Nothing is added to `Spree::FulfillmentProvider::Base`. A provider that has scan
data returns it in the hash its `parse_webhook_event` already returns:

```ruby
{
  tracking_code: '9890000160004',
  tracking_status: 'in_transit',
  estimated_delivery_at: nil,
  delivered_at: nil,
  details: { ... },
  scans: [Spree::Deliveries::Scan.new(...), ...]
}
```

The webhook controller splats `**event.except(:tracking_code)` into the
workflow, so `scans:` reaches `UpdateTracking` with **no controller change**. A
provider that reports scans outside a webhook — a reconciliation job polling the
carrier — calls the same workflow directly.

### Admin and Seller API

```
GET /api/v3/admin/orders/:order_id/fulfillments/:fulfillment_id/deliveries/:id/events
GET /api/v3/seller/orders/:order_id/fulfillments/:fulfillment_id/deliveries/:id/events
```

Index only — an event is never created, updated or destroyed over the API, and
there is no `show`: the timeline is read whole. Paginated through the base
`ResourceController` (Pagy), ordered by `occurred_at` ascending, joining the
`deliveries` resource already mounted in both routers.

`Admin::DeliveryEventSerializer` and `Seller::DeliveryEventSerializer` over a
store `DeliveryEventSerializer` (which phase two wires up, not phase one):
`id`, `status`, `description`, `location`, `occurred_at`; admin adds `details`
and timestamps. The status list is closed over `Spree::Delivery::STATUSES`.

Read and write names match; there is nothing to write.

The type pipeline runs as usual: `typelizer:generate`, `generate:zod`,
integration tests, `rswag:specs:swaggerize`, SDK tests.

### Dashboard

A timeline on the fulfillment card's delivery row: scans in `occurred_at` order,
the carrier's `description` as the primary line, the timestamp beside it, and
`location` when present. Every string through i18next in all locales; the
carrier's own description is data and is never translated.

### The second implementation

The EasyPost gem currently discards the scan array. Mapping
`tracker['tracking_details']` onto `scans:` there — with `status`,
`status_detail` and `datetime` from each detail entry — is a small, separate
change in that gem, and it is worth doing early for two reasons: existing
EasyPost users stop losing data they are already paying for, and the interface
gets a second real implementation, which is the only way its shape is genuinely
tested. One implementation is a guess.

## Migration Path

1. **Model and storage** — one migration creating `spree_delivery_events`, the
   `Spree::DeliveryEvent` model, the `Spree::Deliveries::Scan` value object, and
   the `Delivery` association.
2. **Write path** — `UpdateTracking` gains `scans:`, the `record_scans` step and
   the monotonicity guard, with specs covering: scans recorded, duplicate
   fingerprints collapsed, blank `scans` unchanged, unknown scan status stored as
   `unknown`, and a late report not regressing a delivered parcel.
3. **API** — the two nested index endpoints, serializers, routes, type pipeline
   regeneration, and the SDK resources.
4. **Dashboard** — the timeline component and its e2e spec.
5. **EasyPost** — feed `scans:` from `tracking_details`, proving the interface
   against a second provider.
6. **Phase two (may be 6.1)** — Store API surface for the buyer-facing timeline,
   and the storefront component that reads it.

Steps 1–3 are the shippable core; 4 and 5 follow in the same train.

## Constraints on Current Work

- **Nothing may read the current status from `spree_delivery_events`.** The
  newest event is not the status. `delivery.status` and `delivery.delivered_at`
  are written only by `Deliveries::UpdateTracking` and
  `Fulfillments::MarkDelivered`, exactly as they are today.
- **Nothing writes `delivery_events` outside `Deliveries::UpdateTracking`.**
  A reconciliation job or a provider does not insert rows directly; it calls the
  workflow, so the monotonicity guard and the fingerprint rules apply to every
  path.
- **Do not add a lifecycle event per scan**, and do not add
  `publishes_lifecycle_events` to `DeliveryEvent`.
- **Do not put scan history in `Delivery#details`.** That column keeps its
  documented meaning — the last report's payload, overwritten each time. Code
  that wants history reads `delivery_events`.
- **A provider must not send `scans:` before the guard ships.** Without it, an
  out-of-order scan set can regress a delivered parcel.
- **`status` on an event is a closed list.** A provider that cannot map one of
  its carrier's statuses sends `unknown`; it does not invent a value, and core
  does not accept one.

## Open Questions

- **Retention.** Scans are unbounded in principle. The working assumption is to
  keep everything — a full journey is a few kilobytes and is exactly what a claim
  needs — with a documented pruning task added once real volumes are known.
  Whether retention becomes a store preference is deferred.
- **Page size and cap for the timeline endpoint.** The nested-panel rule says
  paginate rather than cap; the default page size follows the base controller
  unless a scan-dense parcel argues for a larger one.
- **Whether `location` earns its column.** The evidence is thinner than it was:
  达达's callback and 闪送's status callback carry no location, UU's carries the
  rider's coordinates, and 闪送's order detail carries a trail. It stays nullable
  and is dropped if no provider supplies it — a decision to take against
  `6.1-local-delivery.md` rather than against a carrier that is no
  longer in the set.
- **Value object name.** `Spree::Deliveries::Scan` reads well beside
  `DeliveryRateProvider::Estimate` and `LabelPurchase`; `ScanReport` is the
  alternative if a report ever carries more than scans.
