## Summary

The 酒小二 WeChat mini program calls 566 HTTP endpoints on a legacy gateway (`/v2-app-mall`, plus four on `/v2-app-pms`). Mapping them onto Spree 6.0's Store API showed that 107 of them (27 exact, 80 near) correspond to something Spree already models, and 453 do not. Two of the domains with no Spree equivalent were excluded by the author: gamification (49 endpoints) and the home-page CMS (21 endpoints). This plan covers the rest of the gap and does not repeat the per-domain designs, which live in their own plans.

It exists to fix the rules all of those plans must obey, to say which of them are one gem and which are several, to name the capabilities that more than one of them needs and which therefore have to be built once in core rather than twice in two gems, and to put the whole set in an order that never leaves a gem waiting on a capability that has not been built.

## Key Decisions (do not deviate without discussion)

- **Every feature is a standalone, optional gem.** The boundary is the one `spree/providers/wechat_pay/README.md` states in its "Extension boundary" section: a gem ships its own migrations, adds its own classes, and **patches no Spree model**, so an update to Spree does not overwrite it. The `spree` meta gem (`spree/spree.gemspec:28-29`) depends only on `spree_core` and `spree_api`; it never gains a dependency on any gem here.
- **A generic capability an extension needs lands in core first.** The precedent is asynchronous refunds: WeChat Pay needed them, they are generic, so they went into core rather than into the gateway gem, because "a gateway must not decorate core models". Every time a plan in this set wants to `decorate` or monkey-patch a core model, the correct move is to add the missing capability to core in the same change and say so in `docs/plans/decisions.md`.
- **Feature gems live under `spree/extensions/<gem_name>/`; payment gateways live under `spree/providers/<gem_name>/`.** Gateways join the existing provider family. Everything else gets a new sibling directory for the same reason the provider family exists: the starter app's Gemfile already reaches three levels with `glob: '{,*,*/*,*/*/*}.gemspec'` (`server/Gemfile:29`, with a comment saying the extra level exists for `spree/providers/*`), so a gem at `spree/extensions/<name>/` is picked up by the same glob and needs only its `gem '...'` line. Flat gem names (`spree_member_tiers`, not `spree/extensions/member_tiers`), matching the provider rule in `AGENTS.md`.
- **No API compatibility layer.** The mini program is rewritten against Store API v3. We do not implement `/v2-app-mall/*` as a facade over Spree. 80% of the endpoints have no Spree equivalent, so a facade would re-implement the legacy contract in full and then also build the Spree side — paying twice for the same feature.
- **Tenancy comes from the store, never from a parameter.** Anything a customer can see or write is read through `current_store.<association>`, per the scope-fetching rule in `AGENTS.md`. Every new model carrying store data includes `Spree::SingleStoreResource`.
- **One administrative-division design, and the second one is gone.** Chinese geography had two designs in this repository: the four-level `Spree::AdministrativeDivision` (GB/T 2260 plus bureau codes) in `6.1-seller-service-area-routing.md`, and a gem-local 34-province ISO-to-Chinese-name map inside `6.1-cainiao-logistics-provider.md`. The four-level design wins and is extracted into a shared foundation gem — and the province-only variant **left with its plan**: `6.1-cainiao-logistics-provider.md` was superseded on 2026-09-18, so the map is not merely retiring, its consumer is gone. The ISO→bureau crosswalk the retirement needed lands only if another consumer appears.
- **The excluded domains are out of scope and must not creep back in.** Gamification (dice, prize draws, rankings, scan-cashback, yearly count, 49 endpoints) and the home-page CMS (page decoration, topics, articles, ad slots, 21 endpoints) are excluded. A gem in this set that finds itself needing an ad slot or a prize draw is a signal the boundary was drawn wrong.
- **Points are not money; commission balances and store value are.** Spree already models prepaid money as `Spree::StoreCredit` with a `Spree::StoreCreditEvent` ledger, and `6.0-6.1-loyalty-gift-cards-store-credits.md` decided that stored value belongs under the Loyalty group rather than under Promotions. A points balance and a distributor's withdrawable balance are separate ledgers with their own rules and must not be folded into store credits.
- **A number one gem must add to another gem's total is added by hooking an event, never by a rule table.** Spree is event-driven, so the seam is the event plus the owning gem's service: a gem that earns points on something that is not an order subscribes to its own event and calls the points ledger service, and registers no matcher and no kind. `6.1-points-and-growth-value.md` is the worked example — 消费积分, 商品积分 and the 满 N 元门槛 are settings on the one subscriber that gem owns, 生日双倍 and 会员日双倍 are read from the membership rights, and 评价积分 belongs to `6.1-product-reviews.md` because a review is not a purchase. The typed-subclass rule above still governs a value list a gem genuinely owns; it does not license inventing one to carry numbers another gem's events already deliver.

## Design Details

### The anatomy every gem in this set follows

Taken from the gems already in the repository (`spree/providers/wechat_pay`, `spree/providers/social_auth`, `spree/providers/meilisearch`):

```
spree/extensions/<name>/
  spree_<name>.gemspec      # authors, summary, spree_core dependency, files glob
  Gemfile                   # eval_gemfile('../../common_spree_dependencies.rb') + gem 'spree', path: '../../' + gemspec
  README.md                 # an "Extension boundary" section stating what it does and does not touch
  lib/spree_<name>.rb
  lib/spree_<name>/engine.rb
  app/models/, app/services/, app/controllers/, app/serializers/, app/subscribers/, app/jobs/
  config/locales/en.yml
  db/migrate/               # only if the gem introduces tables
  spec/
```

The gemspec's file glob is the one `spree/providers/wechat_pay/spree_wechat_pay.gemspec:17` uses — `Dir["{app,config,db,lib,vendor}/**/*", "Rakefile", "README.md"]` — so a gem that ships migrations must place them in `db/migrate/` for that glob to carry them.

### What each gem must ship

1. **Migrations in the gem**, never in the host app.
2. **Store API v3 controllers** subclassing `Spree::Api::V3::Store::ResourceController` (read-only by default, opting into writes per resource) and **Admin controllers** subclassing the Admin `ResourceController` for back-office configuration. Flat params, prefixed IDs, `{data, meta}` envelope, `resource_permitted_attributes` rather than an override of `permitted_attributes`.
3. **Serializers** subclassing `Spree::Api::V3::BaseSerializer`; the Admin serializer extends the Store one. No timestamps or internal state on the Store side.
4. **A Dashboard plugin** via `defineDashboardPlugin` from `@spree/dashboard-core/plugin` for merchant configuration, per `6.0-admin-spa.md`.
5. **Lifecycle events** for anything that other systems care about (points awarded, a tier changed, a commission earned, a group buy closed), using `publishes_lifecycle_events` and a subscriber in `app/subscribers/spree/`.
6. **Specs** run through `scripts/test/rspec <engine>`, with a CI matrix entry (see Constraints).

### Recurring jobs: one register, and the host app runs them

Upstream's rule is the one this set follows — **core ships no cron, the host app schedules the job** (`6.0-multi-vendor-marketplace.md:178`, and the deployment doc carries the entries an installation must add; `spree_crm`'s expiry job states the same in its own comment). Five plans in this set introduce a periodic job and none of them stated a cadence or a registrar, which leaves every operator to discover five entries by reading five documents. This is that register.

| Job | Cadence | What breaks if it does not run | Owner |
| --- | --- | --- | --- |
| `Spree::CrmMemberships::ExpireLapsedJob` | hourly | members keep a tier they no longer pay for — **removed when `6.1-membership-tiers-and-rights.md`'s ending-of-term sweep lands** | `.custom-extensions/spree_crm`, delivered |
| `SpreeWechatPay::RefreshCertificatesJob` | 6 hours | the platform certificate expires and every refund and callback verification fails | `spree/providers/wechat_pay`, delivered |
| `SpreeWechatPay::ReconcileRefundsJob` | 15 minutes | async refunds stay `processing` and the customer is never told they were paid back | `spree/providers/wechat_pay`, delivered |
| the position-pruning job | daily, operator-set window | `spree_delivery_events` grows without bound — a coordinate stream is a liability as well as a cost | `6.1-delivery-tracking.md` |
| the hold sweep | every minute | lapsed holds are released late; the count is safe because every release is idempotent on the hold's id | `6.1-flash-sales.md` |
| `GroupBuys::RefundMembers` | every few minutes | a failed team's members wait for their money; nothing corrupts, because the membership row is the cursor | `6.1-group-buying.md` |
| the automatic-review job | hourly | completed orders sit unreviewed past the grace period | `6.1-product-reviews.md` |
| the grant scheduler | daily | birthday, member-day and annual grants are missed for that day — each kind's period key makes a late run safe, not a missed one | `6.1-membership-tiers-and-rights.md` |
| the ending-of-term sweep | hourly | an ended term keeps its `CustomerGroup`, so member prices and the free-delivery waiver outlive the membership | `6.1-membership-tiers-and-rights.md` |
| the distributor payout settle | daily, or on the operator's own trigger | rewards accrue and are never paid out | `6.1-distribution-and-commissions.md` |

Three rules for anything added here: **the job must be safe to run twice** (an idempotency key, a status cursor, or an idempotent release — never a counter it decrements blind), **its cadence must be slow enough to be honest about the failure mode** ("late" is almost always acceptable; "wrong" never is), and **a plan that adds one adds its row here in the same change**.

## Migration Path

1. **Placement and the site concept are settled** (both 2026-09-17: gems live in `spree/extensions/`, and a site is a seller; the companion reading of `shopId`, `siteShopId` and `specialId` is in Open Question 2). **Rule on the one question this step still waits for** (Open Question 4 — whether `threeOrder/*` is gamification), close the CI gap for the two gems already missing from it, and build seller resolution first, because every plan below depends on those.
2. **Wave 0.** Land the core Store API gaps, the administrative division gem and the verification-code gem. Each gets its own plan, its own tests, and — for the core work — an OpenAPI regeneration.
3. **Wave 1.** Membership, points, coupons, gift cards, the second gateway. **The grant/benefit primitive's row lives in core, and `spree_grants` owns its kinds and its service** (ruled 2026-09-18 — `6.1-grant-and-benefit-primitive.md`), so no consumer waits on another's start order.
4. **Wave 2.** Catalogue and fulfilment. These depend on Wave 0 only, so they may run in parallel with Wave 1 if there is capacity.
5. **Wave 3.** Growth. Group buying depends on the hold `6.1-flash-sales.md` ships gem-local and generalises into core (ruled 2026-09-18), and distribution depends on the commission side of the marketplace; referrals ride distribution's ledger for money and `spree_grants` for everything else.
6. **Cross-cutting** is built as its consumers appear: the subscribe-message sender is needed by the first gem that notifies a customer.

## Constraints on Current Work

These apply now, before any of the plans below is implemented.

- **Do not decorate or patch a core Spree model from an extension gem.** If a plan needs behaviour on `Spree::Order`, `Spree::Product` or `Spree::Customer` that is not there, add a generic capability to core in the same change, following the asynchronous-refund precedent, and record it in `docs/plans/decisions.md`.
- **Seller scoping is not a feature, it is the request context.** A site is a seller (decided 2026-09-17), so every Store API endpoint in this application runs in the context of one resolved seller. Resolve it once at the request boundary and read it from there, the way `Spree::Current.store` is read — do not let a gem resolve the seller for itself, and do not let it infer the seller from an object it happens to hold. A gem that treats the resolved seller as the owner of the catalogue it reads is wrong by construction: the catalogue is store-wide and the operator's, and the seller scope belongs on its **offers** (`Variant.for_seller`), never on `Product`.
- **Do not add `/v2-app-mall/*` compatibility routes** to `spree/api`, not even temporarily.
- **Do not add a second system-notification sender.** `6.1-notifications.md` owns it, and the marketplace relay beside it is a different thing — a buyer-seller conversation, not a sender.
- **Do not create a `Spree::Zone` reference or a new geographic-eligibility mechanism outside `DeliveryZone`.** `6.0-delivery-zones.md` states this as a constraint on all current work; `6.1-seller-service-area-routing.md` claims an exemption, and its Constraints now write that claim out rather than assuming it (2026-09-18).
- **Do not give an extension gem a dependency on another extension gem** unless the dependency is stated in both plans' headers. The gems must stay individually installable.
- **Do not fork the money rails.** Spree already ships a commission snapshot (`Spree::CommissionLine`), a per-order earning ledger with refund reversals (`Spree::SellerTransfer`), a scheduled settlement (`Spree::SellerPayout`), a balance reader (`Spree::SellerBalance`), a `PayoutProvider::Base` seam with `transfer!`/`pay!`/`reverse!` and idempotency keys, and a verification model (`Spree::SellerRequirement` plus `SellerRequirementSubmission`). A distributor balance, a withdrawal and a real-name check are the same shapes pointed at a customer instead of a seller. Reusing them means changing shipped tables; building parallel ones means two ledgers that can disagree. `6.1-distribution-and-commissions.md` carries that decision — do not start a third money ledger before it is made.
- **A new gem must be wired in three places or its tests never run:** the starter `server/Gemfile` path block, the CI project list in `.github/workflows/tests.yml`, and the gem's own `Gemfile`. Note that this is currently unmet for two gems already in the repository — `providers/wechat_pay` and `providers/social_auth` do not appear in the `tests.yml` project list, so their specs do not run in CI. Fix that before adding an eighteenth gem.
- **Do not let an excluded feature in through a side door.** If a plan needs a prize draw, a ranking list, a home-page ad slot or a decorated page, stop and raise it rather than building a small version of it.

## Open Questions

1. ~~**Where does a feature gem live?**~~ **Decided 2026-09-17: `spree/extensions/<name>/`.** The deviation from `.gitignore:81` and the three reasons it beats `.custom-extensions/` — invisible to CI, no remote on its one precedent, unprovisioned in worktrees — are recorded in `docs/plans/decisions.md` under that date.
2. ~~**What is a "site"?**~~ **Ruled by the author: a site is a seller** (decided 2026-09-17, recorded in `docs/plans/fork-decisions.md`). `siteId` — sent on every request at `miniprogram/static/config/api.js:42` — is a seller identifier, and what it scopes is **whose offers are sellable**, not whose products exist: the catalogue is the operator's store-wide master catalog, and a seller distributes it by holding offers, `Spree::Variant` rows carrying its `seller_id` on master products (upstream Decision 11, and pull request #14576; see `decisions.md`). Three companions are settled by the same reading. A **shop** (`shopId`) is one of the seller's warehouses — `Spree::StockLocation` with that `seller_id`, one seller to many shops, and the location its offers' stock sits in. **`siteShopId` is the same value as `shopId`** (`static/utils/report.js:9` and four more assignments), so it is one identifier under two header names and must not become two fields; nothing reads it but analytics. A **special** (`specialId`) is a campaign zone owned by one seller and delivered by a set of its shops, so its delivery coverage is the union of their polygons rather than an area of its own — which is why the client resolves delivery area in three tiers, shop else special else seller (`pagesF/address/shipping/shipping.js:339`), and `6.1-seller-service-area-routing.md` carries the middle tier as an open question. `mallCode` is **not** a tenant — `app.js:129-141` reads it from the local `miniMall.json` gateway and acts on only two values, `100911` to offer the minimal mall and `100912` for third-party mode — and `minimalSite` is the same seller concept in the reduced-mode state (`state/minimalState.js`, `config/api.js:34,42`) rather than a second model.
3. ~~**Which gem owns the grant/benefit primitive?**~~ **Settled 2026-09-18: the row is core and the kinds and service are `spree_grants`** (`6.1-grant-and-benefit-primitive.md`; `fork-decisions.md`, same date). The "whichever of membership, coupons or points is implemented first" reading above is withdrawn — it made two consumers wait on the first, and the coupon wallet's own placement argument (`6.1-coupon-wallet.md:127`) is answered by the core row instead.
4. **Is `threeOrder/*` gamification?** Eleven endpoints, an ordering-streak activity with prizes. Recommendation is to exclude it. Unblocked by a ruling from the author.
5. **Do the extensions target a Spree release or stand alone?** The plans are named `6.1-` for consistency with `6.1-seller-service-area-routing.md`, but these are not Spree features and will not ride a Spree release. If they are meant to be upstreamed, several of them (points, membership) are large enough to need their own upstream discussion first.
6. ~~**Does membership belong to one seller or to the platform across sellers?**~~ **Settled 2026-09-17: a membership belongs to the customer** (`docs/plans/decisions.md`). The tier and the points balance are customer-scoped and span every seller; the purchase that grants them is still seller-scoped. The client's site-level `siteSvip` flag (`static/state/siteState.js:55`) is a **column on the seller**, not a membership-side allowlist — settled 2026-09-17 (`docs/plans/decisions.md`), because the client reads it off the site record itself: `static/utils/report.js:24-35` assigns `home/allConfig`'s `siteDetails` straight into `setSiteInfo`. Coupons and gift cards still need their own answer, which the ruling does not supply.
