# Social Login (WeChat, Douyin, Google and friends)

**Status:** Draft — design finalized 2026-09-11, nothing built
**Target:** Spree 6.0
**Depends on:** `6.0-platform-auth.md` — `Spree::UserIdentity`, the strategy registry, the redirect-strategy contract, and the admin SSO callback that is the reference implementation for everything here.
**Author:** Damian Legawiec + Claude
**Last updated:** 2026-09-11
**Tracking:** Linear — · GitHub 330437409/spree#1

## Summary

Spree 6.0 already contains most of what social login needs, just not the customer-facing half of it. `Spree::Authentication::Strategies::BaseStrategy` describes a provider as either `:password` or `:redirect`, gives it `#authorization_url(state:)` and `#callback`, and `Spree::Authentication::StrategyRegistry` publishes that self-description to a login page. `Spree::UserIdentity` stores a provider identity (`provider`, `uid`, polymorphic `user_type`) against a `Spree::Customer` or `Spree::AdminUser`. The Admin API already runs the whole redirect flow at `GET /api/v3/admin/auth/providers` and `GET /api/v3/admin/auth/callback/:provider`, terminating in the same JWT and refresh token a password login issues. The Store API has the login endpoint and the registry but **no discovery, no callback, and no provider that speaks to a Chinese platform**.

`spree-contrib/spree_social` cannot fill that gap. Its gemspec pins `spree_core < 5.0` and `spree_auth_devise < 5.0` so it cannot even install; its flow is Devise sessions and `sign_in_and_redirect`; its entry points are Deface overrides on ERB views that no longer exist; its credentials sit in a plaintext table with no uniqueness; it links an existing account on an email the provider never verified; and its last release was 2018, with the default branch frozen in 2021.

This plan replaces it with a provider gem, `spree_social_auth`, that adds **no new identity model, no new session mechanism, and no new admin UI**. Providers are strategy registrations; credentials are `Spree::Integration` subclasses configured on the dashboard's existing Integrations page; the browser redirect is owned by the storefront; and the code exchange terminates in the API v3 token pair. It ships WeChat Open Platform, Douyin and Google first, because a Spree store selling into mainland China cannot offer an account system without the first two — and Google is the cheapest way to prove the shared resolution rules end to end.

## Key Decisions (do not deviate without discussion)

- **A new gem, not a port (2026-09-11).** Nothing in `spree_social` survives except its problem statement. Porting it would mean carrying a Devise session model, Deface, ERB, a plaintext credential table and unverified-email linking into a codebase that has deliberately removed all five. The plan's first deliverable is therefore a gem whose only Spree coupling is the strategy registry, `Spree::UserIdentity` and `Spree::Integration` — all public extension points.

- **Reuse `Spree::UserIdentity`; add no identity table (2026-09-11).** `(provider, uid, user_type)` already models exactly a social identity, with a unique index and `find_or_create_from_oauth` doing the resolution. The only new table this plan causes is `spree_integrations`, which already exists. Legacy `spree_user_authentications` rows are migrated, not read at runtime.

- **Provider credentials live in a per-store `Spree::Integration` (2026-09-11).** A `SpreeSocialAuth::Integration` subclass per provider holds `client_id` / `client_secret` (and the provider-specific extras) as model preferences, with `integration_group = 'authentication'`, `logo_url` and `description` for the gallery card. This buys the merchant a working configuration screen, verify-before-activate, and secret masking for free, and it keeps credentials out of `ENV` where a multi-store install cannot scope them. The legacy `spree_authentication_methods` table — one row per environment, plaintext secret, no uniqueness — is not recreated in any form.

- **The storefront owns the browser redirect; the API owns the code exchange (2026-09-11).** The admin flow works because the dashboard and the API are the same origin, so the callback can set an httpOnly refresh cookie. The Next.js storefront is a different origin and already manages its own access and refresh tokens in cookies, so the same trick does not transfer. Instead the storefront sets its own `state` cookie, receives the provider's redirect on its own route, verifies `state`, and POSTs `{ provider, code, redirect_uri }` to the API; the API exchanges the code using the merchant's secret and answers with the same `{ token, refresh_token, user }` body password login returns. The storefront's existing post-auth bootstrap (store tokens, associate the guest cart, invalidate caches) then runs unchanged.

- **The strategy contract is extended, not bypassed (2026-09-11).** A redirect provider implements `#callback` and is reached through the same registry and the same `provider` dispatch the password strategy uses. No new endpoint per provider, no `omniauth` middleware, no Devise.

- **Customers auto-provision; admins never do (2026-09-11).** `Spree::UserIdentity.find_or_create_from_oauth` already creates a `Customer` on first social login, which is what a shopper expects from "Sign in with WeChat". The admin rule from `6.0-platform-auth.md` (unknown subject rejected, invitation required) is unchanged and this plan does not touch it.

- **Account linking requires a provider-verified email, and the rule lives in core (2026-09-11).** The OIDC rule from `6.0-platform-auth.md` applies to every provider that returns an email: an existing customer is adopted only when the provider asserts the address is verified, and a missing claim falls to a per-provider `trust_unverified_email` that defaults off. Providers that return no email at all (WeChat, Douyin, QQ, Weibo, Alipay) never link — they create a new account. `spree_social`'s `find_by_email(...) || new` is not carried over. **Settled 2026-09-11:** the three resolution rules move into `Spree::UserIdentity` so every provider — this gem's, a merchant's custom strategy, and the admin OIDC path — shares one implementation, rather than the gem carrying a private resolver that drifts from core. The trade-off is accepted knowingly: it changes `find_or_create_from_oauth` for existing custom strategies, which today create a second account when the email already exists. The change is a behaviour fix, and it ships with a spec covering each of the three rules and the refusal cases (unverified claim, explicit `false`).

- **A provider with no email creates the account with a placeholder address (2026-09-11).** `Spree::Customer` requires a unique email, and WeChat, Douyin, QQ, Weibo and Alipay return none. The customer is created as `"#{provider}_#{uid}@customers.invalid"` — `.invalid` is reserved by RFC 2606 and can never be routed — and the storefront prompts for a real address in the account area and before checkout. The alternative (block account creation until an email is supplied) was rejected: it puts a form between a shopper and the account they just authenticated for, which is the friction social login exists to remove.

- **First release ships WeChat, Douyin and Google (2026-09-11).** WeChat and Douyin are the reason for the work; Google is the most common Western provider and the one that exercises the verified-email linking path end to end. QQ, Weibo, Alipay, Apple, Facebook and GitHub are follow-ups against the same base class — one Integration subclass, one Strategy subclass, one cassette, one locale entry each. Alipay is deliberately last: every call is RSA2-signed rather than plain OAuth 2.0, so it needs a signing implementation of its own.

- **The gem lives in this monorepo at `spree/providers/social_auth` (2026-09-11).** The same slot, layout, release train and test harness as `spree/providers/wechat_pay`, which also means the WeChat knowledge already on this branch is one directory away rather than in another repository. A standalone repository (the `spree_social` arrangement) buys independence from upstream at the cost of maintaining a private CI, dummy app and version-alignment discipline for a gem whose only Spree coupling is three public extension points.

- **Identity is keyed on `unionid` when the provider has one (2026-09-11).** WeChat issues an app-scoped `openid` and a platform-scoped `unionid` once the apps are bound to the same Open Platform account. Storing the `unionid` as `uid` (and both in `info`) lets a shopper who signed in through the official account, a mini program or the website land on one customer record. Douyin has the same split (`open_id` / `union_id`); the rule is "`union_id` when present, else `open_id`".

- **No dependency on a payment gem (2026-09-11).** `spree_wechat_pay` (on this branch) already wraps WeChat's OAuth host and error codes for payment scenes. Social login must install without a payment gateway, so the small amount of shared knowledge (host, error-code meanings, timeout policy) is reimplemented in `spree_social_auth` rather than imported. Extracting a shared WeChat client is deliberately out of scope.

- **Plain OAuth 2.0 over Faraday, not OmniAuth strategies (2026-09-11).** The Ruby ecosystem settled this: of the providers in scope only Weibo has a maintained strategy (`omniauth-weibo-oauth2` 0.5.3, 2025-07); QQ's are from 2012–2014 and pinned to `omniauth ~> 1.0`; the Douyin gem's source repository is gone; the WeChat one (0.2.3, 2023) has an open OmniAuth 2.x question and targets the QR host anyway; Alipay's pins a 2017 `alipay` SDK. There is no Chinese-provider aggregator, and `omniauth_china` dates to 2011. Against that, every provider here is a server-to-server exchange that ends in an API v3 token pair, not a Rails session — OmniAuth's middleware adds a dependency and a version floor for little of its actual value. The clients are small: one `oauth2` / Faraday call for the token, one for the profile, with each provider's real shape handled explicitly. Alipay is the one provider a gem still wins for (`alipay` 0.17, RSA2 gateway signing), and it is a follow-up.

## Core Prerequisites

Four small additive changes in `spree/core`, `spree/api` and `packages/sdk`. They are listed here so the gem is not designed around something that does not exist; each has a named home and none is left as a question for the reader.

1. **Account resolution moves into `Spree::UserIdentity`.** The three rules (known identity → known customer with a provider-**verified** email → new customer) become the shared implementation in `find_or_create_from_oauth`, with `trust_unverified_email` per provider and an explicit `email_verified: false` always refused. Today the method only implements rules 1 and 3, so a Google shopper who already has a password account would silently get a second one. The admin OIDC strategy keeps its own stricter rule (unknown subject is rejected rather than created) and is unaffected.

2. **Store provider discovery — `GET /api/v3/store/auth/providers`.** Mirrors the admin endpoint: unauthenticated (it is read before login), rate limited on its own budget with the existing `auth/providers` pattern, returning `{ providers: [{ key, kind, label, authorization_url }] }` for the strategies enabled on the current store. Same contract as admin: never a client secret, never a class name. The `authorization_url` carries a signed, provider-bound `state` minted with `Rails.application.message_verifier`, exactly as `Admin::AuthController#issue_oauth_state` does today.

3. **A way for a registry entry to declare itself unavailable.** `StrategyRegistry#describe` currently lists every registered entry and drops only the ones whose authorization URL raises. A provider whose `Spree::Integration` is missing or inactive must not appear on a login page at all, so a factory gains an `available?` (default true) that `describe` consults, and `authorization_url` stops being the error path. Small, backwards compatible: entries that do not respond to `available?` stay listed.

4. **Store SDK + storefront support.** `client.auth.providers()` and `client.auth.login({ provider, code, redirect_uri, state })` in `@spree/sdk`; buttons on the storefront's `account/page.tsx` and `account/register/page.tsx`; one callback route handler that verifies `state` and calls the API. The storefront change lands in `spree/storefront` (`6-0-dev`), not here.

## Design Details

### Gem layout

`spree/providers/social_auth/` — the same slot and shape as `spree/providers/wechat_pay`:

```
spree/providers/social_auth/
├── app/
│   ├── models/spree_social_auth/integration.rb        # base Integration
│   ├── models/spree_social_auth/integrations/*.rb     # one per provider
│   ├── models/spree_social_auth/strategies/*.rb       # one per provider
│   └── services/spree_social_auth/*.rb                # client, errors, profile
├── config/locales/en.yml
├── lib/spree_social_auth/{engine,version}.rb
├── spec/ (dummy app, VCR cassettes per provider)
└── spree_social_auth.gemspec
```

One gem, not one per provider: the OAuth 2.0 base, the error vocabulary, the profile normalisation and the resolution rules are shared, and six gems would duplicate them. A provider that grows an unusual dependency (Alipay's RSA2 signing) or an SDK can be extracted later without moving its table — there is none.

Each further provider is one Integration subclass, one Strategy subclass, one cassette and one locale entry — `qq`, `weibo`, `apple`, `facebook`, `github`, then `alipay` last.

#### Provider wiring notes

Endpoints and identity fields below are taken from each provider's current documentation; the parameter names are recorded because they differ enough that a single "generic OAuth 2.0" client would be wrong for four of the six.

- **WeChat — `appid` / `secret`, not `client_id` / `client_secret`.** Authorization is `https://open.weixin.qq.com/connect/qrconnect?...&scope=snsapi_login#wechat_redirect` — the `#wechat_redirect` fragment is mandatory and the parameter order is validated. Exchange: `GET https://api.weixin.qq.com/sns/oauth2/access_token?appid=&secret=&code=&grant_type=authorization_code`; profile: `GET https://api.weixin.qq.com/sns/userinfo?access_token=&openid=`. **Failures return HTTP 200 with `{"errcode":…,"errmsg":…}`**, so the client must read the body, never the status — the exact trap `SpreeWechatPay::Oauth` documents. Codes live 10 minutes and are single-use; the access token lives 2 hours and the refresh token 30 days and cannot be renewed. `unionid` is the only cross-app key and is present because this flow always takes userinfo authorization. Since 2021 the profile omits `sex`, `province` and `city`, and `headimgurl` expires when the shopper changes their avatar — so it is a display value, not an identity.
- **Douyin — `client_key` / `client_secret`.** Authorization `https://open.douyin.com/platform/oauth/connect?client_key=&response_type=code&scope=user_info&redirect_uri=&state=`. Exchange is a form-encoded `POST https://open.douyin.com/oauth/access_token/`; profile is `POST https://open.douyin.com/oauth/userinfo/` with `access_token` and `open_id`. The `redirect_uri` must be `https`, must match the registered callback domain, and **must not carry query parameters** — anything extra belongs in `state`. Access token 15 days, refresh token 30 days, renewable five times. Errors are HTTP 200 with `error_code` in the body, and the envelope is inconsistent (`{data, message}` for OAuth, `{data, err_no, err_msg}` for userinfo), so the parser tolerates both.
- **WeChat Official Account and Mini Program are different flows, and out of scope for the first release.** The official account uses `oauth2/authorize` with `snsapi_base` (silent, openid only) or `snsapi_userinfo` (profile), needs a certified service account, and only returns a `unionid` under `snsapi_userinfo`. The mini program's `jscode2session` is a code-for-session exchange, not a browser login at all. Both become additional providers later, sharing the WeChat client.
- **QQ — the openid is a second call.** `GET https://graph.qq.com/oauth2.0/me?access_token=` answers JSONP, not JSON, and only then is `get_user_info` possible. The token endpoint answers form-urlencoded text by default, so `fmt=json` is used. Errors come back as a url-encoded `error=…&error_description=…` query string.
- **Weibo — no refresh token for web apps.** `uid` comes back on the token response; the platform warns against trusting it alone, so the client validates through `oauth2/get_token_info` and matches the app key. `expires_in` is a string in the payload.
- **Alipay — not OAuth 2.0 in practice.** Every call is an RSA2-signed `gateway.do` request (`alipay.system.oauth.token`, then `alipay.user.info.share`), and the callback parameter is `auth_code`, not `code`. It needs the `alipay` gem or a small signing implementation, which is why it is last despite being a common request.

#### Merchant prerequisites (China)

The gem cannot hide these, so the documentation that ships with it must state them plainly:

- Every provider needs a reviewed application: WeChat Open Platform needs developer certification plus website-app review, Douyin needs a website app through platform review, QQ and Weibo need a reviewed app, Alipay needs real-name verification and product signing (签约).
- The redirect URI must be registered with each provider and match exactly — WeChat requires the callback domain in the console, Douyin requires the callback domain and no extra query parameters, QQ requires the redirect to sit under the registered main domain.
- WeChat's website-app review expects the site itself to show company information, a user agreement, a copyright notice and an **ICP备案号**; the review processes generally assume a mainland-China legal entity. Merchants outside China should expect WeChat and Douyin to be the slow part, not the integration.
- Profile data leaving mainland China engages PIPL, and provider endpoints are far from non-China infrastructure. A deployment serving Chinese shoppers should reach the providers from a China-region egress; the plugin keeps its timeouts short and never blocks a request on a slow provider.

### One base strategy, one subclass per provider

```ruby
module SpreeSocialAuth
  module Strategies
    # Shared OAuth 2.0 authorization-code flow. Subclasses declare their
    # endpoints and what to read out of the profile; nothing else differs.
    class Oauth2Strategy < Spree::Authentication::Strategies::BaseStrategy
      class << self
        def kind = :redirect
      end

      def provider = self.class.provider_key

      def authorization_url(state:)
        "#{authorize_url}?#{authorize_params(state:).to_query}"
      end

      # The storefront sends the code here; the secret stays server-side.
      def callback
        return failure(Spree.t('spree_social_auth.errors.expired_code')) if params[:code].blank?
        return failure(Spree.t('spree_social_auth.errors.unknown_provider')) unless integration&.active?

        profile = fetch_profile(exchange_code(params[:code]))
        find_or_create_user_from_oauth(
          provider: self.class.provider_key,
          uid: profile.uid,
          info: profile.info,
          tokens: profile.tokens
        )
      end
    end
  end
end
```

Subclass surface: `authorize_url`, `authorize_params`, `token_url`, `token_params`, `userinfo_url`, `normalize_profile`, and the credentials (`integration.client_id` / `integration.client_secret`). The store's active integration is read from `Spree::Current.integrations` (already memoised per request), so a request for store A can never exchange against store B's app credentials.

### Credentials: one Integration per provider

```ruby
module SpreeSocialAuth
  class Integrations::WeChat < Integration
    preference :client_id, :string
    preference :client_secret, :password
    preference :trust_unverified_email, :boolean, default: false   # unused by WeChat — no email

    def self.integration_group = 'authentication'
    def self.logo_url = ... # data: URI, self-contained like the other provider gems
  end
end
```

Registered from the engine with `Spree.integrations << 'SpreeSocialAuth::Integrations::WeChat'`, which makes each provider a card on `Settings → Integrations` and its credentials editable there with the existing schema-driven form. `can_connect?` is a credentials-completeness check plus, where the provider offers a cheap unauthenticated endpoint, one live call — so "activate" fails loudly on a wrong secret instead of at the shopper's first login.

The strategies are registered by a single engine initializer that walks the same list, so registering a provider is one `Spree.integrations <<` line plus one `Spree.store_authentication_strategies.add`. The factory holds the key and label and reads the credentials per request; `available?` is true only when this store has an active integration for it.

### Account resolution

The three rules live in `Spree::UserIdentity.find_or_create_from_oauth`, so every strategy — this gem's, an admin OIDC registration, a merchant's own custom provider — resolves an identity the same way:

1. **Known identity** — `(provider, uid, user_type)` exists. Log in, refresh `info` and tokens.
2. **Existing customer, first social login, verified email** — the provider asserts `email_verified` (or the integration opts into `trust_unverified_email` because the directory owns its addresses), and a customer with that address exists. Create the identity against that customer and log in. `find_user_by_email` already matches case-insensitively, which matters because Spree normalises email by squishing only. An explicit `email_verified: false` is always refused, whichever way the provider is configured.
3. **Unknown** — create the customer, then the identity. This is what shoppers expect from "Sign in with WeChat"; the admin path keeps its opposite rule (unknown subject rejected, invitation required).

For providers that return no email, rule 3 runs every time, with the placeholder address described under Key Decisions (`"#{provider}_#{uid}@customers.invalid"`). The account works from the first second — cart, orders, addresses, wishlist — and the storefront asks for a real address in the account area and before checkout, which is exactly the state a WeChat-only shopper is in until they give one.

Consumers merge into one identity store scoped by `(provider, uid, user_type)`, so a shop that removes a provider and adds it back reuses the same rows, and an SSO admin and an SSO customer with the same email stay distinct records — the same guarantee the OIDC callback relies on today.

### Store API surface

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | `/api/v3/store/auth/providers` | publishable key | Enabled providers for this store, with authorization URLs |
| POST | `/api/v3/store/auth/login` | publishable key | Existing endpoint; a `provider` whose strategy is `:redirect` is served by `#callback` instead of `#authenticate` |

The second row is the whole API change: one branch in `Store::AuthController#create`, dispatching `:redirect` strategies to `callback`. The alternative — a separate `POST /store/auth/social` — is rejected because the dispatch by `provider` already exists and a second endpoint would duplicate rate limiting, error rendering and token issuance.

`state` is signed by the API (message verifier, 15-minute expiry, payload carries the provider key), so the storefront cannot mint one and a state issued for `wechat` cannot be replayed at `douyin`. The storefront keeps it in an httpOnly cookie between the two legs; the API re-verifies it on the exchange. The admin controller's `issue_oauth_state` / `valid_oauth_state?` is the reference, extracted to a shared concern rather than copied.

### The storefront flow

1. Login page loads → `client.auth.providers()` → one button per provider, ordered by the registry.
2. Shopper taps "WeChat" → storefront stores `state` in an httpOnly cookie and redirects the browser to `authorization_url`.
3. WeChat shows its QR page; on scan the browser returns to `/account/callback/wechat?code=…&state=…` on the storefront.
4. The route handler verifies the cookie's `state`, then `client.auth.login({ provider: 'wechat', code, state, redirect_uri })`.
5. The API exchanges the code, resolves the customer, and returns `{ token, refresh_token, user }` — the same body password login returns.
6. The storefront's existing bootstrap stores the tokens, associates the guest cart, and redirects into the account area.

Errors surface on the login page as a query parameter, as the dashboard login page already does — not as a JSON body the shopper cannot act on.

### Errors

Provider failures must name what to fix, per the house rule for third-party APIs. Each client translates the provider's codes: a spent or expired authorization code is the shopper's to retry (WeChat 10 minutes, Douyin 10 minutes, both single-use); rejected credentials (`40013`/`40125` on WeChat, `10013`/`10003` on Douyin, a signature failure on Alipay) name the integration to re-check; a network failure is reported as such and never as "login failed". Two rules are absolute, because the providers break the assumptions a generic client makes: **WeChat and Douyin return failures with HTTP 200**, so the body decides success, never the status; and QQ returns a url-encoded query string rather than JSON on error. `SpreeWechatPay::Oauth` on this branch is the precedent for the wording and the timeout policy (short open/read timeouts, because the exchange runs inside a shopper's request) — the gem reimplements it rather than depending on that gem.

### Security

- Secrets stay server-side; the discovery endpoint exposes `client_id` only inside the authorization URL, as OAuth requires.
- `state` is signed, expiring and provider-bound; the storefront additionally keeps its own cookie.
- Linking requires a verified email; an explicit `email_verified: false` is always refused.
- Provider tokens are stored on the identity for later API calls (WeChat userinfo only, today) and are never placed in a cookie or a URL.
- The login exchange is rate limited per IP on its own budget so a shopper is never locked out by login-page traffic, and vice versa.
- The callback accepts only `POST` from the storefront; the browser never lands on the API.

### Testing

RSpec with the gem's own dummy app, in the shape of `spree/providers/wechat_pay/spec`: strategy specs with Faraday stubbed for the happy path, the three resolution rules, and each translated error; VCR cassettes for one real exchange per provider, with tokens, codes and secrets filtered; request specs for the two store endpoints (`providers` payload shape, `state` rejection, redirect strategy dispatch, token issuance); an integration spec asserting an identity is unique per `(provider, uid, user_type)` and that two providers with the same email stay two identities unless rule 2 applies. No network in CI.

## Migration Path

1. **Core (this repository).** Store `auth/providers` + `auth/callback` dispatch, the `available?` filter in `StrategyRegistry#describe`, and the verified-email linking rule. Small, additive, independently reviewable; the gem is not required to land first.
2. **Gem.** `spree_social_auth` with WeChat + Douyin + Google, its dummy app and cassettes.
3. **SDK.** `auth.providers()` and the redirect-provider login call.
4. **Storefront.** Buttons, one callback route, error copy.
5. **Merchants on Spree ≤ 5 with `spree_social`.** No in-place upgrade: the gem cannot install on 6.0 and its session model does not exist. A merchant moving to 6.0 either stays on Spree 5, or adopts the new gem and lets shoppers re-link. A one-off task (`spree:social_auth:import_legacy_identities`) can copy `spree_user_authentications` rows into `spree_user_identities` for providers whose `uid` scheme is unchanged (Facebook, Google, GitHub, Twitter-as-X are app-scoped and stable), which preserves the linked accounts even though the login flow is new.

## Constraints on Current Work

- **Do not extend `spree_social`.** No compatibility shim, no shared table, no reading `spree_user_authentications` at runtime.
- **Register providers through `Spree.store_authentication_strategies`.** A new endpoint per provider, or a second dispatch mechanism, is the thing this design exists to avoid.
- **Never link an account on an email the provider did not verify.** If a provider's email semantics are unclear, treat the email as absent.
- **Never put client secrets in `ENV` as the primary mechanism.** A store-scoped `Spree::Integration` is the only supported placement; `ENV` may seed it in a script, never replace it.
- **Never store provider tokens in cookies, sessions or URLs.**
- **Keep the gem independent of payment gems.** Do not call into `spree_wechat_pay`, and do not move WeChat knowledge into a shared gem before a second consumer needs it.
- **Never treat an HTTP status as the provider's verdict.** WeChat and Douyin answer failures with 200 and an error code in the body; QQ answers a url-encoded string. The body is the contract.
- **Identity keys are stable.** `provider` values (`wechat`, `douyin`, …) are what `UserIdentity` stores forever; renaming one orphans every linked account, exactly as the `wished_item` → `wishlist_item` rename had to keep its prefix ID.

## Open Questions

The four design questions this plan opened were settled on 2026-09-11 and now live under Key Decisions (resolution rules in core; placeholder email; first-release provider set; gem home). What remains genuinely deferred:

1. **`can_connect?` for providers with no cheap unauthenticated endpoint.** WeChat, Douyin and QQ cannot be verified without a shopper's authorization code, so "activate" can only check that credentials are present, with real verification left to the first login. Is a presence check acceptable, or should activation for those providers stay unverified-but-allowed while a "test" button simply states that? *Deferred to the Integration pull request; either answer changes only that class.*
2. **Does the guest cart survive the redirect?** The storefront associates the guest cart after login today. Through a provider redirect the cart cookie survives only if the callback returns to the same origin with the same `X-Spree-Token` — worth proving in the storefront spike before the UI work, because a lost cart is the bug that reads as "WeChat checkout is broken". *Blocked on the storefront spike, not on this plan.*
3. **Mini programs and the official account.** Both are WeChat flows with their own identity rules (`snsapi_base` vs `snsapi_userinfo`, `jscode2session`'s session key). They are out of the first release; whether they arrive as extra providers on the store registry or as a separate "mobile" surface is unresolved until a merchant needs them. *Unblocked by demand.*
4. **Alipay: `alipay` gem or a small in-gem RSA2 signer?** The gem saves the signing work and adds a dependency whose last release predates Rails 8. *Deferred to the Alipay pull request.*
