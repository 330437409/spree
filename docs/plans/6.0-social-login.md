# Social Login (WeChat, Douyin, Google and friends)

**Status:** Complete — design finalized 2026-09-11 (rev 3 after the strategy surface was built). Shipped: Phase 1 (core resolution, the registration step, store provider discovery and redirect dispatch), Phase 2's WeChat provider, Phase 3's Douyin provider, Phase 4's Google provider, Phase 5 (the store SDK), Phase 6 (the storefront — buttons, callback route, completion screen and error copy, on `spree/storefront` branch `feat/social-login`) and Phase 7 (merchant guides under `docs/integrations/authentication/`).
**Target:** Spree 6.0
**Depends on:** `6.0-platform-auth.md` — `Spree::UserIdentity`, the strategy registry, the redirect-strategy contract, and the admin SSO callback that is the reference implementation for everything here.
**Author:** Damian Legawiec + Claude

## Summary

Spree 6.0 already contains most of what social login needs, just not the customer-facing half of it. `Spree::Authentication::Strategies::BaseStrategy` describes a provider as either `:password` or `:redirect`, gives it `#authorization_url(state:)` and `#callback`, and `Spree::Authentication::StrategyRegistry` publishes that self-description to a login page. `Spree::UserIdentity` stores a provider identity (`provider`, `uid`, polymorphic `user_type`) against a `Spree::Customer` or `Spree::AdminUser`. `Spree::Customers::Create` (`Spree.customer_create_workflow`) is the single storefront registration flow, with policy hooks, consent recording and password-less accounts. The Admin API already runs the whole redirect flow at `GET /api/v3/admin/auth/providers` and `GET /api/v3/admin/auth/callback/:provider`, terminating in the same JWT and refresh token a password login issues. The Store API has the login endpoint and the registry but **no discovery, no callback, and no provider that speaks to a Chinese platform**.

`spree-contrib/spree_social` cannot fill that gap. Its gemspec pins `spree_core < 5.0` and `spree_auth_devise < 5.0` so it cannot even install; its flow is Devise sessions and `sign_in_and_redirect`; its entry points are Deface overrides on ERB views that no longer exist; its credentials sit in a plaintext table with no uniqueness; it links an existing account on an email the provider never verified; and its last release was 2018, with the default branch frozen in 2021.

This plan replaces it with a provider gem, `spree_social_auth`, that adds **no new identity model, no new session mechanism, and no new admin UI**. Providers are strategy registrations; credentials are `Spree::Integration` subclasses configured on the dashboard's existing Integrations page; the browser redirect is owned by the storefront; account creation runs through the existing customer workflow; and the flow terminates in the API v3 token pair. It ships WeChat Open Platform, Douyin and Google first, because a Spree store selling into mainland China cannot offer an account system without the first two — and Google is the cheapest way to prove the shared resolution rules end to end.

## Key Decisions (do not deviate without discussion)

- **A new gem, not a port (2026-09-11).** Nothing in `spree_social` survives except its problem statement. Porting it would mean carrying a Devise session model, Deface, ERB, a plaintext credential table and unverified-email linking into a codebase that has deliberately removed all five. The plan's first deliverable is therefore a gem whose only Spree coupling is the strategy registry, `Spree::UserIdentity`, `Spree::Customers::Create` and `Spree::Integration` — all public extension points.

- **Reuse `Spree::UserIdentity`; add no identity table (2026-09-11).** `(provider, uid, user_type)` already models exactly a social identity, with a unique index. The only new table this plan causes is `spree_integrations`, which already exists. Legacy `spree_user_authentications` rows are migrated, not read at runtime.

- **Provider credentials live in a per-store `Spree::Integration` (2026-09-11).** A `SpreeSocialAuth::Integration` subclass per provider holds `client_id` / `client_secret` (and the provider-specific extras) as model preferences, with `integration_group = 'authentication'`, `logo_url` and `description` for the gallery card. This buys the merchant a working configuration screen, verify-before-activate, and secret masking for free, and it keeps credentials out of `ENV` where a multi-store install cannot scope them. The legacy `spree_authentication_methods` table — one row per environment, plaintext secret, no uniqueness — is not recreated in any form.

- **The storefront owns the browser redirect; the API owns the code exchange (2026-09-11).** The admin flow works because the dashboard and the API are the same origin, so the callback can set an httpOnly refresh cookie. The Next.js storefront is a different origin and already manages its own access and refresh tokens in cookies, so the same trick does not transfer. Instead the storefront receives the provider's redirect on its own route, checks its own `state` cookie, and POSTs `{ provider, code, state, redirect_uri }` to the API; the API re-verifies the signed `state`, exchanges the code using the merchant's secret, and answers with the same `{ token, refresh_token, user }` body password login returns. The storefront's existing post-auth bootstrap (store tokens, associate the guest cart, invalidate caches) then runs unchanged.

- **The strategy contract is extended, not bypassed (2026-09-11).** A redirect provider implements `#callback` and is reached through the same registry and the same `provider` dispatch the password strategy uses. No new endpoint per provider, no `omniauth` middleware, no Devise.

- **Customers auto-provision; admins never do (2026-09-11).** A shopper who authenticates with a provider gets an account, which is what "Sign in with WeChat" promises. The admin rule from `6.0-platform-auth.md` (unknown subject rejected, invitation required) is unchanged and this plan does not touch it — it lives in the OIDC strategy's own resolution. A merchant's custom *staff* strategy keeps provisioning its own accounts through `UserIdentity.find_or_create_from_oauth`, which is unchanged for a non-customer user class.

- **Account creation runs through `Spree.customer_create_workflow` (2026-09-11, rev 2).** `Spree::UserIdentity.create_user_from_oauth` calls `user_class.create!` directly, which bypasses the one registration flow core documents: the `validate` veto hook (bot/disposable-email screening, fraud checks, B2B approval), the `after_create` hook, terms/consent recording, newsletter-subscriber linking, and the password-less account mode (`password_required: false`). Social registration is still registration; a shop's registration policy must not be optional depending on which button the shopper pressed. The gem's strategies therefore call the workflow, and `find_or_create_from_oauth` keeps only the identity lookup and identity attachment.

- **Account linking requires a provider-verified email (2026-09-11; corrected 2026-09-11 rev 2).** An existing customer is adopted only when the provider asserts `email_verified` (or the integration opts into `trust_unverified_email` because the directory owns its addresses); an explicit `email_verified: false` is always refused. Providers that return no email never link. `spree_social`'s `find_by_email(...) || new` is not carried over. **The current behaviour is worse than the first draft of this plan claimed:** `UserIdentity.find_or_create_from_oauth` does not create a duplicate account for an email that already exists — it raises `ActiveRecord::RecordInvalid: Email has already been taken` (only `RecordNotUnique` is rescued), which surfaces as a failed login at best and a 500 at worst. Verified by running it. This change is therefore a fix to a broken login path, not a convenience, and it ships with a spec for each rule and each refusal.

- **A provider that returns no email gets one registration screen, and the account is password-less (2026-09-11 rev 2).** The first draft created the customer with a synthetic `@customers.invalid` address and asked for a real one later. That path is a dead end: the account is created with a random password (`SecureRandom.hex(32)`) the shopper never sees, changing an email through `PATCH /customers/me` requires `current_password` (`Store::CustomersController#sensitive_update?`), and a password-reset link goes to the placeholder address — so the shopper could never supply a real email at all. And an order placed before they did would send its confirmation to an unroutable domain (see below). Instead, when the provider returns no usable email, the API does not create anything: it returns a short-lived signed `registration_token`, the storefront asks for the email (one screen, prefilled with nothing else), and account creation completes through `Spree.customer_create_workflow` with `password_required: false`. The account has no password until the shopper claims one through the normal reset flow, exactly like the account the checkout "create an account" box already creates. No synthetic address is ever stored.

- **No consumer email ever goes to an address that cannot receive it (2026-09-11 rev 2).** `spree_emails` ships installed and mails `@order.email`; Spree validates only the address's shape, so a synthetic address passes. The registration step removes the case entirely, and the plan keeps it that way by refusing to create accounts without a real address.

- **The `redirect_uri` is the merchant's registered callback, and the storefront's value must match it (2026-09-11 rev 2; refined 2026-09-11 while building the gem).** A provider rejects a token exchange whose `redirect_uri` differs from the one used to authorize, so the value is stored on the provider's `Integration` — the same URL the merchant registers in the provider's console — and both halves of the flow use it. A request carrying a different value is refused before anything is exchanged, and the API never relays a caller-supplied URL to the provider. The controller still checks `store.allowed_origin?(redirect_uri)` on top, so a foreign origin is rejected at the surface too.

- **The signed `state` binds the store as well as the provider (2026-09-11 rev 2).** The registry is process-global while integrations are per store, so the payload carries `store_id` beside the provider key; a state minted on one store's login page cannot complete on another's.

- **Provider tokens on the identity are encrypted at rest (2026-09-11 rev 2).** `spree_user_identities.access_token` and `refresh_token` are plain string columns today — the model comment claiming they are encrypted is wrong. A WeChat refresh token is valid for 30 days and is a credential to the shopper's profile, so the columns get the same treatment the codebase already applies to comparable secrets: `encrypts :access_token, :refresh_token if Rails.configuration.active_record.encryption.include?(:primary_key)`, the pattern in `Spree::WebhookEndpoint` and `Spree::GatewayCustomer`.

- **First release ships WeChat, Douyin and Google (2026-09-11).** WeChat and Douyin are the reason for the work; Google is the most common Western provider and the one that exercises the verified-email linking path end to end. QQ, Weibo, Alipay, Apple, Facebook and GitHub are follow-ups against the same base class — one Integration subclass, one Strategy subclass, one stubbed spec, one locale entry each. Alipay is deliberately last: every call is RSA2-signed rather than plain OAuth 2.0, so it needs a signing implementation of its own.

- **The gem lives in this monorepo at `spree/providers/social_auth` (2026-09-11).** The same slot, layout, release train and test harness as `spree/providers/wechat_pay`, which also means the WeChat knowledge already on this branch is one directory away rather than in another repository. A standalone repository (the `spree_social` arrangement) buys independence from upstream at the cost of maintaining a private CI, dummy app and version-alignment discipline for a gem whose Spree coupling is four public extension points.

- **Identity is keyed on `unionid` when the provider has one (2026-09-11).** WeChat issues an app-scoped `openid` and a platform-scoped `unionid` once the apps are bound to the same Open Platform account. Storing the `unionid` as `uid` (and both in `info`) lets a shopper who signed in through the official account, a mini program or the website land on one customer record. Douyin has the same split (`open_id` / `union_id`); the rule is "`union_id` when present, else `open_id`".

- **No dependency on a payment gem (2026-09-11).** `spree_wechat_pay` (on this branch) already wraps WeChat's OAuth host and error codes for payment scenes. Social login must install without a payment gateway, so the small amount of shared knowledge (host, error-code meanings, timeout policy) is reimplemented in `spree_social_auth` rather than imported. Extracting a shared WeChat client is deliberately out of scope.

- **Plain OAuth 2.0 over Faraday, not OmniAuth strategies (2026-09-11).** The Ruby ecosystem settled this: of the providers in scope only Weibo has a maintained strategy (`omniauth-weibo-oauth2` 0.5.3, 2025-07); QQ's are from 2012–2014 and pinned to `omniauth ~> 1.0`; the Douyin gem's source repository is gone; the WeChat one (0.2.3, 2023) has an open OmniAuth 2.x question and targets the QR host anyway; Alipay's pins a 2017 `alipay` SDK. There is no Chinese-provider aggregator, and `omniauth_china` dates to 2011. Against that, every provider here is a server-to-server exchange that ends in an API v3 token pair, not a Rails session — OmniAuth's middleware adds a dependency and a version floor for little of its actual value. The clients are small: one `oauth2` / Faraday call for the token, one for the profile, with each provider's real shape handled explicitly. Alipay is the one provider a gem still wins for (`alipay` 0.17, RSA2 gateway signing), and it is a follow-up.

## Core Prerequisites

Five additive changes in `spree/core`, `spree/api` and `packages/sdk`. Each has a named home; none is left as a question for the reader. Two of them (1 and 2) touch existing behaviour and deserve their own pull requests.

1. **Account resolution and provisioning in core.** Two changes in one seam:
   - **Resolution** — three rules on `Spree::UserIdentity` (or a small resolver it delegates to): known identity → known customer with a provider-**verified** email → no account. The third case is no longer "create a customer"; it is a decision the caller makes (see 2).
   - **Provisioning** — account creation moves onto `Spree.customer_create_workflow`, so social registration gets the same `validate`/`after_create` hooks, consent recording and password-less account mode as form registration. `find_or_create_from_oauth` keeps the identity lookup, the identity attachment, and the token/`info` refresh.
   - The current failure — `RecordInvalid` when the email is taken — disappears because the taken-email case is now rule 2 rather than a `create!` collision.
   - `Spree::CustomerMethods` gains (or `UserIdentity` borrows) the case-insensitive email lookup that today lives only on `BaseStrategy#find_user_by_email`, because Spree normalises email by squishing and never downcasing.

2. **The registration step — `POST /api/v3/store/auth/complete`.** When the exchange finds no identity and no usable email, the API creates nothing and answers `{ status: 'registration_required', registration_token: '<signed, 15 min>' }`. The token carries `{ provider, uid, info, tokens, store_id }`; the storefront collects an email and posts it back to `complete`, which verifies the token, runs `Spree.customer_create_workflow` (`password_required: false`), attaches the identity, and issues the token pair. A signed token rather than a server-side pending record: the API is stateless between the two calls, and the provider's authorization code is already spent by the first one.

3. **Store provider discovery — `GET /api/v3/store/auth/providers`.** Mirrors the admin endpoint: unauthenticated (it is read before login), rate limited on its own budget with the existing `auth/providers` pattern, returning `{ providers: [{ key, kind, label, requires_email, authorization_url }] }` for the strategies enabled on the current store. `requires_email` lets the storefront warn before the redirect that this provider needs one more step; it is static per provider and derives from the strategy. Same contract as admin otherwise: never a client secret, never a class name. The `authorization_url` carries a signed `state` (provider key + store id) minted with `Rails.application.message_verifier`, exactly as `Admin::AuthController#issue_oauth_state` does today.

4. **A way for a registry entry to declare itself unavailable.** `StrategyRegistry#describe` currently lists every registered entry and drops only the ones whose authorization URL raises. A provider whose `Spree::Integration` is missing or inactive must not appear on a login page at all, so a factory gains an `available?` (default true) that `describe` consults. Small, backwards compatible: entries that do not respond to `available?` stay listed.

5. **Store SDK + storefront support.** `client.auth.providers()`, the redirect-provider login call, and `client.auth.completeRegistration(...)` in `@spree/sdk`; buttons on the storefront's `account/page.tsx` and `account/register/page.tsx`; one callback route handler and one email-completion screen. The storefront change lands in `spree/storefront` (`6-0-dev`), not here.

## Design Details

### Gem layout

`spree/providers/social_auth/` — the same slot and shape as `spree/providers/wechat_pay`:

```
spree/providers/social_auth/
├── app/
│   ├── models/spree_social_auth/integration.rb        # base Integration
│   ├── models/spree_social_auth/integrations/*.rb     # one per provider
│   ├── models/spree_social_auth/strategies/*.rb       # one per provider
│   └── services/spree_social_auth/*.rb                # client, profile, errors
├── config/locales/en.yml
├── lib/spree_social_auth/{engine,version}.rb
├── spec/ (dummy app, WebMock-stubbed provider responses)
└── spree_social_auth.gemspec
```

One gem, not one per provider: the OAuth 2.0 base, the error vocabulary and the profile normalisation are shared, and six gems would duplicate them. A provider that grows an unusual dependency (Alipay's RSA2 signing) or an SDK can be extracted later without moving its table — there is none.

#### Provider wiring notes

Endpoints and identity fields below are taken from each provider's current documentation; the parameter names are recorded because they differ enough that a single "generic OAuth 2.0" client would be wrong for four of the six.

- **WeChat — `appid` / `secret`, not `client_id` / `client_secret`.** Authorization is `https://open.weixin.qq.com/connect/qrconnect?...&scope=snsapi_login#wechat_redirect` — the `#wechat_redirect` fragment is mandatory and the parameter order is validated. Exchange: `GET https://api.weixin.qq.com/sns/oauth2/access_token?appid=&secret=&code=&grant_type=authorization_code`; profile: `GET https://api.weixin.qq.com/sns/userinfo?access_token=&openid=`. **Failures return HTTP 200 with `{"errcode":…,"errmsg":…}`**, so the client must read the body, never the status — the exact trap `SpreeWechatPay::Oauth` documents. Codes live 10 minutes and are single-use; the access token lives 2 hours and the refresh token 30 days and cannot be renewed. `unionid` is the only cross-app key and is present because this flow always takes userinfo authorization. Since 2021 the profile omits `sex`, `province` and `city`, and `headimgurl` expires when the shopper changes their avatar — so it is a display value, not an identity.
- **Douyin — `client_key` / `client_secret`.** Authorization `https://open.douyin.com/platform/oauth/connect?client_key=&response_type=code&scope=user_info&redirect_uri=&state=`. Exchange is a form-encoded `POST https://open.douyin.com/oauth/access_token/`; profile is `POST https://open.douyin.com/oauth/userinfo/` with `access_token` and `open_id`. The `redirect_uri` must be `https`, must match the registered callback domain, and **must not carry query parameters** — anything extra belongs in `state`. Access token 15 days, refresh token 30 days, renewable five times. Errors are HTTP 200 with `error_code` in the body, and the envelope is inconsistent (`{data, message}` for OAuth, `{data, err_no, err_msg}` for userinfo), so the parser tolerates both.
- **WeChat Official Account and Mini Program are different flows, and out of scope for the first release.** The official account uses `oauth2/authorize` with `snsapi_base` (silent, openid only) or `snsapi_userinfo` (profile), needs a certified service account, and only returns a `unionid` under `snsapi_userinfo`. The mini program's `jscode2session` is a code-for-session exchange, not a browser login at all. Both become additional providers later, sharing the WeChat client.
- **QQ — the openid is a second call.** `GET https://graph.qq.com/oauth2.0/me?access_token=` answers JSONP, not JSON, and only then is `get_user_info` possible. The token endpoint answers form-urlencoded text by default, so `fmt=json` is used. Errors come back as a url-encoded `error=…&error_description=…` query string.
- **Weibo — no refresh token for web apps.** `uid` comes back on the token response; the platform warns against trusting it alone, so the client validates through `oauth2/get_token_info` and matches the app key. `expires_in` is a string in the payload.
- **Alipay — not OAuth 2.0 in practice.** Every call is an RSA2-signed `gateway.do` request (`alipay.system.oauth.token`, then `alipay.user.info.share`), and the callback parameter is `auth_code`, not `code`. It needs the `alipay` gem or a small signing implementation, which is why it is last despite being a common request.

#### Merchant prerequisites (China)

The gem cannot hide these, so the documentation that ships with it must state them plainly:

- Every provider needs a reviewed application: WeChat Open Platform needs developer certification plus website-app review, Douyin needs a website app through platform review, QQ and Weibo need a reviewed app, Alipay needs real-name verification and product signing (签约).
- The redirect URI must be registered with each provider and match exactly — WeChat requires the callback domain in the console, Douyin requires the callback domain and no extra query parameters, QQ requires the redirect to sit under the registered main domain.
- WeChat's website-app review expects the site itself to show company information, a user agreement, a copyright notice and an **ICP备案号**; the review processes generally assume a mainland-China legal entity. Merchants outside China should expect WeChat and Douyin to be the slow part, not the integration.
- Profile data leaving mainland China engages PIPL, and provider endpoints are far from non-China infrastructure. A deployment serving Chinese shoppers should reach the providers from a China-region egress; the plugin keeps its timeouts short and never blocks a request on a slow provider.

The merchant-facing version of this list ships under `docs/integrations/authentication/`, with one page per provider.

### One base strategy, one subclass per provider

```ruby
module SpreeSocialAuth
  module Strategies
    # Shared OAuth 2.0 authorization-code flow. Subclasses declare their
    # endpoints and what to read out of the profile; nothing else differs.
    class Oauth2Strategy < Spree::Authentication::Strategies::BaseStrategy
      class << self
        def kind = :redirect

        # Providers that return no email need the registration screen. The
        # discovery endpoint publishes this so the storefront can say so up front.
        def requires_email = true
      end

      def provider = self.class.provider_key

      def authorization_url(state:)
        "#{authorize_url}?#{authorize_params(state:).to_query}"
      end

      # The storefront sends the code here; the secret stays server-side.
      def callback
        return failure(Spree.t('spree_social_auth.errors.expired_code')) if params[:code].blank?
        return failure(Spree.t('spree_social_auth.errors.unknown_provider')) unless integration&.active?

        profile = profile_from(params[:code])

        identity = Spree::UserIdentity.find_by(
          provider: self.class.provider_key, uid: profile.uid, user_type: user_class.name
        )
        return success(identity.user.tap { identity.refresh!(profile) }) if identity

        linkable = profile.verified_email.present? ? find_user_by_email(profile.verified_email) : nil
        return success(attach_identity(linkable, profile)) if linkable

        # No account and no usable email: hand back a signed token instead of
        # creating a customer with an address that cannot receive mail.
        registration_required(profile)
      end
    end
  end
end
```

Subclass surface: `authorize_url`, `authorize_params`, `token_url`, `token_params`, `userinfo_url`, `normalize_profile`, `requires_email`, and the credentials (`integration.client_id` / `integration.client_secret`). The store's active integration is read from `Spree::Current.integrations` (already memoised per request), so a request for store A can never exchange against store B's app credentials.

The `registration_required` result is what `Store::AuthController#create` turns into the `{ status: 'registration_required', registration_token: … }` body; a strategy that resolves a user returns the normal success result and the controller issues the token pair. Both outcomes are the same code path the password strategy already uses, plus one branch.

### Credentials: one Integration per provider

```ruby
module SpreeSocialAuth
  class Integrations::WeChat < Integration
    preference :client_id, :string
    preference :client_secret, :password
    preference :trust_unverified_email, :boolean, default: false   # unused by WeChat — no email

    def self.integration_group = 'authentication'
    def self.logo_url = ... # data: URI, self-contained like the other provider gems
  end
end
```

Registered from the engine with `Spree.integrations << 'SpreeSocialAuth::Integrations::WeChat'`, which makes each provider a card on `Settings → Integrations` and its credentials editable there with the existing schema-driven form. `can_connect?` is a credentials-completeness check plus, where the provider offers a cheap unauthenticated endpoint, one live call — so "activate" fails loudly on a wrong secret instead of at the shopper's first login (see Open Question 1 for the providers that cannot be checked).

The strategies are registered by a single engine initializer that walks the same list, so registering a provider is one `Spree.integrations <<` line plus one `Spree.store_authentication_strategies.add`. The factory holds the key and label and reads the credentials per request; `available?` is true only when this store has an active integration for it.

### Account resolution

Three rules, applied by the strategy's `#callback`, with identity storage in `Spree::UserIdentity` and account creation in `Spree.customer_create_workflow`:

1. **Known identity** — `(provider, uid, user_type)` exists. Log in; refresh `info` and the tokens.
2. **Existing customer, first social login, verified email** — the provider asserts `email_verified` (or the integration opts into `trust_unverified_email`), and a customer with that address exists. Attach the identity to that customer and log in. The email lookup is case-insensitive, because Spree normalises email by squishing and never downcasing. An explicit `email_verified: false` is always refused, whichever way the integration is configured.
3. **No account** — the provider returned a usable email: create the customer through `Spree.customer_create_workflow` (which records consent, runs the shop's registration policy, links a newsletter subscriber, and applies the same validations a form registration gets) and attach the identity. The provider returned no email: return `registration_required` and let `POST /store/auth/complete` finish the job with the email the shopper types.

Consumers merge into one identity store keyed by `(provider, uid, user_type)`, so a shop that removes a provider and adds it back reuses the same rows, and an SSO admin and an SSO customer with the same email stay distinct records — the same guarantee the OIDC callback relies on today.

### The registration step

The provider exchanged a code, so its identity is proven; only the email is missing. Two calls:

**1. `POST /api/v3/store/auth/login`** — `{ provider, code, state, redirect_uri }`

| Outcome | Response |
|---|---|
| Resolved (rules 1–3, email present) | `200 { token, refresh_token, user }` |
| No account, no usable email | `200 { status: 'registration_required', registration_token }` |
| State invalid / provider unknown / code spent / credentials rejected | `4xx` with a stable error code |

**2. `POST /api/v3/store/auth/complete`** — `{ registration_token, email, first_name?, last_name?, terms_of_service }`

Verifies the token (message verifier, purpose `spree/store/social_signup`, 15-minute expiry, payload `{ provider, uid, email, email_verified, info, store_id }`), then calls `Spree.customer_create_workflow` with `password_required: false`, attaches the identity, and returns `201 { token, refresh_token, user }`. A token that fails verification returns `invalid_registration_token`; an email already in use returns `email_taken` (see the consequence below).

The verifier signs, it does not encrypt: the payload is readable by whoever holds the token, so **the provider's access and refresh tokens never travel in it**. The identity is attached without them at registration and picks them up on the next login. The token also carries the store id, so one minted on another store's login page cannot complete here.

The account is password-less until the shopper claims one through the normal password-reset flow, which now works because the address is real. This is the same shape as the account the checkout "create an account" box creates (`password_required: false`, claimed by reset), so nothing about password-less accounts is new.

**The consequence worth stating in the merchant docs:** a shopper whose email already belongs to an account cannot complete social registration — they are told to sign in the way they did before. Linking a social identity onto an existing account from account settings (the reverse direction) is a follow-up, not part of the first release; see Non-goals.

### Store API surface

| Method | Path | Auth | Purpose |
|---|---|---|---|
| GET | `/api/v3/store/auth/providers` | publishable key | Enabled providers for this store, with `requires_email` and authorization URLs |
| POST | `/api/v3/store/auth/login` | publishable key | Existing endpoint; a `provider` whose strategy is `:redirect` is served by `#callback` instead of `#authenticate` |
| POST | `/api/v3/store/auth/complete` | publishable key + `registration_token` | Finishes a social registration with the shopper's email |

The second row is the whole dispatch change: one branch in `Store::AuthController#create`. The alternative — a separate `POST /store/auth/social` — is rejected because the dispatch by `provider` already exists and a second endpoint would duplicate rate limiting, error rendering and token issuance.

`state` is signed by the API (message verifier, 15-minute expiry, payload carries the provider key **and** the store id), so the storefront cannot mint one, a state issued for `wechat` cannot be replayed at `douyin`, and a state minted on one store's login page cannot complete on another's. The storefront keeps it in an httpOnly cookie between the two legs; the API re-verifies it on the exchange. The admin controller's `issue_oauth_state` / `valid_oauth_state?` is the reference, extracted to a shared concern rather than copied.

The exchange also validates that `redirect_uri` is one of `store.allowed_origins` before using it, and rate limits `login`/`complete` on separate budgets from provider discovery.

### The storefront flow

1. Login page loads → `client.auth.providers()` → one button per provider, ordered by the registry; providers with `requires_email` say so on the button's help text.
2. Shopper taps "WeChat" → storefront stores `state` (and the page the shopper was headed for) in an httpOnly cookie and redirects the browser to `authorization_url`.
3. WeChat shows its QR page; on scan the browser returns to `/account/callback/wechat?code=…&state=…` on the storefront.
4. The route handler verifies the cookie's `state`, then `client.auth.login({ provider: 'wechat', code, state, redirect_uri })`. The `redirect_uri` is read back out of the authorization URL the API minted — never from the request — because the API requires it to be one of the store's allowed origins **and** to equal the callback registered on the integration. A storefront callback on a custom domain therefore needs that URL allowlisted on the store as well as registered with the provider (Phase 7 documents it).
5. **If the API answers `registration_required`**, the storefront shows one screen: the email (plus optional first/last name) and the terms box, then `client.auth.completeRegistration({ registration_token, email, first_name, last_name, terms_of_service })`.
6. Either way it ends with `{ token, refresh_token, user }` — the same body password login returns. The existing bootstrap stores the tokens, associates the guest cart through `PATCH /carts/:id/associate`, and hands the shopper to the destination they started from (the account area, or the checkout a sign-in prompt interrupted).

Errors surface on the login page as a query parameter, as the dashboard login page already does — not as a JSON body the shopper cannot act on.

The storefront is a separate repository, so its half of this plan travels as `docs/plans/6.0-social-login.storefront.patch` until `spree/storefront` carries it on `6-0-dev`. The patch applies cleanly to `0916c66` and includes the five locale bundles.

### Errors

Provider failures must name what to fix, per the house rule for third-party APIs. Each client translates the provider's codes: a spent or expired authorization code is the shopper's to retry (WeChat 10 minutes, Douyin 10 minutes, both single-use); rejected credentials (`40013`/`40125` on WeChat, `10013`/`10003` on Douyin, a signature failure on Alipay) name the integration to re-check; a network failure is reported as such and never as "login failed". Two rules are absolute, because the providers break the assumptions a generic client makes: **WeChat and Douyin return failures with HTTP 200**, so the body decides success, never the status; and QQ returns a url-encoded query string rather than JSON on error.

The store surface returns stable codes the storefront can branch on, mirroring the admin vocabulary in `ErrorHandler::ERROR_CODES`: `invalid_oauth_state`, `invalid_provider`, `registration_required`, `invalid_registration_token`, `email_taken`, and the existing `authentication_failed`. Retryable (network, provider busy) and terminal (configuration) failures are distinguished by code, not by message text.

`SpreeWechatPay::Oauth` on this branch is the precedent for the wording and the timeout policy (short open/read timeouts, because the exchange runs inside a shopper's request) — the gem reimplements it rather than depending on that gem. A failure logs one line naming the provider, store and code, so a merchant can see why logins fail without reading a 500.

### Security

- Secrets stay server-side; the discovery endpoint exposes `client_id` only inside the authorization URL, as OAuth requires.
- `state` is signed, expiring, provider-bound and store-bound; the storefront additionally keeps its own cookie.
- `redirect_uri` must be one of `store.allowed_origins` **and** equal the callback URL registered on the provider's integration; the API never relays a URL of the caller's choosing to the provider.
- Linking requires a verified email; an explicit `email_verified: false` is always refused; providers without an email never link.
- Provider tokens are encrypted at rest with the codebase's existing `encrypts … if ActiveRecord::Encryption configured` guard, and are never placed in a cookie or a URL.
- Account creation runs the shop's registration policy (`Spree.customer_create_workflow`'s `validate` hook) — social sign-up is not a policy bypass.
- The login and completion endpoints are rate limited per IP on separate budgets, so a shopper is never locked out by login-page traffic, and vice versa.
- The callback accepts only `POST` from the storefront; the browser never lands on the API.

### Non-goals (first release)

- **Linking a provider onto an existing account from account settings**, and the reverse (unlink). Deferred deliberately; the email-taken path above tells the shopper what to do instead.
- **Phone-number or SMS login**, and any provider not in the first-release set.
- **WeChat Official Account (`oauth2/authorize`) and Mini Program (`jscode2session`)** — different flows, later.
- **Admin SSO** — already built as OIDC (`6.0-platform-auth.md` Phase 7); this plan does not touch it.
- **Social sharing, friend lists, or posting on a shopper's behalf** — the providers' tokens are used for profile reads only.
- **A per-store choice of which providers appear** beyond "the integration is active" — no separate toggle, matching the auth registry's existing stance.

### Testing

RSpec with the gem's own dummy app, in the shape of `spree/providers/wechat_pay/spec`:

- **Strategies** — Faraday stubbed for the happy path; each resolution rule; each refusal (unverified claim, explicit `false`, no email → `registration_required`); each translated provider error, including the HTTP-200-with-error-code shape.
- **Provider HTTP** — WebMock with network access disabled, the practice `spree_wechat_pay` established: the request shapes (endpoints, parameters, which half is a GET and which a POST) and every translated refusal are proved without a merchant account. A recorded real exchange would prove the payload shapes only and would need sandbox credentials, so it is not required by CI; add one as a fixture only when a provider's wire format is genuinely in doubt.
- **Request specs** — `providers` payload shape (including `requires_email` and that an inactive integration's provider is absent), `state` rejection across providers and stores, redirect dispatch, `auth/complete` happy path, replayed/expired `registration_token`, `email_taken`, token issuance.
- **Isolation matrix** — the same provider key configured in two stores with different apps: a code obtained for store A cannot complete at store B, and each exchange uses its own store's credentials.
- **Core** — `Spree::UserIdentity` rule specs and a `customer_create_workflow` spec proving social provisioning records consent and runs the `validate` hook.
- No network in CI.

## Migration Path

1. **Core (this repository).** Phase 1 above: resolution and provisioning through `Spree.customer_create_workflow`, `available?`, store `auth/providers`, redirect dispatch in `auth/login`, `auth/complete`, `redirect_uri` validation, encrypted identity tokens.
2. **Gem.** `spree_social_auth` with WeChat + Douyin + Google, its dummy app and stubbed specs.
3. **SDK.** `auth.providers()`, the redirect-provider login call, `completeRegistration`.
4. **Storefront.** Buttons, one callback route, one completion screen, error copy.
5. **Merchants on Spree ≤ 5 with `spree_social`.** No in-place upgrade: the gem cannot install on 6.0 and its session model does not exist. A merchant moving to 6.0 either stays on Spree 5, or adopts the new gem and lets shoppers re-link. A one-off task (`spree:social_auth:import_legacy_identities`) can copy `spree_user_authentications` rows into `spree_user_identities` for providers whose `uid` scheme is unchanged (Facebook, Google, GitHub, Twitter-as-X are app-scoped and stable), which preserves the linked accounts even though the login flow is new. Rows whose provider returns no email still resolve — the identity exists, so rule 1 logs the shopper straight in.

## Constraints on Current Work

- **Do not extend `spree_social`.** No compatibility shim, no shared table, no reading `spree_user_authentications` at runtime.
- **Register providers through `Spree.store_authentication_strategies`.** A new endpoint per provider, or a second dispatch mechanism, is the thing this design exists to avoid.
- **Social account creation goes through `Spree.customer_create_workflow`.** Direct `user_class.create!` in a strategy is the bypass this plan removes; do not reintroduce it. Accounts for a user class the storefront flow does not own — a custom staff strategy a merchant wrote and trusts — keep their existing inline creation, because registration policy, consent and password reset belong to the storefront flow they are not part of.
- **Never create a *customer* account with a synthetic or unroutable address.** If the provider gives no email, take the registration step or fail — no placeholders.
- **Never link an account on an email the provider did not verify.** If a provider's email semantics are unclear, treat the email as absent.
- **Never relay a storefront-supplied `redirect_uri` without checking it against the store's allowed origins.**
- **Never put client secrets in `ENV` as the primary mechanism.** A store-scoped `Spree::Integration` is the only supported placement; `ENV` may seed it in a script, never replace it.
- **Never store provider tokens in cookies, sessions or URLs**, and never add a new plaintext credential column.
- **Keep the gem independent of payment gems.** Do not call into `spree_wechat_pay`, and do not move WeChat knowledge into a shared gem before a second consumer needs it.
- **Never treat an HTTP status as the provider's verdict.** WeChat and Douyin answer failures with 200 and an error code in the body; QQ answers a url-encoded string. The body is the contract.
- **Identity keys are stable.** `provider` values (`wechat`, `douyin`, …) are what `UserIdentity` stores forever; renaming one orphans every linked account, exactly as the `wished_item` → `wishlist_item` rename had to keep its prefix ID.

## Open Questions

The four design questions this plan opened were settled on 2026-09-11 and live under Key Decisions (resolution rules in core; the registration step in place of placeholder emails; first-release provider set; gem home). What remains genuinely deferred:

1. **`can_connect?` for providers with no cheap unauthenticated endpoint.** WeChat, Douyin and QQ cannot be verified without a shopper's authorization code, so "activate" can only check that credentials are present, with real verification left to the first login. Is a presence check acceptable, or should the dashboard say plainly that verification happens on first sign-in? *Deferred to the Integration pull request; either answer changes only that class.*
2. **Does the guest cart survive the redirect?** The storefront associates the guest cart after login (`PATCH /carts/:id/associate`), and the cart's `X-Spree-Token` lives in the storefront's own cookie, so the redirect should be transparent — but it is worth proving in the storefront spike, because a lost cart is the bug that reads as "WeChat checkout is broken". *Blocked on the storefront spike, not on this plan.*
3. **Should the registration token be single-use?** It is signed and expires in 15 minutes, but nothing stops a second use inside that window — the same property the admin OAuth state has. Enforcing single use means a cache entry keyed by the token's nonce, deleted on first use, which couples registration to the cache being available. *Deferred: decide when a merchant or a review asks for it; the payload carries no credential either way.*
4. **Linking and unlinking from account settings.** A shopper whose email is already taken by an account, or who wants to detach a provider, has no path in the first release. The shape (a "connected accounts" card on the account page, driven by `UserIdentity`) is sketched here but not designed. *Unblocked by the first merchant who needs it; it is the first follow-up after the storefront ships.*
5. **Mini programs and the official account.** Both are WeChat flows with their own identity rules (`snsapi_base` vs `snsapi_userinfo`, `jscode2session`'s session key). They are out of the first release; whether they arrive as extra providers on the store registry or as a separate "mobile" surface is unresolved until a merchant needs them. *Unblocked by demand.*
6. **Alipay: `alipay` gem or a small in-gem RSA2 signer?** The gem saves the signing work and adds a dependency whose last release predates Rails 8. *Deferred to the Alipay pull request.*
