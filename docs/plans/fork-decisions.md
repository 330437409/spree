## 2026-09-10 — WeChat Pay lands as a gateway gem; async refunds become an opt-in gateway capability

Two decisions from `6.0-wechat-pay-gateway.md`, both of which reach past that
plan.

**Payment gateway credentials stay on `PaymentMethod` rows, and a gateway is
not an `Spree::Integration`.** This restates the 2026-07-30 cardinality
decision because `6.0-integrations-admin.md` carries a blanket constraint —
"new provider gems must ship an Integration subclass" — that reads as covering
payment gateways. It does not: integrations are the store-level singleton
connection (delivery rates, tax, fulfillment, pickup points), where one
credential serves many config rows, and their `(store, type)` uniqueness
actively fights the merchant-entity model that payments need. A gateway
subclassing `Spree::Integration` is wrong, not merely redundant. A scope note
was added to that plan's constraint.

**A gateway may declare asynchronous refunds, and only such a gateway's refund
rows carry a status.** `spree_refunds` has no status column today — a refund is
either credited (`transaction_id` present) or destroyed on failure — and
`credit_allowed` sums every row. WeChat Pay accepts a refund request and settles
it later, sometimes failing after acceptance, so the truth cannot be recorded in
that shape. Core gains `Spree::PaymentMethod#async_refunds?`, **false by
default**, plus a `processing`/`completed`/`canceled` status on `spree_refunds`
and a `credit_allowed` that ignores no-longer-live refunds.

**Constraints now:** with `async_refunds?` false nothing about the refund path
may change — Stripe's existing refund specs are the guard, and they must pass
untouched; and nothing is added to the refund path that cannot be expressed for
both kinds of gateway. WeChat's own statuses map non-trivially and the mapping
is deliberate: only `SUCCESS` and `CLOSED` are terminal per WeChat's own
documentation, so `SUCCESS` is `completed`, `CLOSED` is `canceled`, and — the
part worth stating — **`ABNORMAL` stays `processing`, not `failed`**. An abnormal
refund is non-terminal and can still succeed, so calling it failed would both
misstate the money to the operator and corrupt the balance: `credit_allowed`
excludes failed refunds, so a still-live refund marked failed would free that
amount as creditable while WeChat could still complete it — a double-refund
path. The provider's own status goes in the refund's `metadata`, which the model
and the admin serializer already carry.

The general rule, which any future async-refund gateway inherits: **a
non-terminal provider state must never be mapped onto a terminal canonical one,
however alarming the provider's wording is.**



## 2026-09-17 — Mini-program feature gems live in `spree/extensions/`, a recorded deviation from the local-extension ignore rule

Plan: `6.1-miniprogram-extension-architecture.md`.

The plan recommended `spree/extensions/<name>/` for its feature gems and `.custom-extensions/` turned out to be this repository's actual convention: `.gitignore:81-82` ignores that directory under the comment "Local custom extensions (developed outside the core monorepo tree)", and `spree_crm` is a working precedent — ten migrations applied in `server/db/schema.rb`, server-side migrations mounted from the engine rather than copied into `server/db/migrate/`, routes added through `Spree::Core::Engine.add_routes`. So the plan's recommendation contradicted a stated rule and had to be either withdrawn or recorded. It is recorded.

**Decision.** The eighteen feature gems live in `spree/extensions/<name>/` with flat gem names (`spree_member_tiers`), and payment gateways stay in `spree/providers/<name>/`. `.custom-extensions/` remains what its ignore rule says it is — a place for one-off local work — and nothing in this set goes there.

**Consequences for other work.** The three reasons are that `.custom-extensions/` is gitignored, so CI cannot see a gem placed there while the plan's own constraint requires a new gem to be wired in three places or its specs never run; `spree_crm` has no git remote at all, making it a single copy; and `scripts/worktree/setup.sh` never provisions the directory, so a worktree created the documented way has neither the gems nor the `server/Gemfile` line that names them. `spree/extensions/` reuses the three-level path glob at `server/Gemfile:29`, which the comment there says exists for `spree/providers/*`; each gem still needs its own `gem '…'` line and its own `eval_gemfile('../../common_spree_dependencies.rb')` plus `gem 'spree', path: '../../'`. These gems are committed to the author's fork, not upstream — they must not be offered as a pull request against `upstream/spree`. Before the first new gem lands, the CI project list has to gain the two gems already in the repository that are missing from it: `.github/workflows/tests.yml` lists neither `providers/wechat_pay` nor `providers/social_auth`, so their specs have never run in CI.

## 2026-09-17 — A mini-program "site" is a seller, and every Store API request is seller-scoped

Plans: `6.1-miniprogram-extension-architecture.md`, `6.1-seller-service-area-routing.md`.

The mini program sends a `siteId` on every request (`miniprogram/static/config/api.js:42`) and calls the resulting object a site. Reading the restored client made it look like a place of business — it carries business hours, a map point and a twenty-five minute delivery promise — and the plan accordingly proposed `Spree::StockLocation` with `kind: 'store'`, having rejected Store, Channel, Market and a new model. The author has ruled otherwise: **a site is a seller.** The platform is an operator only, and the seller is the unit a customer shops from. The catalogue is the one exception, and the entry below corrects it: products are the operator's master catalog, and what a seller owns is its *offer*.

**Decision.** `siteId` resolves to a `Spree::Seller`. The seller's premises is that seller's own stock location (`Spree::StockLocation#seller_id`, `kind: 'store'`), so the client's single `site` object is a seller *and* its one stock location collapsed into one shape, which is what it looks like when each seller has exactly one premises. Resolving the seller is therefore request-scope infrastructure rather than a delivery detail: every Store API call in this application is made in the context of one seller, and the `resolve_seller` step in `6.1-seller-service-area-routing.md` is that mechanism rather than a routing-only helper.

**Consequences for other work.** Spree's Store API v3 is store-scoped and carries no seller context, so seller scoping has to be added as a first-class capability before any feature gem can be correct; it precedes Wave 0 rather than sitting inside it, and `6.1-seller-service-area-routing.md` is promoted to the keystone accordingly. Every gem in the set is seller-scoped at the point where a seller is chosen — not in the catalogue, which the entry below establishes is store-wide and the operator's. `6.1-site-scoped-pricing.md` is renamed `6.1-seller-scoped-pricing.md`, and per-seller invoicing is now the expected reading because the platform does not sell. Membership entitlement is explicitly **not** settled here and stays an open question: a seller-scoped system does not say whether a tier or a point balance belongs to one seller or to the platform across sellers.

## 2026-09-17 — A membership and a points balance belong to the customer, not to a seller

Plan: `6.1-membership-and-loyalty-points.md`.

The decision above — a site is a seller — left the tenancy of a tier and a point balance open, and the membership plan had drafted around the ambiguity: `spree_memberships.seller_id` nullable, with null meaning store-wide and a value meaning the seller-scoped SVIP the mini program sells, and the balance already per customer. The author has ruled: **a membership belongs to the customer.**

**Decision.** The member, the tier and the points balance are customer-scoped and span every seller in the store. `spree_memberships` keys on `(store_id, customer_id)` and carries no seller column; `spree_loyalty_accounts` likewise. The purchase that produces an entitlement is still seller-scoped — the cart, the order and the payment belong to the seller that sold — but the entitlement it grants does not.

**Consequences for other work.** The programme's participation allowlist is a list of **sellers**, not stock locations, so `spree_loyalty_programme_stock_locations` becomes `spree_loyalty_programme_sellers`, and "site" anywhere in that plan now means a seller rather than a row in a stock-location table. Because one balance is spendable at every seller, a redemption at one seller may be funded by points earned at another, so every ledger entry records the seller and the order that earned or spent it even though the balance itself is not divided by seller — without that attribution the platform cannot settle between sellers. The client's `isSvipSite` flag and `getSvipSiteList` endpoint are not explained by this ruling and remain a narrowed open question in the plan.

## 2026-09-17 — The catalogue is the operator's master catalog; a seller holds offers, not products

Plans: `6.1-miniprogram-extension-architecture.md`, `6.1-store-api-miniprogram-gaps.md`.

The author supplied the missing premise: the site belongs to the operator, a seller is the operator's franchise shop, and a seller's role is to distribute the site's products. Upstream already models exactly that, and the model shipped before we looked. `6.0-multi-vendor-marketplace.md:202-210` records Decision 11 as shipped on 2026-08-16: several sellers may sell the same item and **the seller lives on the variant, not on a separate offer record**. A **master product** is a product whose `seller_id` is nil — the marketplace's shared catalog, the operator's. A seller's row on one is an **offer**, and an offer *is* a variant: `variants.seller_id` and `variants.delivery_profile_id` are kept on a master product and blanked on an owned one, `Variant#resolved_seller` and `Variant.for_seller` resolve the seller either way, `Seller has_many :variants` is exactly the seller's rows on master products, and `Products::SelectBuyBox` picks the offer a product leads with. The Store API already returns `seller_id` on every variant and the buy box winner's price. The half that had not shipped is being delivered by upstream pull request #14576 *Let sellers list offers against master catalog products* (branch `feat/seller-master-catalog-ui`, open), which adds `products.open_to_sellers`, a `status` on every variant with its own review lifecycle recorded on `Spree::ProductSubmission#variant_id`, and the operator and seller surfaces — implementing `docs/plans/6.0-seller-master-catalog-listings.md`, which is not in this repository until that pull request merges.

**Decision.** A mini-program site is a seller, and a seller distributes the operator's catalogue by holding **offers** — variant rows carrying its `seller_id` on master products. The catalogue itself is store-wide and the operator's. A seller owns a product only where the operator also lets it submit its own (`6.0-seller-product-submission.md`); that is the owned-product case, and it is not the franchise case this application models.

**Consequences for other work.** A seller-scoped catalogue is reached through `Variant.for_seller`, never `Product.for_seller`. On a master catalog `products.seller_id` is nil, so scoping a product list by it returns the operator's listings rather than the seller's offers — an empty or wrong storefront, and it fails silently because both are valid relations that return rows. The pattern is `Product.joins(:variants).merge(Variant.for_seller(seller))`. `Products::SelectBuyBox` takes `product:`, `currency:` and `option_value_ids:` and **has no seller parameter**, so in a seller-scoped storefront it leads with a first-party or rival offer; constraining it is a design requirement rather than a tuning detail, and the service is swappable through `Spree::Dependencies.product_buy_box_service`. The client's `shopId` is a seller's warehouse — `Spree::StockLocation` carrying that `seller_id`, which is where its offers' stock sits, matching the upstream rule that prices are the seller's and stock is in the seller's warehouses. `open_to_sellers` and `variants.status` are unmerged: no gem in this set may depend on either until #14576 lands, and once it does, every shopper-facing read of a product's variants must exclude rows that are not `active`.

## 2026-09-17 — The operator funds the member discount; core's seller ledger assumes the seller does

Plans: `6.1-membership-and-loyalty-points.md`.

The author ruled that the operator funds the member discount (Open Question 7 of the membership plan). The ruling also settles the shape question that sat beside it: one party funds it and that party is not the seller, so the tier catalog is the operator's, store-wide, priced with `automatic` rather than `fixed`, and `spree_loyalty_programme_sellers` governs who awards and accepts points rather than whose prices are discounted.

**Decision.** The operator bears the difference between the base price and the member price, and the seller is paid as though the discount had not happened.

**Consequences for other work.** Core documents the opposite position as its v1 stance, so the ruling has to be paid for explicitly rather than configured. `Spree::Commissions::CalculateLine.base_for` charges the fee on `subject.taxable_basis` and says that "discounts come off either way … a promotion is the seller's concession in v1" (`spree/core/app/services/spree/commissions/calculate_line.rb:77-82`). The seller's earning agrees: `SellerTransfers::Create#earned_amount` is `order.total` less the commission lines (`spree/core/app/workflows/spree/seller_transfers/create.rb:106-119`), so **any reduction the customer sees reduces the seller's payout automatically, with nothing warning**. Funding it from the operator therefore requires an explicit credit row to the seller, for the seller's shortfall against their base-price net rather than for the whole discount, because the commission base stays where the 2026-09-17 commission ruling put it.

That credit has no home yet. `SellerTransfer::KINDS` is a frozen two-value constant (`%w[earning refund_reversal]`) and `validates :kind, inclusion: { in: KINDS }` binds that array when the class loads, so an extension cannot add a third kind. The settlement machinery itself needs no change: `SellerPayouts::Sweep` partitions unsettled rows by **sign**, not by kind (`rows.partition { |row| row.settlement_amount.negative? }`), so a positive row of any kind is swept into the payout and `SellerBalance` follows it. One core change — a `subsidy` kind plus the workflow that writes it — therefore buys funding that the existing machinery already pays for, whereas a gem-local second ledger does not, because the sweep and the balance would never see it.

**Corrected 2026-09-18: it is five edits, not one.** An audit of the membership plan checked the sentence above against the code and found the sweep is the only place that reads by sign. Four others read by kind, and each would silently mishandle a `subsidy` row: `scope :awaiting_provider` is `earnings.retryable.where(payout_id: nil)` (`spree/core/app/models/spree/seller_transfer.rb:91`), so the credit would never be handed to the payout provider; `Spree::SellerTransfers::Reverse` finds its counterpart with `.earnings.find_by(order_id:)` (`reverse.rb:42`) and `SellerTransfer#reversible_amount` returns zero unless the row is an earning (`:127-128`), so a subsidy could never be reversed when the sale is refunded; and `refund_id` carries a non-partial unique index (`db/migrate/20260822000001_create_spree_seller_transfers.rb:46-47`) whose behaviour the reversal's `RecordNotUnique` recovery is built on (`reverse.rb:52,70`). The ruling of 2026-09-18 is therefore **five coupled edits**, and the membership plan now carries them as its core change with the files named. This is the same "the operator owes a seller money" shape as a points redemption at one seller against points earned at another, so both should be settled as one mechanism. A first-party order needs no row at all: `SellerTransfers::Create#ensure_creditable` halts when the order has no seller, because the money is already the operator's.

## 2026-09-17 — Commission follows the actual selling price, for a member price and a promotional price alike

Plans: `6.1-membership-and-loyalty-points.md`.

The author ruled that a seller's commission is taken on the actual selling price — a member price and a promotional price alike (Open Question 8 of the membership plan). The ruling confirms what core already does rather than changing it.

**Decision.** `base_for` keeps reading `subject.taxable_basis`, which is `[amount + taxable_adjustment_total, 0].max` (`spree/core/app/models/spree/line_item.rb:246-270`). A promotional discount reaches it through `taxable_adjustment_total`; a member price arrives already reduced as the line's own price. Either way the fee follows what the customer paid. **No core change to `base_for`**, and no change to the "a promotion is the seller's concession in v1" position that the funding ruling has to pay for separately.

**Consequences for other work.** A price-list member price leaves no `Discount` row at all — the walk returns a `Spree::Price` (`spree/core/app/models/spree/pricing_provider/internal.rb:36-38`) and the line records where it came from in `price_list_id` and `price_source` (`spree/core/app/services/spree/carts/price_items.rb:97`) — so the rule needs nothing from an extension to come out right, and the operator-funded subsidy equally cannot be read off a discount row. The subsidy is the seller's shortfall against their base-price net, `discount × (1 − commission rate)`, so **it must be calculated and persisted when the transfer is created and never recomputed later**, because the base price it compares against can move after the sale; `SellerTransfers::Create` already runs once at completion, so the credit snapshots with it. The formula's dependence on the rate is arithmetic rather than a defect — the operator receives less commission precisely because the customer paid less, and its net is the same whichever base the fee is charged on. Because `Spree::Commissions::Context#commission_basis` weighs a value band on that same discounted figure (`spree/core/app/models/spree/commissions/context.rb:54-68`), a member discount can drop a sale into a lower band and lower the rate with it; that is worth knowing before commission bands are set for a store that runs a membership.

## 2026-09-17 — A purchasable membership rides the gift-card flag, and that flag stops meaning stored value

Plans: `6.1-membership-and-loyalty-points.md`, `6.0-6.1-loyalty-gift-cards-store-credits.md`, `6.1-gift-card-purchase-and-transfer.md`.

The author ruled that a purchasable membership is a gift-card-flagged product (Open Question 3 of the membership plan). Reading the mini program found the client agreeing with the ruling and showing why it is the right one: a membership is bought through `vip/addOrder` then `vip/payByWxMp`, which sits structurally beside the gift card's `gift-card/addOrder` then `gift-card/payByWxMp` and, like it, never touches the cart; and what the customer receives is literally a card, held in the wallet "待激活/赠送" (`miniprogram/pagesB/cards/mine/mine.wxml:20-21`), giveable to a friend with a claim window after which "会员卡退回账户中" (`miniprogram/pagesB/cards/presentation/presentation.wxml:19`), and moved through `activation` plus donation `success` → 已赠送, `invalid`/`recycled` → 已失效, `activation` → 已激活, `expired` → 已过期 (`miniprogram/pagesB/cards/record/record.js:49`).

**Decision.** `spree_products.gift_card` marks a purchasable membership as well as a gift card, and no second non-physical flag is added — which is what the loyalty plan's own constraint demands (`6.0-6.1-loyalty-gift-cards-store-credits.md:131`). The flag's meaning therefore widens from "prepaid money the store owes" to "prepaid and not a physical good". A membership is never stored as a `Spree::GiftCard`: it has no face value to spend, and its home is `spree_memberships`.

**Consequences for other work.** Three of the five switches the flag throws are wrong for a membership and must branch on the kind instead: `promotionable` false and exclusion from price lists (a membership sale should be discountable), refusal of payment with a gift card or store credit (buying a membership from a credit balance is ordinary), and non-taxability on the grounds that the tax falls on what the card later buys (a membership is a service period, and the sale is taxable in many jurisdictions). The two that travel are no inventory tracking and a digital delivery profile, and the second is already core's job through the delivery profile and `Product#digital?` rather than the flag's. The one thing the flag does **not** disturb is `Spree::GiftCards::IssueFromOrder`. This entry originally claimed the opposite — that because a membership was "issued on `order.paid` too", the flag stopped being the discriminator and the issuer had to key on the linkage instead. **That claim is withdrawn**, same day, by the scenario-order ruling recorded below: a membership is issued on a scenario order's settlement, which creates no `Spree::Order`, so `order.paid` never fires for one and the workflow cannot reach it. And because paying issues a **dormant** card whose term begins at activation or at a claim, "issued when the order is paid" is no longer the same as "the term has started": `spree_memberships.starts_at` is written on activation, and its `status` carries `dormant`/`active`/`gifted`/`recycled`/`expired`. The membership shares the activation-and-transfer *situation* with `6.1-gift-card-purchase-and-transfer.md` — dormant state, claim window, return to the account, `recycled` void — and not its recipient half, because a membership is given through the wallet rather than by naming an email address at checkout. **Superseded in part, same day:** the membership card does not inherit that lifecycle from the gift-card plan at all; it owns its own tables and transitions. See "A membership card is its own instrument" below.


**Amended 2026-09-18, re-homed.** This analysis was originally written into
upstream's `6.0-6.1-loyalty-gift-cards-store-credits.md`; it belongs here,
because it is about *our* membership plan. The flag marks a purchasable
membership as well as a gift card, so nothing may treat it as "stored value":
the three switches that only make sense for stored value — `promotionable`
false and exclusion from price lists, refusal of payment with a gift card or
store credit, and non-taxability — do not fit a membership, which is a service
period whose sale is taxable in many jurisdictions. The per-kind behaviour
branches on the kind, not on the flag. `IssueFromOrder` is unchanged: both
purchases are scenario orders (`vip/addOrder`, `gift-card/addOrder`) and never
reach `Spree::Order#paid`, so it stays the cart channel's issuer and a
membership never arrives there. Nothing keying on the flag may act without
asking what kind of product it is — and a membership is never stored as a
`Spree::GiftCard`, having no face value to spend.

## 2026-09-17 — A points redemption is a discount on the order, not a tender

Plans: `6.1-membership-and-loyalty-points.md`.

Open Question 5 of the membership plan asked whether a points redemption applied to a cart is a `Spree::Discount` with `kind: 'loyalty'` (the value `6.0-6.1-split-adjustments.md:194,307` lists but the shipped model does not accept — see the entry on the third `Discount` kind below) or a credit-like payment. The mini program settles it in favour of the discount.

**Decision.** Points spent on an ordinary order are a discount, `kind: 'loyalty'`. The client sends a boolean `useIntegral` on `calc/buyCalc`, `calc/cartCalc`, `order/buySubmit` and `order/cartSubmit`; the server answers with `integralTotal` (available), `integralNum` (points that would be spent) and `integralMinus` (the money off), plus an `integral` entry inside the order's ordinary `minusList` — the same array that holds `coupon` and `first_order` (`miniprogram/pagesF/static/behaviors/settlementBehavior.js:43`, `miniprogram/pagesF/static/template/order-discount.wxml:42-61`). The toggle is opt-in, some activities refuse it through `seckillIntegralFlag`, and the client performs no arithmetic: the money off is the server's number.

**Consequences for other work.** A credit-like design would put points in the tender list beside the gift-card balance, which is not where the client keeps them — a balance is a tender guarded by a payment password ("支付密码将用于下单时礼品卡余额的抵扣", `miniprogram/pagesB/me/password/set-pay/set-pay.wxml:12`), while points are one more reduction row. No new core model is needed; the ledger entry points at the discount, which is core's record. Three details belong in the plan. Points earned are computed on the amount paid **after** the deduction ("商品积分值将按照优惠后（扣除积分抵扣、优惠券等活动）实付金额进行换算"), so the earning rule reads the discounted total rather than the base. The redemption ratio is not the earn ratio: `getIntegralConversionRatio` is the earn side ("每消费N元得1积分") and is display-only — the client multiplies nothing — while redemption has its own figure ("每N个可抵扣1元"). And expiry is a banner over the balance (`willExpireIntegral`/`willExpireDate`), not a row kind: the ledger's filters are only 全部/收入/支出 and its label is a server-supplied `integralExplain`, so an `expire` entry may never need to be listed at all. The points mall is a different mechanism and stays one: `integral-mall/addIntegralMallOrder` creates a standalone order paid wholly in points (`convertType: 'integral'`, with no payment call at all) or in points plus cash (`point_amount`), with no address step, which is `spree_loyalty_rewards` and `spree_loyalty_redemptions` rather than a cart reduction.

## 2026-09-17 — The growth-value ranking is a backend subsystem, not a read-only view

Plans: `6.1-membership-and-loyalty-points.md`.

Open Question 4 asked whether the growth-value leaderboard is a Spree concern at all, and recommended that the ledger feed a read-only ranking view while "the ranking itself belongs to whichever system already computes it". Reading the mini program shows that recommendation cannot stand as written.

**Decision.** The per-customer growth-value **ledger** is ours, and the **ranking** is a real subsystem that must be named as either this backend's or an explicit external dependency. ## 2026-09-17 — A membership card is its own instrument, and its lifecycle belongs to the membership gem

Plans: `6.1-membership-and-loyalty-points.md`, `6.1-gift-card-purchase-and-transfer.md`, `6.1-distribution-and-commissions.md`.

The author ruled that the membership card is decoupled from the gift-card plan: it is built against its own table, and activation, gifting, claiming and voiding are owned by the membership gem rather than inherited from `6.1-gift-card-purchase-and-transfer.md`.

**Decision.** A card is an instrument and a membership is an entitlement, so they are separate rows. `spree_membership_cards` holds what is bought, held, given away and voided; `spree_memberships` holds the period a named customer is entitled to, produced by activation. The gift is a third table, `spree_membership_card_transfers`, carrying a plain `membership_card_id` and an opaque `token` from `has_secure_token` — the `spree/core/app/models/spree/company_invitation.rb:21` pattern. The four transitions, 激活 activation, 相赠 gifting, 领取 claiming and 作废 voiding, are this gem's. A membership card is **not** a `Spree::GiftCard` and is never a row in `spree_gift_card_donations`; the two plans share the situation of a card bought dormant and activated later, and share no tables and no workflows. Neither plan gates the other, so the membership card can be built without waiting on the gift card plan's unbuilt phase 2.

**Why separate rows rather than one card that becomes a membership.** Three facts in the client force it rather than merely allowing it. A customer holds **several** dormant cards at once — the wallet counts them ("您有{{cardCount}}张酒小二会员卡待激活/赠送", `miniprogram/pagesB/cards/mine/mine.wxml:20`) — which "one membership per customer per level" cannot express. A card carries facts a membership cannot: whether it may be given away at all (`item.giftTransfer`, `:36`) and the deadline to activate or give it away ("请于{{item._validUntil}}前赠送/激活", `:32`). And a card that was given away stays in the giver's record as 已赠送 (`miniprogram/pagesB/cards/record/record.js:49`), so the card keeps its buyer while the entitlement goes to the claimer.

**A claim and an activation are the same transition, entered from two doors.** The client sends one call and distinguishes the doors with `activateType` — `"my"` from the wallet (`miniprogram/pagesB/cards/mine/mine.js:118-119`), `"relay"` from the received gift (`miniprogram/pagesB/receive-gifts/receive-gifts.js:100-104`). Giving each door its own resource also removes an ambiguity the client itself carries: its `cardId` parameter means a card's id in the wallet and the **giving's** id on the receive page, which the share link supplies (`miniprogram/pagesB/cards/presentation/presentation.js:60`, `miniprogram/static/behaviors/locationLinkBehavior.js:200-202`).

**Consequences for other work.** The public read of a gift is addressed by the giving's opaque `token` and does not live under `customers/me`, because the receive page reads it before sign-in and only asks for login when the visitor activates (`miniprogram/pagesB/receive-gifts/receive-gifts.js:74,97`). The token must therefore never be derived from the card, whose id travels in clear through the wallet, the activate call and the cancel call (`miniprogram/pagesB/cards/mine/mine.js:95,118,160`). `spree_memberships` loses the `dormant` and `gifted` statuses, which were always the card's, and the card carries the `order_id` and the `membership_id` that link the two — concrete foreign keys, keeping the repository's "concrete foreign keys, no polymorphic source" rule (`spree/core/app/models/spree/commission_line.rb:8-9`). Every membership now comes from a card, which is what anchors its period to the order that paid. The distribution plan's payee fork narrows to a single instance: a membership card's gift is no longer a second subject in a transfer table, so Option A against Option B in `6.1-distribution-and-commissions.md` Open Question 1 is a question about the seller ledger's payee and nothing else. One thing this ruling does **not** fix: a gift-card product and a membership product both still carry `spree_products.gift_card`, and `Spree::GiftCards::IssueFromOrder` still keys on that flag alone, so separating the tables does not separate the trigger — the guard belongs in the issuer, not in the schema.

## 2026-09-17 — A cart line carries the shopper's tick, and completion copies only the ticked lines

Plans: `6.1-store-api-miniprogram-gaps.md`.

Open Question 1 of the Store API gaps plan offered three mechanisms for "check out only the ticked lines" and asked the author to rule before the cart work could start. The mini program already answers it, so this one needed reading rather than ruling.

**Decision.** A cart line item carries a persisted `selected` flag. The cart's money is computed over the selected lines, checkout is scoped to them, and completion copies only them. Option A of the question, placed on the **cart's** line item rather than the order's. The Store API surface the client needs is one bulk write over a set of line ids plus a chosen count on the cart serializer.

**Why the client decides it.** The choice is durable cart state, not a transient UI flag: `cart/getCartInfo` returns a `choose` boolean per line beside a server-computed `chooseTotalQuantity` (`miniprogram/pagesF/cart/cart.js:216,319,408`), and `cart/chooseCart` writes it in bulk over a set of line ids as `{ choose, idSet }` (`miniprogram/pagesF/static/api/cartApi.js:7-9`, `miniprogram/pagesF/cart/cart.js:588-605`). No request in the checkout path carries the chosen ids: the settle page is opened as `?type=cart` with none (`miniprogram/pagesF/cart/cart.js:757-759`), `orderSubmit` builds its payload from `calcParams` plus order-level fields only (`miniprogram/pagesF/settlement/settlement.js:868-887`), and `calc/cartCalc` sends the same shape (`:271-279`) — the buy-now path is the one that names goods explicitly, through `calcGoodsList` (`:673-674`), which is precisely the difference between "these items" and "my ticked items". The client also **repairs** the selection rather than only reading it: when the server marks a chosen line disabled the client calls `chooseCart` with `choose: false` for those ids and reloads (`miniprogram/pagesF/cart/cart.js:216-224`), which a flag applied at checkout would never need. And the selection is not one of two modes — the cart offers per-line ticks and a single bulk tick per combo group, which sends every line of that group (`:510-521`), with **no select-all control anywhere**, so "check out everything" is this one state with every line ticked rather than a second mechanism.

**Why the other two options are out.** Option B, one cart per selection, contradicts a single cart per site: `getCartInfo` takes only `siteId` and answers with every line and its flag (`miniprogram/pagesF/cart/cart.js:209-214`). Option C, splitting at checkout, contradicts the selection being enforced before checkout — it gates the cart's own minimum-order verdict and the client repairs it across page loads, so there is persistent state to keep.

**Consequences for other work.** The flag belongs to the cart and not the order because 6.0 separates the two models and completion copies (`6.0-cart-order-split.md`, Key Decision 3): `copy_line_items!` iterates `cart.line_items` (`spree/core/app/workflows/spree/carts/complete.rb:308-316`), so an unselected cart line is never copied and no order ever holds one. That shrinks the question's own objection — that a `selected` boolean forces every promotion, tax and shipping rule to ignore unselected lines consistently — to **cart-side calculation only**, where the client's server already applies it: the minimum-order hint is gated on the chosen count and compares the cart's money figure against the period minimum (`miniprogram/pagesF/static/behaviors/cartBehavior.js:106-113`, called with `chooseTotalQuantity` at `miniprogram/pagesF/cart/cart.js:405`). The shared money readers that must learn the scope are `Spree::Purchase::Totals#quantity` and `#amount`, which read `line_items` directly (`spree/core/app/models/concerns/spree/purchase/totals.rb:9-16`). Two constraints are recorded on the plan: do not model selection as two checkout modes, and do not compute a cart's money over the whole line set and filter it afterwards. The plan's three remaining questions were settled the same way on the same day — promotion selection, the checkout aggregate, and the menu-shaped category response.

Open Question 2 asked whether the mini program's `cart/changePromotion` is "apply my coupon" — already covered by `carts/discount_codes` — or "choose between two automatic promotions", which is a rule-engine change. The client answers it, and more sharply than the question framed it.

**Decision.** A cart line carries the shopper's **choice among the promotions the server has already found eligible for that line**. **Consequences for other work.** Two things are undecided and belong to the implementation rather than to this ruling: the scope of the preference (per line, per combo group, or per cart — the client sends a line's id with a candidate from that line's list while the currently-applied promotion it displays is the group's), and how a stored preference interacts with a promotion that stops being eligible, which the client already meets — it renders "超活动限制，以非新人价结算" on a ticked line whose new-customer price no longer applies (`miniprogram/pagesF/static/template/cart-goods.wxml:26`). ## 2026-09-17 — The ordering menu is a page composition, not a Store API resource

Plans: `6.1-store-api-miniprogram-gaps.md`.

**Why the menu is not a catalogue resource.** A root menu node is a category id **plus** a `menuType` that selects one of three different fetch strategies for its children: `combo` and `guess` go to the combo-zone list, `market` goes to the market activity goods page, everything else goes to the ordinary children endpoint (`miniprogram/pagesA/make-order/make-order.js:566`). ## 2026-09-17 — A membership purchase is a scenario order, and gifting it is the same purchase with a different purpose

Plans: `6.1-membership-tiers-and-rights.md`, `6.1-scenario-purchases.md`.

Two draft plans answered the same endpoint in opposite ways. `6.1-membership-tiers-and-rights.md` called `vip/addOrder` "an ordinary order, then the standard payment session" and mapped the summary to `Spree::Cart` and the purchase history to `Spree::Order`. `6.1-scenario-purchases.md` listed `vip` as one of its six kinds, and its fourth key decision says a scenario purchase creates no `Spree::Order` unless it genuinely delivers physical goods. The plan that owns the feature and the plan that owns the frame disagreed, and both were still Draft.

**Decision.** The operator ruled it: **a membership purchase is a scenario order.** `6.1-membership-tiers-and-rights.md` registers the `vip` kind and owns what the purchase costs, what settling it issues, and the reads only the kind can answer — the pre-purchase check and the post-settlement read-back. `6.1-scenario-purchases.md` owns the frame, the endpoint, the lifecycle, the payment channel and the customer-scoped list. The purchase therefore creates no cart, no line item, no tax treatment and no shipment.

**Why the client decides it.** Buying a term is one call, and its payload is a package id, the site, the coordinates, a referral code and whether the buyer keeps it or gives it away — no cart, no line item, no address, no quantity, no shipping choice (`miniprogram/pagesB/components/member/pay-suspension/pay-suspension.js:143-148`). An `orderNum` comes back and goes straight to the gateway (`:155,166-172`). Nothing under `pagesB/member/` or `pagesB/cards/` mentions a recipient, an address or a shipment.

**Consequences for other work.** Gifting needs no second endpoint. `svipPurpose` is `1` to keep the term and `2` to give it away (`pay-suspension.js:96`, from 赠好友 at `pay-suspension.wxml:25`), and both produce a **dormant card owned by the buyer**. That is why `spree_membership_cards.customer_id` stays "the buyer, and it does not move on a claim": a purchase for someone else begins in the same state as one for the buyer, and giving it away is the same transfer either way. Second, `vip/addOrderCheck` is **not** a stock check; it answers whether a term already overlaps, and the page warns "自{{lowerData._lowEndTime}}起，您的权益将变更为{{svipCurList.name}}权益" (`pay-suspension.wxml:62,64`). It is advisory — the page buys on an **empty** answer and on a failure alike (`:85,87`); a non-empty answer opens the warning popup whose confirm proceeds — and it is the visible edge of the one-tier-group-per-customer rule. Sold out is a separate verdict the page holds before it calls anything (`:113`). Third, the gift-card issuer needs no guard at all, and the "discriminator is the linkage" rule this entry first recorded is withdrawn. `Spree::GiftCards::IssueFromOrder` runs on `order.paid`; a membership is issued on a scenario settlement and never reaches it. The two issuers are disjoint, and neither gem has to learn about the other. The residual exposure is a membership product put into a cart, which is the membership gem's requirement to prevent where a tier binds a product, not something the issuer detects. Fourth, the membership card's link back to its purchase is a `scenario_order_id`, not an `order_id`, since there is no order to point at. This also settles a disagreement between the two membership plans: `6.1-membership-and-loyalty-points.md` Open Question 3 had already recorded that `vip/addOrder` → `vip/payByWxMp` is "structurally identical to `gift-card/addOrder` → `gift-card/payByWxMp`, and neither goes through the cart" — the same reading reached here from the purchase payload.

## 2026-09-17 — The gift-card flag stays shared, and the issuer guard it was said to need is withdrawn

Plans: `6.0-6.1-loyalty-gift-cards-store-credits.md`, `6.1-gift-card-purchase-and-transfer.md`, `6.1-membership-and-loyalty-points.md`, `6.1-membership-tiers-and-rights.md`, `6.1-coupon-wallet.md`, `6.1-scenario-purchases.md`.

Reconciling the shared `spree_products.gift_card` flag after the scenario-order ruling. **The widening stands**: a purchasable membership carries the flag, and its meaning is "prepaid and not a physical good". What does not stand is the consequence recorded alongside it. Three plans were carrying a requirement that `Spree::GiftCards::IssueFromOrder` stop keying on the flag and start keying on "the linkage", on the premise that a membership reaches `order.paid` the way a gift card does.

## 2026-09-17 — A kind is a subclass and a registration, never an enum the client's strings define

Plans: `6.1-membership-tiers-and-rights.md`, `6.1-membership-and-loyalty-points.md`. Applies to every kind list in this plan set.

The membership plan had modelled a right as a content row carrying an `api_type` from a closed vocabulary of ten strings, on the argument that the client switches on exactly those and a kind outside the list renders with a dead button. It then accepted the client's six member-centre section names as "a contract, not operator data". The operator rejected both: the client's logic is worth learning from, but the backend must not be shaped by it, and the answer is the rule/registry approach Spree already uses.

**Decision.** A right is a **registered typed subclass**. `spree_membership_rights` is an STI table whose column is `type` — not `api_type`, which is derived — and each kind is a class under `Spree::MembershipRights::` listed in `config.spree.membership_rights` via `registers_subclasses_via`, `PreferenceSchema` included. The ten strings the client switches on are the **built-in kinds**, not a closed set. The kind list reaches the admin through a registry picker (`GET /api/v3/admin/membership_rights/types` → `{ type, label, description, preference_schema }`) rather than a hardcoded array.

**Why the repository already argues it.** `Spree::CommissionRule` states the principle in its own comment: *"A rule that could only name a record — this seller, this category — left everything else unsayable… Each of those was a schema migration and an edit to the matcher. As a class it is a subclass and a registration."* The same holds here, and harder: an enum column cannot carry a coupon's settings, and each new kind would be a migration plus an edit to the read. The families to copy are `PromotionAction` (`registers_subclasses_via { Spree.promotions.actions }`) and `CommissionRule`, and the controller shape is `Admin::PromotionRulesController#types`.

**Why the client decides which layer is the model.** The client reads the same rights **twice**. The rights page reads one **flat array** — every right with its own `action`, `showName` and `open` flag, no grouping (`yeargift/getYearRightsDetailsVo`, `miniprogram/pagesD/interests/interests.js:128-173`). The member centre reads the same rights **grouped** into six keys (`center.js:245-262`, keys at `center-item.js:35-40`). A flat list keyed by a type string is what a registry produces; the grouping is a second reading of it. So the flat read is the model and the grouping is a projection, and the Store API's rights resource is the flat one.

**Consequences for other work.** A right is an **entitlement**, not a condition — the tier it belongs to *is* the condition, so its shape is `PromotionAction` and not `PromotionRule`, and `isHave` and the `condition` array the client prints are both derived rather than stored. The six member-centre keys are each kind's own `presents_as` declaration, so a kind naming an existing panel joins it with no change to the serializer, the model or the admin; nothing in the backend may enumerate the six. A kind declaring a new panel has no panel in this client until a client release adds one, which is a limit on one view and not on the domain — the kind is still authored, published, listed on the rights page and served by the Store API, so it must not be refused at creation or hidden from the picker. The rule generalises to the rest of the set: wherever a plan is tempted to validate a kind against a literal array, or a serializer is tempted to branch on a kind, the answer is a subclass plus a registration. The first further instance was found by applying it: `spree_membership_grants` carried a `kind` reading `birthday`/`annual`/`member_day`/`monthly` — three of which restate right kinds (`birthday_double_integral`, `give_gift`, `svip_date`) — so the grant now points at the right that caused it and the period is the kind's own computation rather than a case statement in the job.

**The sweep across the rest of the set found two more, and one that already passed.** `6.1-coupon-wallet.md` called `spree_coupon_campaigns` a typed-subclass family in the same sentence that gave it a `kind` column and a `settings` JSON blob — a subclass whose configuration lives in a hash no class owns is a subclass in name only, and the AGENTS.md `PreferenceSchema` shape is what makes the registration mean anything. It is now `type` plus `preferences`, `include Spree::PreferenceSchema`, `registers_subclasses_via { Spree.coupon_campaign_types }` and a `type_must_be_registered` validation, matching `Spree::CommissionRule` line for line, with its six acquisition kinds named as the **built-ins** and the picker reading the registry. The membership history file's `spree_loyalty_rewards` — "typed by `api_type`: a variant, a coupon, or a membership" — is superseded outright; see the entry below. And `spree_point_products.jxe_type` was checked and **passes the rule's own test, so it was left alone**: it cites `Spree::CommissionLine` for its shape, its prose says the issue step is registered by whichever plan owns the thing being issued, and its three known payloads are concrete foreign keys under an exactly-one-of validation rather than a kind validated against a literal array. **One seam is raised rather than settled.** The *issue step* is registered, but the *payload* is a concrete foreign key, so a kind a later plan registers still needs a column — which is the cost `CommissionLine` accepts knowingly, since core's own line carries a fixed set of subjects. The rule's purpose is that a new kind is a class and a registration; here half of it is. Whether a fourth payload is expected decides whether that matters, and no plan currently expects one.

## 2026-09-17 — The points deduction is built beside the points mall, it needs a third `Discount` kind, and points are debited at creation on both paths

Plans: `6.1-points-and-growth-value.md`, `6.0-6.1-split-adjustments.md`.

The points plan's Open Question 4 asked which plan owned the `useIntegral` deduction on an ordinary order, on the reading that the ruling above left the mechanism unowned. The operator ruled that **both** mechanisms are built: the deduction on the ordinary order, and the mall's standalone order. That does not reopen the ruling — its own closing sentence keeps the mall as "a different mechanism" — it settles the half the ruling left open, which is where the deduction is stored.

**Decision.** The deduction belongs to `6.1-points-and-growth-value.md` and is written as `Spree::Discount` with `kind: 'loyalty'`. It adds no endpoint of its own: the boolean rides core's `calc/*` and `order/*Submit`. The mall is unchanged.

**"Reserved" was the wrong word, and it was mine.** The ruling above called `'loyalty'` "the value `6.0-6.1-split-adjustments.md:194,307` reserved". The split plan does list it among the kinds (`:194`) and does say custom discounts write it (`:307`), but the shipped model froze the list at two values — `KINDS = %w[promotion manual].freeze` (`spree/core/app/models/spree/discount.rb:16`), validated with `inclusion: { in: KINDS }` (`:27`) — and the serializer publishes it as a closed enum (`spree/api/app/serializers/spree/api/v3/discount_serializer.rb:8`). Nothing was reserved, and `'loyalty'` is not merely unvalidated: it is not representable.

**The shape to copy is `Spree::Fee`'s, the only unfrozen `KINDS` in core.** Nine of the ten freeze theirs; `Fee` does not, and says why — "Extensions may append their own kinds — the list is validated, not frozen" (`fee.rb:10,14`) — with the validation reading the constant through a lambda so an append is seen (`inclusion: { in: ->(_fee) { KINDS }, allow_blank: true }`, `:25`) and the open tier on the wire (`enum_type_name: 'FeeKind'`, `fee_serializer.rb:8`), which `spree/api/lib/typelizer/open_enums.rb:1-9` names as the archetype. `Discount` becomes the second. The tradeoff is stated rather than buried: because the points gem is an extension, an appended kind makes the generated `DiscountKind` union depend on which extensions are installed. `Spree::Actor` refuses that tradeoff — a frozen `BUILT_IN_KINDS` naming only what core registers, an open union, no autocomplete for an extension's kind (`actor.rb:14-21`). Either shape is defensible; a gem un-freezing a core constant is not, so this lands in `spree/core` and `spree/api`. No column and no migration change: `spree_discounts` already permits a row with no promotion source (`6.0-6.1-split-adjustments.md:353`) and the adjusters already clamp so combined discounts never push an adjustable below zero (`:99`).

**Why not a promotion action, which would need no core change.** The promotion engine reconciles its own rows destructively — `adjustable.discounts.where(kind: 'promotion').destroy_all unless best` (`6.0-6.1-split-adjustments.md:269`, with `:271,275`) — so a discount whose amount depends on a customer's balance and an opt-in boolean, which is not a "best action wins" computation, would be cleared by any recalculation in which no action is best.

**When the points leave the balance (ruled the same day).** At creation, on both mechanisms. The mall's debit is proven rather than chosen: `addIntegralMallOrder` returns `convertType` and the client branches on the **answer**, so a redemption that completes with no payment call at all can only have been settled by the create request (`pagesD/integral/goods/goods.js:226,253,262-267,272`). The deduction is debited in the same act — `order/buySubmit` or `order/cartSubmit` is what persists the `loyalty` row, and the points leave with it. Debiting at payment was refused because it leaves a window in which one balance is spent twice, once in the mall and once here.

**The cost of that ruling is stated rather than left to be discovered.** A mall order that is never paid has a state to sit in (`6.1-scenario-purchases.md:35,52`); an ordinary order does not. `Spree::Order::STATUSES` is `draft`, `placed`, `canceled` (`spree/core/app/models/spree/order.rb:130`), with no outcome for an abandoned purchase, and core runs no job that closes one — so an order submitted with a points discount and then never paid holds those points until something cancels it. The reversal therefore has to exist, and the seam already does: `Spree::Orders::Cancel` declares `hooks :before_cancel, :after_cancel` (`spree/core/app/workflows/spree/orders/cancel.rb:11`) and runs `after_cancel` inside the transaction that stamps the status (`:55-59`). The return belongs in that hook rather than in a subscriber on `order.canceled` (`:66`), because the same transaction that cancels the order must not be able to leave the balance spent if it rolls back. The `loyalty` row stays on the order — it records what the order carried, and the reversal is the ledger row.

## 2026-09-18 — A bundle is a composition and a discount, not a sellable variant

Plans: `6.1-product-bundles.md` (new), `6.1-product-reviews.md`, `6.0-multi-vendor-marketplace.md`.

The inventory carried this plan as "Combos, and the stock question they raise". The question dissolves once the modelling follows the client's own wire: adding a combo writes **one cart line per component**, each tagged `promotionCode: "combo"` with the bundle's id (`miniprogram/components/j-combo/format/format.js:169-190`), the cart endpoint re-groups those lines for display (`pagesF/cart/cart.js:273-315`), and the order surfaces carry no bundle shape at all. A bundle modelled as a sellable variant would therefore have to be given its own price, weight, stock, reservation, fulfilment and review surface — six things the client proves it does not have. Modelled as a composition plus a discount, all six stay where core already puts them: the components are ordinary line items, `Spree::Stock::Quantifier` computes their availability unchanged (`spree/core/app/models/spree/stock/quantifier.rb:29-38`), `Stock::Package` sums their weight (`6.1-weight-bracket-shipping-calculator.md:37`), the existing reservation primitive holds each of them line-item-scoped (`stock_reservation.rb:19,22,129-131`), and the bundle gets no review surface because `6.1-product-reviews.md:44-46` reviews the offer.

**Ruled the same day.** The saving is an order-level discount of the **existing `manual` kind** — not a promotion, because the client's own copy says the combo price "与满减满赠等活动不同享" and the promotion engine clears rows a recalculation does not choose; not a new core kind, because `manual` already exists and this plan therefore needs **no core change at all**, which the points plan could not avoid. **One seller per bundle**, refused at save time, because `Carts::SplitBySeller` re-totals each child order from its own lines and a single bundle price has no home in that fan-out. **And one false friend named.** `frozen` and `frozenQuantity` ride every combo path and are 冰冻 — a chilled-drink option with its own picker — not a stock hold.

## 2026-09-18 — The loyalty family's shared ownership: a foundation gem for grants, one home per artifact, and four endpoints placed

Plans: `6.1-membership-tiers-and-rights.md`, `6.1-points-and-growth-value.md`, `6.1-coupon-wallet.md`, `6.1-scenario-purchases.md`, `6.1-membership-and-loyalty-points.md`, `6.1-miniprogram-extension-architecture.md`.

An adversarial audit of the membership and points plans found the split between them leaking in eight places: endpoints two plans both claimed or neither did, and artifacts nobody owned. The remedies are ownership rulings rather than designs, taken together because they constrain one another.

**One — the grant/benefit primitive is its own foundation gem.** The architecture plan requires "a small shared model the loyalty-family gems depend on, so a coupon and a membership right are not two unrelated tables" and left the owner open (`:64`, `:154`, Open Question 3). Leaving it to "whichever of membership, coupons or points starts first" would make two of the three wait on the first, and the two that already exist disagree on what a grant is: `spree_membership_grants` is keyed on a right with a `period_key`, `spree_point_grants` is a lot with `remaining` and an expiry. **Two — one home per artifact.** A granted coupon is held by the **coupon wallet**; the membership plan records what a grant issued and points at the holding. The growth-value fields of `vip/getUserVipInfo` are served by the **membership** endpoint, whole, because the client fetches that payload once and the tier is its core; the points plan's account endpoint carries points and the ledger only. The membership card issued by a points redemption is issued by the **membership** plan through a non-purchase source on the same lifecycle, not by the points gem, whose own constraint already forbids it.

**Three — four endpoints placed.** `delIntegralOrder` goes to `6.1-scenario-purchases.md` as a `destroy` on the scenario-order resource, because an integral-mall order *is* a scenario order and deletion is a property of that resource rather than of one kind. The activation gift bag is issued by the **membership** plan, calling the points ledger service and the coupon wallet's service: a three-way header declaration rather than an event round trip, because "once per period, never twice" is easier to hold in one transaction than across three subscribers. And `god/getWineValueDetailPage` stays **excluded** with the rest of `god/*` — the membership plan's handoff of it to the points plan is withdrawn, and that plan's own re-exclusion stands.

**Two items the audit found unowned are *not* settled here** and are recorded rather than assigned: `goods/getVipGoods` and `goods/getGoodsVipCategory` (a VIP-gated catalogue read and its categories) have no owner in any plan, and `coupon/getSvipCoupon` is assigned by the membership plan to the coupon wallet, whose own tables never name it. Both are named in the membership plan's dependency table so the next reader sees them as gaps rather than as done.

**Why the rulings are recorded rather than remembered.** Each of the eight leaks was invisible from inside either plan — the membership plan says "everything below the purchase is self-contained", and the points plan says the four moved endpoints "are the scenario plan's". Both sentences were false, and neither plan could have caught it alone. The audit and this entry are the record.

## 2026-09-18 (later) — The grant row lands in core, and `spree_grants` owns the kinds and the service

Plans: `6.1-grant-and-benefit-primitive.md` (new), `6.1-coupon-wallet.md`, `6.1-membership-tiers-and-rights.md`, `6.1-points-and-growth-value.md`, `6.1-gift-card-purchase-and-transfer.md`, `6.1-miniprogram-extension-architecture.md`.

Writing the foundation gem's plan turned up the objection the ruling above had not answered: `6.1-coupon-wallet.md:127` recommends **core** for its own holding, because an extension would otherwise "have to decorate `Spree::CouponCode` and `Spree::Order`". Putting the shared row in a gem leaves that argument standing for every consumer that touches a core model, and answering it once per consumer is how five plans end up disagreeing again.

**Decision — the row is core; the gem owns the kinds and the service.** `spree_grants` and `Spree::Grant` land in `spree/core`, with `SingleStoreResource`, `Metadata`, `has_status`, paranoia, lifecycle events and a `Spree.grant_kinds` registry hook. The `spree_grants` gem at `spree/extensions/spree_grants/` ships the kinds, the service (`grant!`, `claim!`, `consume!`, `revoke!`) and the built-in kinds no other plan owns. A consumer's kind is a gem-local subclass of the core model — its own class, which the extension boundary allows, not a reopening of someone else's.

**Why core rather than the gem, in one line.** It answers the coupon wallet's argument for all four consumers at once, it is the fork's own doctrine ("a generic capability an extension needs lands in core first"), and by the merge-cost rule this set has been using it is the cheap kind of core change: **a new table and a new base model are new files, and it edits no file upstream owns.**

**Ruled with it, and recorded because each constrains the model.** "Shared" means **one table with kinds**, not a base class over per-family tables — the architecture plan's justification is that a coupon and a membership right should not be *two unrelated tables*, and a shared ancestor keeps that criticism intact. The gem is **`spree_grants`**. The gift card's **welfare grant is a kind** — neither consumable nor expiring — rather than a fourth grant-shaped table. And consumption stays **delegated to the kind**, because a primitive-level quantity would put points' partial arithmetic back into the shared row it was just taken out of.

**Consequences.** The architecture plan's Open Question 3 is answered and the "whichever ships first" sentence at `:154` no longer governs. The membership plan's header names the gem and the core row; the coupon wallet's Open Question 1 is answered as core and its holding becomes a kind; the points plan's lot keeps `remaining` and its allocations in its own side table; the gift-card plan's welfare row becomes a kind. The coupon wallet's stored `expired` status is the one item still at odds with expiry-as-a-date and must be reconciled.

## 2026-09-18 (later) — A pricing context is request scope, resolved by core's channel resolution, so the product read does not change

Plan: `6.1-seller-scoped-pricing.md`.

The plan's verification pass left one question it could not answer for itself: the three context reads (区域 / 现场推广 / 线下) were written as a `context=` parameter on `GET /api/v3/store/products/:id`, a route whose controller, serializer and route are core's — so serving it meant either editing an upstream controller (the permanent merge tax this set avoids) or a gem-owned path that shadows core's read.

**Decision.** Neither. **The context is request scope, and the machinery for it already ships.** `Spree::Api::V3::ChannelResolution` resolves the request's channel at the boundary — the publishable key's binding first, then the `X-Spree-Channel` header (code or `ch_…` id, scoped to the store), then `current_store.default_channel` — and writes it to `Spree::Current.channel` (`channel_resolution.rb:40-42,80-81`); the pricing context already falls back to that (`@channel = channel || Spree::Current.channel`, `context.rb:25`), and `Spree::Current.channel` also feeds `catalogs_for` and the global pricing context (`current.rb`). So the product read is **unchanged**, the client asks for the context it is in through the header, and nothing new is built on the server. **The seller is the member that was missing from that scope**, and the routing plan now lands it (its Decisions 17 and 18).

**Why this is the strong answer rather than the cheap one.** The price on the read, the price the cart writes on the line and the price the checkout charges become **one context by construction** instead of three that must be kept in step — and it costs no core edit, no new mechanism and no second payload. It follows the 2026-09-17 ruling's own shape: the request-scope context is where tenancy lives, and the seller is the member that scope was still missing.

**Accepted trade-offs, stated rather than discovered.** The popularize context's detail call carries no identifier of its own (`{ id }` and nothing else), so the context comes from the header the rewritten client sends or, failing that, the customer's binding; a signed-out visitor whose client sends neither sees the default channel's price. And because the context belongs to the request, two contexts cannot be compared inside one request — a screen showing an area price beside an offline price needs two requests.

**Consequences.** The pricing plan's Store API surface shrinks to one route (the seller lookup) and the reads it replaces are core's own. **The routing plan — the keystone — gains the amendment it had been credited with but never written**: its Decision 17 lands `Spree::Current.seller` and the boundary concern, and its Decision 18 puts the seller attribute, that concern and the `StockLocation` geocoding columns in core rather than in the gem. Two plans that read the seller (`6.1-membership-and-loyalty-points.md`, `6.1-seller-scoped-pricing.md`) now have one place to read it from.

## 2026-09-18 (later) — The delivery plugin is the platform's: its fee is a rule, its waivers are promotions, and the platform's quote is cost

Plan: `6.1-local-delivery.md` (renamed from `6.1-instant-delivery-providers.md` in the same pass).

The entry above created the supply half — a provider family dispatching a shop's delivery to a local rider network — and left the price as an open question: pass the platform's live quote through to the customer, or set our own fee. The author ruled the second, and widened the plan from "platform adapters" to **the platform's delivery capability**, because the fee, the gate and the waiver are the same feature from the merchant's side.

**Decision one — the customer-facing fee is the delivery method's own price, and the platform's quote is cost.** `DeliveryMethod` carries two independent columns and this ruling is what they are for: `rate_provider` stays `Internal`, so the **calculator** prices (a flat default fee today; a distance- or time-band calculator is not shipped), while **supply** is `fulfillment_provider`, naming the platform that dispatches. "同城配送 ¥8, dispatched to 达达" is one method. The platform's live quote is recorded on the dispatch attempt as `charged_amount` beside `quoted_amount`, and the difference is the merchant's — or the operator's, when the operator promised the benefit. **The rejected shape is named rather than deleted**: a provider-priced method (`uses_calculator?` false) would pass the live quote through, and the Estimator's `markup_percent`/`markup_flat` is the built-in margin seam for exactly that; it stays available for a merchant who wants the platform's price plus a margin, and the default methods price by rule.

**Decision two — a waiver is a promotion, never a fee engine.** 满额免配送 is `Promotion::Rules::ItemTotal` plus `Promotion::Actions::FreeShipping`; 会员免配送 is `Rules::CustomerGroup` plus the same action, and **the membership plugin needs no change at all**, because a tier is a `Spree::CustomerGroup`. `FreeShipping` writes a `Discount` on the fulfillment for the whole cost and its `persist_at_zero?` is load-bearing — `Order#has_free_shipping?` is a **row-existence test** and `DeliveryRate#final_price` reads it, so a waived fee is a zero row rather than an absent one. The membership plan says in writing that none of its ten rights waives shipping; that stands, and no `free_delivery` kind is added.

**Decision three — who funds a waiver.** A **shop-level** rule is the seller's own money: the customer pays zero, the seller earns less, no transfer is written. An **operator-promised** benefit is funded through `6.1-membership-tiers-and-rights.md`'s `subsidy` seller-transfer kind — the operator owes the seller the waived amount, settled by the sweep and the balance — which is five coupled core edits the membership plan already carries. This plan consumes that capability and does not re-open it.

**Decision four — the plan widens and is renamed.** `6.1-local-delivery.md` owns the platform's delivery capability: supply, the fee and its waivers, and **the 起送 gate**. The gate is a delivery-method rule, which is the shape `DeliveryMethodRules::ItemTotalRule` already is; the client renders a minimum order with **peak and off-peak** variants, and no shipped rule reads the clock, so that rule kind is the one new class here. The client's side is stated so nobody builds what it cannot render: the fee reaches it as `deliveryFee` plus additive `order_service_fee`/`merchant_service_fee` lines (配送服务费总额), a waiver reaches it as **zero**, and a "免配送费 −¥8" row would be a client release rather than a server change.

**Consequences.** Seventeen references across six documents were renamed with the plan, and the architecture plan's two rows for it now describe the widened subject. **Two of the three questions it carried were then answered in the same pass.** 达达's callback signature **is** knowable: `MD5_lower(sort_asc([client_id, order_id, update_time]).join(""))` — three fields, no secret, lowercase, with `update_time` hashed exactly as received because it is milliseconds under `order_status == 1000`. The request side is uppercase, secret-wrapped and over every parameter, so the two signatures live in separate methods; one shared helper would reject every genuine callback. And the ingress question produced a stronger ruling than verification: **a callback is a hint, not a fact** — a terminal state is confirmed by re-querying the platform with our own signed call, which is the only control that holds for **闪送, whose callback carries no signature at all by design**, and for 顺丰同城, whose `sign` concatenation is the one that is genuinely not public. **All three of the questions the plan opened are now answered, and two of the answers corrected the plan's own premises.** Alcohol is a **declared category, not a prohibited cargo**, and the draft had it wrong twice: not every platform takes a two-level category (only the WeChat channel does), and alcohol does have a home — 达达's flat `cargoType` carries **24 酒品**, the WeChat channel carries **日用百货 → 酒水行**, 美团 allows 酒类 with conditions and 蜂鸟 files it under 名酒坊 behind a 食品经营许可证. The clauses that name **酒精** prohibit the flammable liquid, not packaged beverage alcohol. **The exception the dispatcher must respect is 闪送**: no public alcohol category, an unpublished degree threshold in its internal rules, and no 保价 — so it is not a candidate for a spirit order, and alcohol fitness is a per-member fact rather than a family-wide one. The same goes for the capability matrix the walk reads (保价, the 收/取货码 pair, tips, the cancel window), and for the hard caps that can make one delivery impossible — the WeChat channel's ¥5,000 declared-value limit, which a case of 白酒 can breach. Nothing anywhere can verify age, and nothing needs to: the client self-declares 18+ at login, so the integration's alcohol settings are the category, the insurance and the 收货码. **Distance-band pricing stays deferred, and the deferral is now a data question rather than an argument**: no comparable storefront prices delivery by distance (1919 快喝 gives it away with the tiers living in the promise; 歪马送酒 is free above ¥29), the zone workaround is unavailable in this market because the client carries no postal codes, and the plan now records the platform's own routed distance on every attempt — so one month of rows settles whether a flat fee ever loses money. **Decision one — the gem is `spree_service_areas`.** It names what the gem owns rather than one of its consumers and leaves `spree_delivery*` free for the delivery work.

**Decision two — the binding and `Spree::DeliveryZone` are not bridged.** The plan recorded a merchant configuring "the same coverage twice": once as a zone for shipping, once as a binding for seller discovery. The two are not the same coverage, and the ruling says so: a zone answers *may this delivery method serve this address* and matches country, state or postal code; the binding answers *which seller serves this point* and matches a division subtree plus a polygon. **A bridge was rejected on a mechanical ground rather than a preference:** zone members stop at the state, so expressing a district-or-deeper binding through them would either lose the precision the binding exists for or require a new member type in an upstream model. This deployment authors no zone for coverage at all — the client carries no postal codes and delivery is instant and local — so coverage is configured once, in the stock-location form, and the rule is written into the plan's constraints rather than left to habit.

**Decision three — the binding and its geocoding columns stay on `spree_stock_locations`, and the shared contract survives.** The worry was that upstream's `6.0-order-routing.md` (upstream's plan) might land `latitude`/`longitude` first with a different meaning. It does not: it mentions them only inside its own open question and defers them to phase two, and the table carries neither column today — while the geocoding primitive that *does* ship is `Spree::Address`'s columns and its job. Whichever side lands first owns the migration and the other consumes it. Two consumers reading where a location is is one fact, not two meanings; if a future upstream point genuinely differs from a shop's public point, that is a second suite of columns on the anchor that owns the service area, never a rename of these.

**Decision four — two tiers, and the campaign tier stays out.** The client resolves delivery area as shop → special → seller, and the plan modelled two. A **special is inside the decoration bucket the architecture plan excludes**, so it does not come back through this plan. What makes the answer safe is that the middle tier is *derived* whenever it returns: a special belongs to one seller and is delivered by a set of its shops, so its coverage is the union of their polygons, and the only new fact would be the campaign-to-warehouse membership — merchandising, not geography. Until then the two address checks that name it answer from the seller tier, which is a superset of any zone the excluded feature would have defined.

## 2026-09-18 (later) — The first extension gem: `spree/extensions/` is open, and the CI gap it needed closed first

Plan: `6.1-administrative-division-gem.md` (In progress), plus `scripts/test/rspec`, `.github/workflows/tests.yml`, `.gitignore`, `CLAUDE.md`.

The seller scope's first slice landed in core. This is the second: the administrative tree becomes the fork's first extension gem, and the repository gains the scaffolding every later gem needs.

**The CI gap closed first, because the plan requires it before an eighteenth gem appears.** `providers/wechat_pay` and `providers/social_auth` were absent from `.github/workflows/tests.yml` — from both install loops and both matrices — so two shipped gems had **never run their specs in CI**. Both now ride the providers lane, together with `extensions/spree_administrative_divisions`; the lane is where the small suites already live, and the comment says so. The fork's `scripts/test/rspec` learned the third engine root (`spree/extensions/<name>/spec`, beside `spree/<engine>` and `spree/providers/<engine>`), and the root `.gitignore` learned `spree/extensions/*/Gemfile.lock`, which the existing two patterns did not cover.

**The gem is `spree_administrative_divisions`, and it ships the tree, not yet the data.** The model and its migration are here — the five levels, the GB/T and bureau code scheme, `dataset_version`, and the `first_pinyin`/`pinyin` columns the client's picker sorts and anchors on. The dataset files, the import task and the tree resource are the next change; nothing reads the table yet, which is why the plan's status is *In progress* rather than *Implemented*.

**Shipping a table from a gem is a path this repository had never walked, and it needs one more file than the provider gems do.** Every gem here that `rake test_app` builds either ships no migrations or ships a **no-op** install generator (`spree_stripe`, `spree_emails` — both say so in their own comments). The dummy-app builder runs `generators/<gem>/install/install_generator` after `db:migrate`, and **skips it silently when the file is absent** — so the first spec run failed with `Could not find table 'spree_administrative_divisions'` while every other step reported success. The gem therefore carries a real install generator that copies its `db/migrate` into the host app, the shape our own out-of-tree `spree_crm` extension already uses. Worth knowing for every gem that follows: **a table without a generator is a table nobody's dummy app has.**

**One correction to the plan's table, made while implementing it.** The `parent_id` column was specified as `uuid`, carried over from the seller plan. **No table in this repository has a uuid primary key** — the check that settled it was the applied schema, where `spree_sellers` and every other table is bigint — so a uuid foreign key would have had nothing to point at. The gem ships `bigint`, and both plans' tables now say so with the correction recorded rather than silently rewritten.

**The dataset question answered itself, and the answer is that there is no annual refresh to plan for.** The plan deferred *which bureau release to start from and at what cadence*; the first import settled it. The release is the bureau's **2023-06-30** snapshot (31 provinces, 342 cities, 2,975 districts, 41,352 townships), mirrored from `modood/Administrative-divisions-of-China`, and it is probably the last full one — **since October 2024 the National Bureau of Statistics publishes the classification rules but no longer the codes themselves.** So a future refresh is a *different source*, not a newer file from the same one, and nothing in the model, the import or the endpoints changes: a new source becomes a new `dataset_version` directory. The shipped files carry the provenance, the counts and a licence note; the preparation script ships beside them so a release is reproducible rather than mysterious.

**Two data facts the import forced into the open, both now impossible to miss.** The publisher writes province and city codes truncated (`11`, `1101`), so preparation widens them to the six digits GB/T 2260 uses — which is also what makes a row's level readable from its code alone. And **three cities administer no districts and the publisher's tree repeats each of them under its own code**, once as a city and once as the single "district" inside it: 东莞市, 中山市 and 儋州市. A code names one node, so the shallower occurrence is kept, the repeat is recorded in the file's `dropped` field, and the townships (36, 23 and 18) still attach to the city. Left alone, the unique index would have decided which of the two survived — silently, and differently on the second run — so the import now **refuses** a release carrying a duplicate code instead of importing it half-way.

**What the three-place wiring means in practice, and where it is not enough.** The gem is in the CI matrix, its own `Gemfile` resolves the monorepo's dependencies, and the starter's `server/Gemfile` lists it — so a worktree loads it after `bundle install` and `rails spree:install:migrations`. `server/` is a clone rather than tracked code, which is worth remembering: the wiring that survives a fresh worktree is the CI list and the gem's own Gemfile, while the starter's line has to be present in each clone.

## 2026-09-19 — The service-area binding lands in core, and the plan's "the gem owns the polygon" is amended

Plan: `6.1-seller-service-area-routing.md` (the binding columns, the polygon and its validation), with the migration in `spree/core`.

The binding is now real: `spree_stock_locations` carries `administrative_division_id`, the polygon and its bounding box, the geocoding columns, and a partial unique index that gives one active warehouse per node — `deleted_at IS NULL` in the predicate because a stock location is paranoid, so a soft-deleted row that never flipped `active` would hold its node forever. MySQL has no partial indexes, so there the rule degrades to one binding per node and the active-only half is the validation's; the migration says which engine gives which, the way core's own API-key migration does.

**Two amendments to the plan, both recorded in it rather than discovered later.**

**The polygon, its validator and the write-time normalisation are in core, not in the gem.** Decision 18 had them in `spree_service_areas`, but a validator has to attach to `Spree::StockLocation` — a core model — and a gem may not reopen one: this fork's own extension ships no decorators at all, and the architecture plan's boundary forbids it. So the classes sit beside the column they protect, keeping the plan's feature-prefixed names (`Spree::SellerRouting::Polygon`, `Spree::SellerRouting::PolygonValidator`) so the gem can reopen that namespace for `Locate` and `Decision` instead of duplicating it. **The gem keeps everything that needs no core class**: the routing service, the decision object, the reverse geocoders, the code mapping and the endpoint.

**The geometry is hand-rolled rather than RGeo's.** The plan chose in-memory RGeo for portability across the three databases; the same portability arrives without adding a dependency to core, because the shapes are hand-drawn and small — self-intersection is a segment-crossing test, containment is a ray cast, and winding is a signed area. `rgeo` stays available to the gem if routing turns out to need more geometry than this, but core does not carry a geometry library to validate one column.

**The coordinates needed a scale, and MySQL is where that showed.** `t.decimal` with no scale is scale 0 on MySQL, which rounds silently: a warehouse at 39.9089 was stored as 39 — a hundred kilometres from where it is — while the other two engines kept the decimals, so nothing local noticed and the MySQL lane in CI did. The columns are now `decimal(10, 7)` through a migration of their own rather than an edit to the one that added them, because that one has run where this has not. **Upstream's `spree_addresses.latitude`/`longitude` carry the same defect** — the same `t.decimal` with no scale, on the same three-engine support — so address geocoding rounds to whole degrees on MySQL today. It is upstream's migration rather than ours to change, and the fork's own copy of that table is not worth a permanent divergence; recorded here because the first person to compare a geocoded address against a map on MySQL will otherwise spend a day on it.

**What the write path guarantees, and the one thing it deliberately does not.** A polygon arrives either way round and is canonicalised rather than refused — an operator's map editor should not fail over an orientation nobody chose — while genuinely unusable geometry (too few points, an open ring, a non-finite or off-map coordinate, a ring that crosses itself) is refused with a readable message. The bounding box is derived on write, because the match path tests it before parsing anything and a box computed per candidate is a box computed thousands of times.

## 2026-09-19 (later) — The administrative tree is readable: one public collection, cached by release

Plan: `6.1-administrative-division-gem.md` — **implemented**, except for the vendor code maps.

`GET /api/v3/store/administrative_divisions` answers the client's three calls, because they differ in filter rather than shape: no filter is the province list a picker opens with, `parent_code` is its lazy cascade, and `keywords` is its search box — which searches the romanisation as well as the name, since the dataset carries both. Each node answers `{ code, name, level, first_pinyin, has_children }`. The controller lives in the gem and draws its route through `Spree::Core::Engine.add_routes` — the hook this repository's own extension already uses — so no core routes file is touched, and inheriting the Store API's base is what gives it the publishable key, the guest gate and the error shape.

**The cache is keyed by release and filter, so a new import is a new key rather than an invalidation** — the previous release's entries age out on their own, and nothing has to be swept. One key does have to be cleared: the memo of *which* release the table holds, because a rake task that writes a release and leaves every reader believing in the old one strands the whole tree. The import clears it.

**One edge case was worth the spec that found it, and it is now a regression test.** The obvious implementation of `parent_code` resolves the code and matches on the id; a code that resolves to nothing makes that `where(parent_id: NULL)` — which is the root's own predicate — so a question about a node that does not exist would have answered the top of the tree. It answers an empty list instead: a picker whose step disappeared shows nothing, which is the truth.

**What the plan still owes is the Tencent and Amap mapping files.** They ship beside the tree — the ruling moved them here — but nothing reads them until the routing slice's reverse geocoder does, and inventing mapping data before it is needed would be guessing at a shape the mapper should decide.
## 2026-09-19 (later) — The reverse geocoder ships Tencent first, and the seam is what makes that cheap

Plan: `6.1-seller-service-area-routing.md` — Decision 8 amended, Open Question 3 narrowed.

The plan had both adapters shipping with a configured primary and fallback. **The first version ships the Tencent LBS adapter only.** The decision is about a resource rather than a design: a vendor account and its quota belong to the operator, and the second vendor earns its place the day someone holds a key for it — while the pluggable seam is worth nothing if it is only written down and never travelled.

**What is deliberately unchanged is everything that makes a late arrival cheap.** The provider interface, the store-level provider and fallback configuration, and the cache key carrying the provider all stay exactly as written; the fallback path stays in the code even though, in the first version, there is no second provider to try — that is the state a fallback is in most of the time, and `Resolve` handles it. Adding Amap later is one adapter class and one mapping file under `data/administrative/amap/`, not a change to the orchestration, the cache key or the API.

**What the mapping turned out to be, once a vendor was actually read.** The plan (and this entry's own first draft) assumed a translation table: vendor code in, bureau code out, shipped as versioned data beside the tree. Tencent does not need one — **its `adcode` is the bureau's own code at the level it resolved**, so the mapper walks the imported tree from that code instead of translating it, and matches a township by name inside the district. `data/administrative/tencent/` is therefore an exceptions file with nothing in it: it earns its first row the day a vendor name and a bureau name disagree about the same place. The township check the plan owed is unchanged, and it is now the only thing standing between a district-level match and a township-level one.

**Consequences recorded rather than discovered.** The administrative gem's mapping debt is now a single file — `data/administrative/tencent/` — and the plan's township-coverage check narrows to Tencent, with the same check owed for Amap only if it ships. The `preferred_reverse_geocode_fallback_provider` setting stays in the store preferences, unused, because removing and re-adding it would be a migration for a column that costs nothing.

## 2026-09-19 (later) — The fork's features are documented in their gem, not in upstream's docs tree

Decided while shipping `spree_service_areas`, and it applies to every gem this fork builds.

`CLAUDE.md` says a new model or entity gets a page under `docs/developer/`, and `docs/developer` is upstream's Mintlify tree — deployed to the public documentation site and rewritten by every upstream sync. **For the fork's own features the documentation is the gem's `README.md` plus the plan** (`docs/plans/6.1-*.md`), which is what `spree_administrative_divisions` already does and what this ruling makes deliberate rather than accidental. A page there would be a merge conflict on every sync, for content that describes software nobody outside this deployment runs.

**What still goes in `docs/developer`** is anything that belongs to upstream's own surface: a core or API behaviour this fork changes, or a page upstream's readers expect to find. That is the original rule's real subject, and it is unchanged.
