## Summary

The mini program calls 85 coupon and promotion endpoints. Spree's model is the inverse of what they assume: a promotion carries an order-usable code, and **a code is not an asset a customer holds**. `Spree::CouponCode` (`spree/core/app/models/spree/coupon_code.rb:7,16-18`) has no `customer_id` — it binds only to a promotion, a cart and an order — so there is no wallet, no per-customer code, no expiry the customer can see and no way to give a code to a friend. This plan adds the holding as a small, generic core capability, because the alternative is an extension that decorates `Spree::CouponCode` and `Spree::Order`, which the extension boundary forbids. It deliberately builds no discount engine: promotion stacking is already scheduled for 6.1.

## Key Decisions (do not deviate without discussion)

- **A code is a promotion artifact; a holding is the customer's asset.** `spree_coupon_holdings` is a new, small table pointing at an existing `Spree::CouponCode`. `Spree::CouponCode` does **not** gain a `customer_id`: one code row can be held, released and re-held, and putting the holder on the code would make the promotion's code pool and the customer's wallet the same object, which they are not.
- **One application mechanism, forever.** Codes continue to be applied through `Spree::PromotionHandler::Coupon`, reached from `POST /api/v3/store/carts/:cart_id/discount_codes` (`spree/api/config/routes.rb:55`). `decisions.md` (upstream, 2026-07-29, “Admin discount application follows the Saleor shape”) fixes that as the single path for both the storefront and the admin, and a wallet is a place to *keep* codes, not a second way to apply them.
- **Stacking is not built here.** `6.0-6.1-split-adjustments.md:110` states that 6.0 ships winner-only and stacking-ready, and that 6.1 adds `Promotion#combines_with` with "no migration, no adjuster rewrite"; the seam is isolated at `spree/core/app/models/spree/adjusters/promotion.rb:50-56`. A wallet that stores codes ships before that. A wallet whose value is "use ten at once" cannot.
- **A purchased voucher bundle is not a new product type, and it does not ride the gift card's issuer.** `6.0-6.1-loyalty-gift-cards-store-credits.md:88-106` designs a purchasable prepaid instrument that phase 2 issues from `order.paid` through `Spree::GiftCards::IssueFromOrder`, and `:131` forbids a second non-physical flag that would have to be reconciled with `gift_card`. A coupon bundle is the same shape as a gift card **purchase** — prepay, then receive codes — but not the same channel: the mini program buys a bundle in one call and settles it as a scenario order, so it never reaches `order.paid` and never meets the gift card's issuer. Register `coupon_combo` with `6.1-scenario-purchases.md` and issue the codes from that kind's settlement step, following `IssueFromOrder`'s idempotency rather than extending the workflow. The member add-on pack (会员加量包) is the same object carrying a tier condition, so it rides the `rights` kind rather than a third registration, and the tier that may buy one is a membership right and not a column here.
- **Stored value surfaces under Loyalty, never Promotions.** `6.0-6.1-loyalty-gift-cards-store-credits.md:127` makes this binding on all current work: "Do not add anything new under the Promotions nav group or docs group unless it is a discount mechanism."
- **The holding is a kind of the shared grant row, and the wallet is a gem (2026-09-22).** The 2026-09-18 ruling applied: `Spree::Grant` is core's and already built, its kinds are gem-local subclasses, so a holding is a `Spree::Coupons::Holding` kind beside a small side table — the code it points at, the campaign that minted it, and how it came to the customer. Status, expiry, holder and idempotency are the grant row's. **The table sketch this plan first carried (`status`, `source`, `granted_at`, `expires_at` on the holding) and its "in core" sentence are superseded by that ruling**, not amended: nothing here decorates `Spree::CouponCode` or `Spree::Order`, so the objection that argued for core is answered for every consumer at once. The domain's tables and reads live in `spree/extensions/spree_coupon_wallet/`, the way the points programme's live in `spree_points`.
- **A campaign names the promotion whose codes it hands out (2026-09-22).** `spree_coupon_campaigns.promotion_id`: a code belongs to a promotion and the campaign is what decides which one, so without it "what does this campaign hand out" is unsayable. A campaign whose promotion is not a multi-codes one is refused, because only a multi-codes promotion has code rows to give, and minting is `Spree::CouponCodes::BulkGenerate`, which ships.
- **The wallet holds `Spree::CouponCode` (2026-09-22).** Open Question 4 answered as this plan assumed: the row that can be held, released and given away on its own. **Accepted consequence:** a coupon a customer can keep comes from a multi-codes promotion, and a single-code promotion's `code` column is not made into a holdable asset.
- **`Spree::CouponCode.state` is left alone (2026-09-22).** Open Question 3 stays open rather than answered here: the holding's status is the grant's and the wallet read shows both, so nothing in this run turns on it, and migrating an existing column is a breaking change to a public-ish model that wants an upstream ruling.

- **A new status column follows 6.0 conventions, not `CouponCode`'s.** `Spree::CouponCode.state` is an integer enum with a default of 0 (`spree/core/app/models/spree/coupon_code.rb:7`, migration `20241004181911`), which predates the `has_status` convention and breaks the rule against defaults on status columns. The holding uses a string `status` set by its creating workflow and does not copy that shape.

## Design Details

### The holding: a kind of the shared grant row

The row every consumer shares already exists — `Spree::Grant` in core, whose holder is nullable so a campaign can mint a holding before anyone claims it, written through `Spree::Grants` in `spree_grants`. A holding is a **kind** of it, so what this plan owns is the coupon's own columns beside the grant:

```ruby
create_table :spree_coupon_holdings do |t|
  t.references :store, index: true
  t.references :grant, null: false, index: { unique: true }  # owed, granted, expiring, consumed: the primitive's, for every kind
  t.references :coupon_code, null: false, index: true        # the existing Spree::CouponCode
  t.references :campaign, index: true                        # what minted it; null for a purchase or an operator's hand
  t.string   :source, null: false                            # draw/exchange/purchase/gift/admin/sms
  t.datetime :deleted_at
  t.timestamps
end
```

- `Spree::CouponHolding` inherits `Spree.base_class`, includes `Spree::SingleStoreResource` and `Spree::Metadata`, uses `acts_as_paranoid`, publishes lifecycle events, and declares uniqueness on `coupon_code_id` and on `grant_id` with matching unique indexes — a code is held once, and one grant is one holding.
- **Status, expiry and the holder are the grant's.** `has_status`, `expires_at` and `customer_id` are core's columns, `expired` stays a display fact derived from the date, and the wallet's own status is read through the grant rather than stored twice.
- **`source` is the wallet's own axis** — how the customer came by the code — and is a column rather than a preference because every kind shares it and the wallet filters on it.
- The kind is `Spree::Coupons::Holding`, registered in `Spree.grant_kinds`, answering `coupon_holding` on the wire.

### Core capability: transfer

A coupon transfer is **a row of the shared transfer primitive** (`6.1-transfer-primitive.md`), not a table of this plan's. The primitive owns the opaque token, the window and the three endings — `pending`/`accepted`/`canceled`, with `expired` derived from the date rather than stored — and it points at whatever is being moved, here a `Spree::CouponHolding`. What this plan contributes is the contract on the holding: **given** reserves nothing (a coupon has no balance to hold), **accepted** moves the holder to the recipient, **canceled** releases nothing. The three workflow classes an earlier draft registered in `Spree::Dependencies` go away with the table: the steps that differ per domain are the contract methods, and the steps that do not are the primitive's own. The token stays opaque and addressable without a session, matching the shape `spree/api/config/routes.rb:158-159` already uses for company invitations.

**A coupon transfer moves a holding, never a card.** `Spree::GiftCard` carries bearer semantics — a card is money and assigning `customer_id` is how it is restricted (`6.0-6.1-loyalty-gift-cards-store-credits.md:102`) — and a coupon must keep its promotion linkage, which a card has nowhere to carry. The gift-card plan's donation and this transfer share the row (`6.1-transfer-primitive.md`) and nothing else: what moves is a holding here and a card there.

### Core capability: campaigns

`spree_coupon_campaigns`: `store_id`, `name`, `status`, `type` (string, `null: false` — the subclass, e.g. `Spree::CouponCampaigns::Draw`), a `preferences` column, `starts_at`, `expires_at`, `deleted_at`. The family is **a subclass and a registration**, matching `Spree::CommissionRule` exactly (`commission_rule.rb:17,48`; migration `20260816210001:71-83`): `include Spree::PreferenceSchema`, `registers_subclasses_via { Spree.coupon_campaign_types }`, a `type_must_be_registered` validation, and the `respond_to?(:jsonb)` guard on the preferences column. Each kind **declares its own settings as preferences**, so a new kind is a class plus a registration rather than a column — which is what the `settings` blob an earlier draft of this row carried would have prevented, since a kind's configuration would have lived in a hash no class owned. The admin picker is built from the registry (`GET /api/v3/admin/coupon_campaign_types` → `{ type, label, preference_schema }`), never a hardcoded array. The mini program's acquisition endpoints are six **built-in** kinds of the same thing — draw (`drawCoupon*`, `drawGodCoupon`), exchange (`exchangeCoupon`, `exchangeBig*`), new-customer (`getNewUserCoupon*`), site-scoped (`gotRegisterAndGotSite`, `getShopArea`), surprise and SMS (`*SurpriseCoupon*`, `smsSurpriseCoupon`), and third-party links (`thirdCoupon*`, `receiveLinkCoupon`). They differ in eligibility and issuance, not in structure, so they are one model with a `type` rather than six tables.

Merchant-facing extra fields on a campaign go to Custom Fields, not columns, per `AGENTS.md`.

### Voucher products and bundles

No new model for the codes themselves. A `couponGoods/*` purchase (buy goods to get or use a coupon) is merchandising over the phase 2 substrate plus a promotion linkage, and a `coupon_combo/*` bundle takes the scenario route described below. What is genuinely new is the issue step: a settled `coupon_combo` scenario order has to mint the bundle's codes and place them in the wallet, idempotently, keyed to that scenario order — and **the minting already ships**: `Spree::CouponCodes::BulkGenerate` (`spree/core/app/services/spree/coupon_codes/bulk_generate.rb`) takes `(promotion:, quantity:)`, generates collision-safe codes and writes them with `insert_all`, so what this plan adds is the wallet-side placement and the idempotency key rather than a code generator (checked 2026-09-18; an earlier draft said the step "has to mint" them without noticing the service). `Spree::GiftCards::IssueFromOrder` is not the place for it — the workflow runs on `order.paid`, and `coupon_combo/addCouponCombo` sends only `{ couponComboId, siteId }` and settles through `coupon_combo/payCouponComboByWxMp` (`miniprogram/pagesC/coupon-combo/details/details.js:162-172`), so no cart order exists for it to fire on.

**The member add-on pack is the same family, and it is ruled (2026-09-17).** The
member centre sells it as 会员加量包, and it is a bundle of promotional coupons —
not a product, and not a scenario kind of its own. Three `rights/*` endpoints
follow it here from `6.1-membership-tiers-and-rights.md`: `getRightsAddDetails`
(what one pack holds and what it costs a member), `addCouponOrder` (buy one), and
the dead `getRightsAddDetailsCouponList`. The purchase rides the scenario order's
**existing** `rights` kind (`6.1-scenario-purchases.md:61`), whose settlement step
mints the pack's codes into the wallet exactly as `coupon_combo`'s does — so no new
kind is registered and no new model is added.

What is **not** this plan's is the tier condition. Only the tiers a membership
right names may buy a pack, and the buyer's term end bounds it, which is why the
pack detail carries `svipEndDate`. `6.1-membership-tiers-and-rights.md` owns that
binding as its `add_bag` right; this plan reads it as eligibility, the way a
campaign reads any other condition.

This depends on the loyalty plan's own deferred question at `:138`, "several gift cards on one order" — a bundle *is* several on one order — so that question must be answered before either is built.

### Channel-specific work stays in a provider gem

`spree/providers/wechat_promotions` ships no migrations and patches nothing. It holds: the SMS coupon hand-off, receiving a coupon from a 公众号 or mini-program link (`receiveLinkCoupon`), and the payment scenes that pay for a bundle (`payCouponComboByWxMp`, `payCouponComboByChinaumsWxPay`). Those payments are not a coupon concern at all — they are scenario purchases settled through the ordinary payment-session flow, which `6.1-scenario-purchases.md` owns.

`thirdCoupon*` (fetching a coupon from an external partner) is a third-party API integration: Faraday with timeouts, retries and a circuit breaker, and VCR-recorded specs, per `AGENTS.md`.

## Migration Path

1. The gem (`spree/extensions/spree_coupon_wallet/`) with the holding as a grant kind and its side table, and the Store API wallet read. A wallet that only stores and shows codes is useful on its own and does not need stacking. **Being built** (2026-09-22).
2. `spree_coupon_campaigns` — the promotion its codes come from included — and the receive and draw endpoints. **Being built** (2026-09-22). The exchange kind's own client flow (hand a coupon back, take a bigger one) is read but its semantics are ambiguous in the client, so it is registered and filled by whichever step settles it rather than guessed here.
3. Transfer — the contract on `Spree::CouponHolding` and this plan's three routes, landing together with the primitive's other two consumers (`6.1-transfer-primitive.md`) rather than ahead of them.
4. The provider gem for SMS coupons, link receipt and the external-partner fetch.
5. Voucher bundles, gated on the loyalty plan's phase 2 and its "several on one order" question.
6. Dashboard: the Loyalty nav group gains wallet configuration and campaign management.
7. Regenerate types, Zod, OpenAPI and SDK tests after each step.

## Constraints on Current Work

- **Do not add `customer_id` to `Spree::CouponCode`.** The holder is the holding.
- **Do not add a second code-application path.** `carts/:cart_id/discount_codes` and `Spree::PromotionHandler::Coupon` are the only ones.
- **Do not build a discount engine to make a wallet work.** Stacking arrives through `Promotion#combines_with` in 6.1.
- **Do not add a new non-physical product flag.** The prepaid-instrument flag is `spree_products.gift_card`.
- **Do not surface the wallet under Promotions** in the dashboard nav or the docs tree. Stored value goes to Loyalty.
- **Do not put merchant-managed campaign fields in columns.** Custom Fields.
- **Do not validate a campaign `type` against a literal array, and do not branch on one in a serializer.** Wherever a kind tempts either, the answer is a subclass plus a registration (`docs/plans/decisions.md`, 2026-09-17). The six acquisition kinds above are the built-ins, not a closed set, and the picker reads the registry rather than a list.
- **Do not let a coupon code appear in an event payload, a log or a share image for a code the current customer does not hold.**
- **Do not put a status, an expiry or a holder on the holding's side table.** Those are the grant row's; a second set of columns is the drift the shared primitive exists to prevent.
- **Do not add a coupon wallet table to core.** The row is core's; the wallet's own tables are the gem's.
- **Do not mint a single-code promotion's `code` into a wallet.** A holdable coupon is a `Spree::CouponCode`, and only a multi-codes promotion has them.
- **Do not build a coupon transfer table.** A transfer is a row of the shared primitive (`6.1-transfer-primitive.md`); what this plan adds is the contract on the holding, and the three workflow classes an earlier draft registered are gone with the table. The status vocabulary is the primitive's `pending`/`accepted`/`canceled`, with `expired` derived from the date.

## Open Questions

1. ~~**Does the holding live in core or in an extension?**~~ **Settled 2026-09-18: core, as a kind of the shared grant primitive.** The recommendation above is adopted and generalised — the grant row is core (`spree_grants` + `Spree::Grant`), while the kinds and the service live in the `spree_grants` gem (`6.1-grant-and-benefit-primitive.md`; `fork-decisions.md`, same date). A holding becomes a kind of it whose holder is unclaimed until someone claims the code, and the decoration argument is answered once for every consumer rather than once per consumer.
2. **What does a purchased bundle actually yield?** "N codes on one order" needs `Promotion#combines_with` plus the loyalty plan's "several on one order" question answered; "N separate orders" needs no stacking but makes a bundle a checkout flow rather than a product. Unblocked by a product decision.
3. **Should `Spree::CouponCode.state` be migrated to a string status?** It is an integer enum with a default, which 6.0 forbids for new columns. Migrating it is a breaking change to an existing public-ish model; leaving it means two coupon status conventions coexist. No plan in the repository covers this. Unblocked by an upstream ruling.
4. ~~**Which "coupon" does the wallet hold?**~~ **Settled 2026-09-22: `Spree::CouponCode`** — the row that can be held, released and given away individually. The consequence, recorded in Key Decisions, is that a holdable coupon comes from a multi-codes promotion.
